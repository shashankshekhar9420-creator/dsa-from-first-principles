Queue: Why Does FIFO Exist?

We have just spent several articles on sliding window. One of the most important ideas was that when a window moves, something enters from the right and something leaves from the left: [2 1 5] becomes [1 5 3], the 2 leaves and the 3 enters. That sounds simple, but it hides an interesting question: what data structure naturally represents things entering from one side and leaving from the other?

That is where the queue comes in. But rather than starting with "a queue is a linear data structure that follows FIFO", let us first understand why we would want such a thing at all.

The first thing that enters should be the first thing that leaves.

1. Start with a real problem

Imagine a line of people waiting at a counter: A B C D, with A at the front. A arrived first, so when the counter becomes free, A is served. Then B, then C, then D. The rule is obvious: the person who arrives first gets served first. This is not arbitrary. If D could suddenly go before A, the line would stop behaving like a line.

First In → First Out. FIFO.

2. Why not just use an array?

We could say: "fine, I will store the people in a list." Joining the line is queue.append("E"). Leaving is queue.pop(0), removing the first element. Conceptually this works. But think about what an array-like structure has to do after removing the front: every remaining element has to shift.

The naive way, in slow motion

The dashed cell is the gap left by the removal. Watch it travel to the back.

With a million elements in the queue, removing the first one would mean dealing with all the elements behind it.

We do not merely want a container that can represent a queue. We want a structure whose operations naturally match the behaviour of a queue.

3. The queue's actual job

Forget the people for a moment. A queue has a very simple responsibility: new things join at the back, old things leave from the front. That is the entire idea.

So the queue gives us two core operations. Enqueue adds something to the back. Dequeue removes something from the front. There are also two ways to inspect it: peek (see who is next without removing them) and is_empty (is anyone waiting?). The ordering is preserved automatically. Try it yourself:

New elements enter at the back. Oldest elements leave from the front.

4. Queue is about access order

It is easy to reduce data structures to vocabulary, so this is worth emphasizing. A queue is not interesting because it stores a bunch of values. An array can do that, and so can a list, a set and a dictionary. Pick a structure:

The important thing about a queue is that it controls which element gets access next.

For A B C D the queue says: A first, B second, C third, D fourth. The order in which elements arrived determines the order in which they leave.

5. Queue versus stack

A useful comparison, because it shows that a data structure is really about rules of access. A queue says: first one in, first one out. A stack says: last one in, first one out (LIFO), like a stack of plates where the most recently placed plate is the easiest to remove. Both receive A, B, C, D in that order. 6. The simplest interface, and Python's deque

We do not need many operations to understand a queue, and we do not need to memorize a large API. We just need the invariant from before. Python gives us a natural structure:

Python code (click to hide or show)
from collections import deque

q = deque()

q.append("A")      # enqueue: add to the back
q.append("B")
q.append("C")

q.popleft()        # dequeue: remove from the front
q[0]               # peek: look at the front without removing
len(q) == 0        # is_empty (also: not q)

Despite the name, deque means double-ended queue. We will come back to the "double-ended" part in the next article. For now we use it as an ordinary queue. Step through the code and watch the queue.

One caution: popleft() on an empty deque raises IndexError, which is why is_empty exists.

7. Why deque and not a list?

A normal Python list is optimized around array-like behaviour. Repeatedly calling queue.pop(0) asks for the first element to be removed, and the remaining elements may need to shift. A deque is designed specifically for efficient operations at its ends. Drag the slider to see how the work grows.

listdeque
Add at the backO(1) amortizedO(1)
Remove from the frontO(n): elements shiftO(1)
Read the middle by indexO(1)O(n)

The trade-off is honest: a deque gives up fast random access in the middle to get fast access at both ends. For a small queue you will not notice any difference, because the shifting is a quick memory move; the point is how the cost grows. The lesson is not about memorizing implementation details.

Choose a data structure whose natural operations match the operations your problem needs.

If your problem constantly says "add at one end, remove at the other", a queue-like structure is a natural fit.

8. Now look back at sliding window

Remember what happens when a fixed-size window moves from [2, 1, 5] to [1, 5, 3]: 2 leaves, 3 enters. Does that remind you of anything? A queue does almost exactly this: the oldest element is removed from the front, a new one is added at the back. Step through a sliding window and watch the matching queue underneath.

Python code (click to hide or show)
from collections import deque

def windows_as_queue(nums, k):
    q = deque()
    for x in nums:
        q.append(x)            # enters at the back
        if len(q) > k:
            q.popleft()        # oldest leaves from the front
        if len(q) == k:
            print(list(q))

This does not mean every sliding-window problem should use a queue. Definitely not. Most of the sliding-window problems we solved did not need one. But it gives us a useful new way to think: the movement of a sliding window and the movement of a queue have something in common.

Something old leaves from one side while something new enters from the other.

9. A queue is about things moving through time

If A, B, C, D enter over time, the queue preserves their arrival order, and eventually they leave in that same order. So a queue is particularly useful when elements have a lifetime: enter, wait, leave. In a sliding window, an element enters the window, stays inside for some time, and eventually the left pointer moves past it. It expires. Drag the time slider with a window of size 3.

The queue gives us a natural language for thinking about that lifecycle.

10. But there is a problem: order is not value

Now we reach the important part. Suppose the window is [2, 1, 5] and we ask: what is the maximum element? The queue can tell us that 2 arrived first and that 5 arrived last. But it cannot tell us that 5 is the maximum. A queue cares about arrival order, not value. The queue says 2 leaves first, while our problem says 5 is the largest. These are completely different questions.

Drag through the windows of [2, 1, 5, 3, 4, 1, 6, 2] with k = 3. Yellow is who leaves next (the queue's front), green is the maximum.

A queue answers "who leaves next?". Sliding Window Maximum asks "who is the best candidate?".

So simply putting the window into a queue does not solve Sliding Window Maximum, and this is exactly where the next idea begins.

13. A useful way to recognize these problems

When you meet a new problem, do not ask "which structure is this?". Ask:

  1. Do things arrive and leave in a fixed pattern? Adding at one end and removing at the other points to a queue.
  2. Who should be served first? The oldest suggests FIFO, the newest suggests LIFO.
  3. Do elements have a lifetime? Enter, wait, expire is the language of a queue.
  4. Am I asking about order or about value? A queue answers order only. A question about the best element needs more.
  5. Which operations will I repeat? If it is removing from the front, avoid a plain list and use deque.
  6. Do I need both ends? If so, a double-ended queue is the next step.
