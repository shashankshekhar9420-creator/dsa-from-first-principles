Two Problems That Make Two Pointers Click: Container With Most Water and Trapping Rain Water

We have already seen the basic idea behind two pointers. But knowing that an algorithm uses two pointers is not the same as understanding why two pointers are possible. That distinction becomes especially important with two famous problems:

  • LeetCode 11: Container With Most Water
  • LeetCode 42: Trapping Rain Water

They look similar. Both involve vertical bars. Both involve water. Both have elegant two-pointer solutions. And yet the reasoning behind the two solutions is slightly different, which makes them excellent problems for developing intuition. Instead of starting with “This is a two-pointer problem. Where should I put the pointers?” we’ll start with a better question:

What information does the problem give us, and what possibilities can we safely eliminate?

That is where the algorithms come from. As before, every section has something you can click, and code can be hidden with the button at the top.

1. Container With Most Water

Consider height = [1, 8, 6, 2, 5, 4, 8, 3, 7]. Each number is the height of a vertical line. If we choose two lines, they form a container. The amount of water it can hold depends on two things: how far apart the lines are, and how tall the shorter line is.

area = (right − left) × min(height[left], height[right])

Why the shorter line? Because water cannot rise above it. If one wall is 10 tall and the other is 5, the container only holds water up to 5. The shorter wall is the bottleneck. Build a container yourself. Move the two sliders and watch the blue region, and what happens to the taller wall’s extra height:

The bottom line of that widget already hides the key idea. If we keep the shorter wall and move the other wall inward, the best we could possibly do is (width − 1) × shorter, which is always less than what we have. We will come back to this. First the obvious solution.

Start with the obvious solution

Try every pair of lines: for every i, pair it with every j > i.

Python code (click to hide or show)
def max_area(height):
    best = 0

    for i in range(len(height)):
        for j in range(i + 1, len(height)):
            width = j - i
            water_height = min(height[i], height[j])

            best = max(best, width * water_height)

    return best

There is nothing intellectually wrong with this solution. In fact it is useful because it exposes the real problem: do we actually need to examine every pair? With 10,000 lines there are 49,995,000 pairs. Most of them cannot possibly be the answer. The challenge is finding a way to prove that. Here is every pair for our nine lines, each cell holding that pair’s area:

Start with the widest possible container

The two outermost lines have something special: the largest possible width. No pair is farther apart. Suppose the heights there are left = 8 and right = 5. The container’s height is 5, because the right wall is shorter. Now ask: what happens if we keep the right wall and move the left wall inward? The width gets smaller, and the right wall is still only 5, so the new container is at most smaller_width × 5. That is less than old_width × 5. There is no reason to examine that possibility, and we have eliminated a whole group of candidates at once.

See it with numbers. The wall at the left is 8 and the wall at the right is 5. Every container that keeps the 5 and pulls the other wall inward is listed below, next to the container we already have:

The first big insight

If the left wall is taller than the right wall, moving the taller wall inward is useless: the width decreases, the shorter wall remains the bottleneck, and the maximum possible height does not improve. So to find a better container we need to get rid of the shorter wall:

Python code (click to hide or show)
if height[left] < height[right]:
    left += 1
else:
    right -= 1

This isn’t a rule we memorized. It is a consequence of the geometry. Now make the decision yourself, on a real run. At each state, choose which wall to discard. If you pick the wrong one, you’ll see exactly what that choice throws away:

The trade-off is the algorithm

Every time we move a pointer inward, we knowingly sacrifice width. Why would we do that? Because we are searching for greater height: move inward, lose width, hopefully gain height. But which wall should we replace? The shorter one, because it is the one preventing a greater height. The taller wall is already tall enough. Here is the full run on the example. Watch the width fall by exactly 1 each step, and what the height has to do to compensate:

The two-pointer algorithm emerges naturally

Start at the widest possible pair. At each step: calculate the current container, record the best answer, look at the shorter wall, discard it, move inward.

Python code (click to hide or show)
def max_area(height):
    left = 0
    right = len(height) - 1
    best = 0

    while left < right:
        width = right - left
        water_height = min(height[left], height[right])

        best = max(best, width * water_height)

        if height[left] < height[right]:
            left += 1
        else:
            right -= 1

    return best

The important line is not the multiplication. It is the if. That line represents a proof: once a wall is the shorter wall, every container using that wall with a narrower width cannot improve upon the current container, so we eliminate it. Step through it, with the geometry drawn:

The search space, drawn properly

Here is the same run on the grid of all pairs. Yellow is the pair being compared, blue is what this comparison just ruled out, grey was ruled out earlier, green is the best container. A discarded left wall wipes out a whole row; a discarded right wall wipes out a whole column:

How much did that buy?

The gap right − left starts at n − 1 and shrinks by exactly 1 every step, so there are at most n − 1 comparisons. That is O(n) time and O(1) space, against n(n−1)/2 pairs:

Why starting from the outside is important

Why not start somewhere in the middle? Because we want to begin with the maximum possible width: n − 1. Every future move makes the width smaller, so moving inward is expensive. We’re giving up something valuable, so we only move inward when we have a reason: the current shorter wall cannot help us anymore. This is a useful general mindset:

When an operation sacrifices something, ask what makes the sacrifice safe.

A subtle but important point

Notice that we are not saying “the shorter wall can never be part of the optimal answer.” That is too strong. The shorter wall might well be part of some optimal pair. What we are saying is more precise:

Given this particular pair and its width, every future pair that keeps this shorter wall has a smaller width, while its height cannot exceed the height of the other wall unless the shorter wall is replaced. So continuing with that wall is useless from this state.

Why is that enough? If the best pair uses the shorter wall, that pair was either already measured (when the pointers were at it), or it has a smaller width than the pair we hold and no more height, so it can’t beat the pair we hold. Good algorithms are built from precise statements like this rather than vague assumptions. And you don’t have to take my word for it:

Container With Most Water: the intuition

Start with maximum width. The shorter wall is the bottleneck. Since moving inward always loses width, the only movement that can possibly compensate is replacing the shorter wall with something taller.

That is why the pointers move. Not because “container problems use two pointers.”

2. Trapping Rain Water

Now the second problem. At first glance it looks almost identical. We again have vertical bars, height = [0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1], but we’re asking a different question. We’re not choosing two walls. We’re asking: how much water is trapped across the entire landscape? Rain falls, and water collects in the valleys:

Start with one position

Forget the whole array for a moment and stand at one position i. How much water can sit above it? We need two things: the tallest wall to the left, left_max, and the tallest wall to the right, right_max. The water level is set by the shorter of those two boundaries, so

water[i] = min(left_max, right_max) − height[i]

(if positive; it is never negative because both maxima include height[i] itself). Why the minimum? Because water escapes over the shorter boundary. If the left boundary is 10 and the right is 6, the level only reaches 6, and the right wall is the bottleneck. Slide to any position. Blue bars are the two boundaries, the orange block is the water above this position:

The obvious solution

For every position, search for the highest wall on each side, then calculate the water:

Python code (click to hide or show)
water = 0

for i in range(n):
    left_max = max(height[:i + 1])
    right_max = max(height[i:])

    water += min(left_max, right_max) - height[i]

This works conceptually, but we’re repeatedly searching through the same data.

First improvement: remember what we’ve already discovered

Instead of recomputing the maximum on the left, maintain it. Likewise for the right. Every position can then be evaluated from the two running maximum rows:

Python code (click to hide or show)
def trap_prefix_suffix(height):
    n = len(height)
    left_max = [0] * n
    right_max = [0] * n

    left_max[0] = height[0]
    for i in range(1, n):
        left_max[i] = max(left_max[i - 1], height[i])

    right_max[n - 1] = height[n - 1]
    for i in range(n - 2, -1, -1):
        right_max[i] = max(right_max[i + 1], height[i])

    return sum(min(left_max[i], right_max[i]) - height[i] for i in range(n))

This is already a useful optimization, from O(n²) to O(n) time, at the price of O(n) extra space. But we can ask an even better question:

Do we actually need to know both maximums at every position?

This is where the two-pointer solution appears.

The key observation

Suppose at some point we know left_max = 5 and right_max = 9. The water level is min(5, 9) = 5. The right side could be 9, or 100, or 1,000,000. It doesn’t matter. As long as the right side is at least 5, the left side is the bottleneck. So we can calculate the left side without knowing the exact maximum on the right. All we need is the knowledge that the right side is high enough. Move the sliders and find where this stops being true:

Why the smaller maximum determines what we can process

With left_max = 5 and right_max = 9, the right side has already proved “I am at least 9,” so it cannot be the limiting boundary. The left side is. So we can safely process the left side. Conversely, with left_max = 9 and right_max = 5, the right side is the bottleneck, so we process the right side:

Python code (click to hide or show)
if left_max <= right_max:
    # process left
else:
    # process right

Notice how different this is from Container With Most Water:

Container With Most WaterTrapping Rain Water
What decides the movethe shorter current wallthe smaller known maximum boundary
What the pointer doesmoves (discards that wall)processes that side, then moves
What it meanskeeping this wall can’t helpthis side’s answer is already decided

Both involve a bottleneck, but the bottleneck represents different things.

Why can we calculate a position before knowing the other side exactly?

This is the most important question in the entire problem. Suppose left_max = 4 and right_max = 7, and we’re processing a position on the left. We know right_max ≥ 7 and left_max = 4, so min(left_max, right_max) = 4. No matter what the exact right maximum turns out to be, it is already at least 7, so the water level 4 is guaranteed. If the current bar has height 1, the water above it is 4 − 1 = 3. We can finalize that answer. We don’t need to wait for more information. Try it, on a real run. At each state, decide which side’s answer is already determined:

A general algorithmic idea

You don’t always need complete information to make a decision. You only need enough information to make the decision certain.

Once we know left_max ≤ right_max we have enough information. The right side doesn’t need to be completely understood: it has already been proven sufficiently tall. This is what allows us to throw away a position after processing it.

Deriving the two-pointer solution

We maintain left = 0, right = n − 1, left_max = 0, right_max = 0, and process inward. If left_max ≤ right_max, the left side is the limiting side: update left_max with height[left], add left_max − height[left] to the answer, and move left. Otherwise do the mirror image on the right.

Python code (click to hide or show)
def trap(height):
    left = 0
    right = len(height) - 1

    left_max = 0
    right_max = 0

    water = 0

    while left <= right:
        if left_max <= right_max:
            left_max = max(left_max, height[left])
            water += left_max - height[left]
            left += 1
        else:
            right_max = max(right_max, height[right])
            water += right_max - height[right]
            right -= 1

    return water

Blue water is finalized. Yellow bars are the two pointers. Lighter bars have been processed. The last two presets use the wrong rule on purpose, processing the side with the larger maximum:

Understand the movement rather than memorize the code

Read the if in plain English: “Which side currently has the smaller boundary?” If left is smaller: “Left is the bottleneck. Therefore I already know the water level on the left. Process it.” If right is smaller: “Right is the bottleneck. Therefore I already know the water level on the right. Process it.” That is the algorithm.

Why not move the side with the larger maximum?

Suppose left_max = 5 and right_max = 9. If we process the right side instead, we don’t know the exact water level there, because the left side is only guaranteed to be 5. The right position’s level depends on information from the left, so we shouldn’t finalize it yet. The left side, however, is already determined. The principle:

Process the side whose answer is already determined by the information you have.

The deeper meaning of the two pointers

It is tempting to say “so two pointers means move from both ends.” That’s not the real lesson. The pointers help us maintain two pieces of information, the highest boundary discovered on the left and the highest boundary discovered on the right, and they let us gradually finalize positions once enough is known. The pointers aren’t the idea. The information they maintain is the idea.

3. Why not sort, and why not one approach for both?

Why not sort the array?

Suppose we sorted the heights. The problem depends heavily on position: a wall on the left and a wall on the right create a basin. Rearrange the heights and you destroy the landscape. For Container With Most Water, sorting also destroys width information, since right − left is essential. Compare:

Why not use the same approach for both problems?

The problems look so similar, but Container is searching for the best pair, while Rain Water is calculating the contribution of every position. That difference changes the reasoning.

Container
Choose two walls
↓
maximize their area

The pointer movement is about eliminating impossible candidate pairs. “Can any pair involving this shorter wall beat the current pair?” No, so discard it.
Rain Water
Evaluate every valley
↓
sum all trapped water

The pointer movement is about finalizing positions whose answer is already determined. “Can I determine the water level here yet?” Yes, so process it.

A much deeper view of two pointers

Two pointers are often presented as a technique: left = 0; right = n − 1; while left < right: … But that is only the visible part. The actual technique:

Maintain two useful boundaries so that information from one side lets you safely eliminate or finalize part of the search space.

The pointers are just the mechanism for moving through that reduced search space.

4. The common principle behind both problems

Both algorithms follow the same high-level reasoning:

StepContainer With Most WaterTrapping Rain Water
1. Start with a large search spaceall possible pairsall positions whose water contribution needs to be determined
2. Identify the limiting factorthe shorter wallthe smaller boundary maximum
3. Ask what information it gives uskeeping the shorter wall while reducing width cannot improve the areathe smaller boundary already determines the water level
4. Safely eliminate workdiscard the shorter wallfinalize the side with the smaller maximum
5. RepeatEventually nothing remains to examine. That’s where the linear solution comes from.

The trade-off is the important part

Good algorithms are full of trade-offs. In Container With Most Water we move a pointer, lose width, and potentially gain height. We accept the loss of width because keeping the shorter wall has no upside. In Trapping Rain Water we process one side without knowing everything about the other, but we know enough to make this answer certain. We accept incomplete information because complete information isn’t necessary. These are two different forms of the same deeper idea:

Give up something only when you can prove that what you’re giving up cannot improve the answer.

Why these problems are more valuable than memorizing a pattern

Suppose tomorrow you meet a completely different problem. It doesn’t mention water, it doesn’t have an array like this, and it doesn’t look like a standard two-pointer question. If you have memorized “Container → move shorter pointer” you probably won’t recognize the technique. But if you have learned the reasoning, “Can I start with an extreme state, and then prove that one side of the search space can never produce a better answer?” you may recognize the opportunity. That is a transferable skill.

5. A useful checklist when encountering a new problem

Instead of asking “Is this a two-pointer problem?” ask:

  1. What am I trying to calculate? A pair? A range? A contribution at every position? An optimum?
  2. What determines that answer? Look for the actual formula or constraint.
  3. What is the bottleneck? Is there a minimum, maximum, boundary, capacity, or limiting resource?
  4. If I move one boundary, what do I lose? Usually something like width, range, possibilities or information.
  5. What could I potentially gain? Maybe greater height, a better value, or more information.
  6. Can I prove that one direction cannot help? This is the critical question. If yes, we can eliminate part of the search space.
  7. Can I make a decision without knowing everything? If yes, we may be able to process one side immediately.

6. The two intuitions worth remembering

For Container With Most Water:

Start with maximum width. The shorter wall is the bottleneck. Moving the taller wall only reduces width while leaving the bottleneck unchanged, so it can never help. Move the shorter wall because replacing it is the only way to potentially gain enough height to compensate for the lost width.

For Trapping Rain Water:

Water is controlled by the smaller of the best boundaries on the two sides. If one side’s maximum is already smaller than the other, that side’s water level is already determined. We can process it without knowing the exact boundary on the other side.

And the broader lesson:

Two pointers are not about having two indices. They are about finding a way to use two boundaries to prove that most of the search space does not need to be explored.

That is the intuition we want to carry into the next problems.
