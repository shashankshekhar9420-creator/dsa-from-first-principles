Two Pointers: Understanding the Idea Before the Pattern

When learning DSA, we are often taught techniques as patterns: “If you see a sorted array, try two pointers.” Or: “Use left and right.” That is useful for solving problems quickly, but it doesn’t answer the more important question:

Why do two pointers exist in the first place?

What problem are they solving? And why do we sometimes use two pointers even when the array isn’t sorted? Let’s forget the technique for a moment and build the idea from scratch. Code blocks can be hidden with the button at the top, or one at a time.

Start with a problem, not a technique

Take the array [2, 7, 11, 15]. We want two elements whose sum is 9. A natural first thought: “I’ll try every possible pair.”

def two_sum(arr, target):
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] + arr[j] == target:
                return i, j

This works. But notice what we’re doing: examining pairs one by one. How many pairs are there? Each cell below is one pair (i, j) with i < j. Change the array size:

Deriving the count

The unit step is checking one pair. Element 0 can pair with the n−1 elements after it. Element 1 with n−2. And so on, down to the second-to-last element, which has just 1 partner:

(n−1) + (n−2) + … + 1 = n(n−1)/2

To add those up, pair the first term with the last: (n−1) + 1 = n, then (n−2) + 2 = n, and so on. There are (n−1)/2 such pairs of terms, each worth n, giving n(n−1)/2. That is roughly n²/2, so the work grows quadratically: O(n²). Ten times more elements means about a hundred times more pairs.

The important question is not simply “Can we make this faster?” It is:

Are we doing work that we could have avoided?

That question leads us toward two pointers.

The array contains information we’re not using

Look again at [2, 7, 11, 15]. It is sorted, and that ordering tells us something. Take the two ends:

2 + 15 = 17, but our target is 9. We’re too large.

Now the important question: which pointer should move? We need a smaller sum. Because the array is sorted, moving the right pointer left gives a smaller number: 2 + 11 = 13, still too large. Move again: 2 + 7 = 9. Found it. But the interesting part isn’t that we found 9. It’s what we didn’t have to check.

Why is moving safe? Proof by elimination

We started with 2 + 15 = 17, which is more than 9. Consider every pair containing 15:

Pair with 15Sumvs target 9
2 + 1517too big (what we checked)
7 + 1522too big, because 7 > 2
11 + 1526too big, because 11 > 2

Since 2 < 7 < 11, if 2 + 15 > target then 7 + 15 and 11 + 15 are bigger still. So 15 cannot be part of any valid pair. We didn’t test those pairs. We proved them impossible and eliminated them all with one comparison.

Two pointers allow us to use the structure of a problem to eliminate large parts of the search space instead of checking every possibility individually.

Pointers are the boundaries of a shrinking search space

This is a better mental model than “two pointers means left and right.” Initially, the answer could be anywhere. The pointers define the boundaries. We inspect the situation at those boundaries, learn something, eliminate a region, shrink the search space, and repeat. The pointers aren’t magical. They are moving boundaries of a shrinking search space.

Here is that, drawn properly. The grid shows every pair and its sum. Watch which cells get eliminated by each comparison: yellow is the pair being compared, blue is what this comparison just ruled out, grey is ruled out earlier, green is the answer.

Notice how a single comparison wipes out a whole column (when the sum is too big, that right element is useless) or a whole row (when the sum is too small, that left element is useless). We never visit most of the grid.

Why do we need two pointers?

Because the problem involves two positions simultaneously. We’re asking “which two elements together satisfy some condition?” So we track two candidates, one for each side of the pair, and move one of them depending on what we’ve learned.

Python code (click to hide or show)
def two_sum_sorted(arr, target):
    left = 0
    right = len(arr) - 1

    while left < right:
        total = arr[left] + arr[right]

        if total == target:
            return left, right
        if total < target:
            left += 1       # arr[left] is too small for any partner
        else:
            right -= 1      # arr[right] is too big for any partner

    return None             # pointers met: no valid pair

This code is added to the script for clarity. It only works because the array is sorted.

How much did we improve?

Brute force can check up to n(n−1)/2 pairs. How many comparisons can two pointers make? Look at the gap between the pointers, right − left. It starts at n − 1. Every comparison either finds the answer, or moves one pointer inward, which shrinks the gap by exactly 1. The loop stops when the gap reaches 0. So:

comparisons ≤ n − 1, so T(n) = O(n)

From quadratic to linear. And no extra memory is needed: just two index variables, O(1) space. See what that means as the array grows (bars use a log scale, otherwise the second one would be invisible):

Be honest about the best case: for the script’s example with target 9, brute force happens to hit the answer on its very first pair, 2 + 7. The improvement is about the worst case. In the second preset above (target 26), brute force checks all 6 pairs and the pointers need only 3 comparisons.

The price: the array must be sorted. If it isn’t, sorting first costs about O(n log n) and moves elements, so we’d lose their original positions unless we track them. The improvement exists because we used a property of the problem.

A completely different problem: Remove Element

Consider LeetCode 27: nums = [3, 2, 2, 3], val = 3. We want to remove every 3. Conceptually the answer is [2, 2], but we don’t physically shrink the array. Instead, the first k positions must hold the elements we keep. So our real problem is:

How do we take all the elements we want to keep and pack them toward the beginning of the array?

The array isn’t sorted. There is no pair sum. Yet two pointers are still useful. Why?

There are two different jobs

Imagine scanning left to right. We must answer two different questions: what element am I currently looking at? and where should the next valid element go? Those are two different positions, so we naturally get two pointers: read explores, write constructs the answer. The reason isn’t sorting, or pair sums, or a special rule. The problem itself has two different positions that matter.

Choose an input and step through. R is read, W is write:

  • If read finds an unwanted element: read moves, write stays.
  • If read finds a wanted one: copy it to write, then both move.

So the pointers move at different speeds, and both go left to right. That is still two pointers. They don’t have to move toward each other.

read is at index 3. write is at index 0. “Where am I looking?” and “where does the next useful element belong?” are different facts. One pointer could hold only one of them.

The gap has meaning, and the invariant explains everything

After scanning some elements, there is a gap between write and read. It represents elements we’ve already examined and decided don’t belong in the answer. The array splits into three zones:

correctly built: elements we keep
already processed; free to overwrite
not processed yet
write ↑
read ↑

Everything before write is already a correctly packed collection of elements that should be kept.

This invariant also shows why the algorithm is safe. write can never get ahead of read, because it only advances after read has passed an element. So the cell at write has always been read already, and overwriting it never destroys an unread element.

The code becomes almost inevitable

Python code (click to hide or show)
def remove_element(nums, val):
    write = 0

    for read in range(len(nums)):
        if nums[read] != val:
            nums[write] = nums[read]
            write += 1

    return write

There isn’t a “two-pointer trick” hiding here. The code simply expresses two responsibilities: read says “let me inspect the next element,” and write says “let me put the next useful element here.”

How much did this improve things?

A tempting first approach: whenever we find val, delete it the way an array deletes, by shifting everything after it one place left. We derived that cost earlier: deleting at index i moves n − i − 1 elements. If every element equals val, we delete from the front each time, and the moves add up to:

(n−1) + (n−2) + … + 0 = n(n−1)/2, so O(n²)

Two pointers: read visits each element exactly once (n reads) and write copies at most once per element (≤ n copies). Total at most 2n, so O(n). Compare the two on different inputs. The unit step is one read or one element moved or copied:

The shifting approach is added to the script for comparison. Note that when nothing needs removing, the shifting approach is not worse: two pointers still do their n reads and n copies. The win is on the bad inputs.

Why carrying state forward makes things linear

This is the most important algorithmic lesson under the technique. Imagine processing an array without remembering anything. You repeatedly ask “where is the next useful element?” and start another search, then another. You redo work you’ve already done. Two pointers let us carry state forward: “I’ve already processed everything before this position. I don’t need to reconsider it.”

That is exactly why the totals are linear. Each pointer only ever moves in one direction and never goes back, so its total travel is bounded by n, and each move costs a constant number of steps:

So two pointers does not fundamentally mean “use left and right,” or “the array must be sorted,” or “move two indices toward each other.” The deeper idea:

Maintain two positions in a sequence because those two positions allow you to carry useful information forward while processing the array.

Don’t throw away information

A brute-force approach says “I don’t know, so I’ll try everything.” An optimized approach asks “What do I already know?” and then “Can I use that knowledge to avoid work?” In sorted Two Sum, the ordering lets us eliminate possibilities. In Remove Element, the processed prefix lets us avoid repeatedly searching for where useful elements belong. Different techniques, same philosophy: don’t throw away information you’ve already gained.

Recognizing two-pointer problems

Instead of memorizing “sorted array → two pointers,” ask:

  1. Am I maintaining two meaningful positions in the array? Candidate + candidate, reader + writer, start + end.
  2. Do these positions have different responsibilities? If yes, that’s a strong signal.
  3. Can the pointers move without repeatedly reconsidering what they’ve already passed? If yes, even stronger.
  4. Does every movement eliminate work or preserve information about what has been processed? That’s where the efficiency usually comes from.

The mental model to keep

Don’t memorize “two pointers = left and right.” Remember:

Two pointers = two positions carrying two pieces of useful state while we move through a sequence.

Then ask: why do I need those two pieces of state?

ProblemThe two pieces of state
Two SumWhere is my lower candidate? Where is my higher candidate?
Remove ElementWhat am I currently examining? Where should the next useful element go?
Sliding windowWhere does my region begin? Where does it end?
Slow / fastHow far has one notion of progress gone? How far has another gone?

The core idea

Two pointers are useful when keeping track of two moving positions lets us preserve information, eliminate unnecessary work, or maintain the structure of the answer as we move through an array.

The pointers themselves aren’t the clever part. Figuring out what each pointer should mean is the clever part. That is why learning two pointers as a template is less useful than learning to ask: “What two positions do I actually need to keep track of, and why?”
