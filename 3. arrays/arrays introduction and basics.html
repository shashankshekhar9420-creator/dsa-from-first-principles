Arrays from First Principles

When learning data structures, it is tempting to memorize facts like these:

  • Array access is O(1)
  • Searching is O(n)
  • Insertion is O(n)
  • Dynamic arrays have amortized O(1) append
  • Binary search is O(log n)

These facts are useful. But memorizing them doesn’t tell us why they are true. A better way to learn arrays is to start with a simple problem:

We have a lot of related data. How should we organize it so that a computer can work with it efficiently?

Once we start solving that problem, arrays and their properties begin to emerge naturally. Every piece of code below can be hidden with the button at the top, or one block at a time.

We have many values

Suppose we want to store the marks of five students: 85, 72, 91, 64, 78. The simplest approach is separate variables.

Python code (click to hide or show)
mark1 = 85
mark2 = 72
mark3 = 91
mark4 = 64
mark5 = 78

This works. But something is wrong. These five values are related: they are the same kind of information. Yet our program has no single thing representing “these are all the marks.” With 10,000 students we would have mark1, mark2, … mark10000. The computer can store them all. The problem is that we have no convenient way to treat them as one collection.

The first important idea: we want to group related values into a single structure.

Finding one value: positions and indices

Now we have marks = [85, 72, 91, 64, 78] and want the third student’s mark. How do we identify it? We could give every value its own name (first, second, third…), but that doesn’t scale. Instead, notice something natural about a collection: every element has a position. Pick a position:

Python code (click to hide or show)
marks = [85, 72, 91, 64, 78]
print(marks[2])   # 91

This is the idea of an index. Instead of naming every element, we identify it by its position. Our collection now has two important properties: all related values belong to one structure, and each value can be identified by an index. That is already very close to an array.

What an array looks like in memory

Now look underneath the abstraction. At the conceptual level, arr = [10, 20, 30, 40, 50] is a row of boxes with indices. But the computer’s memory isn’t really a row of boxes called “index 0”, “index 1”. Memory is a large collection of addresses. The important thing about a traditional array is that its elements are stored in contiguous memory: consecutive locations, one right after another. If each integer takes 4 bytes:

This physical organization is responsible for many of the properties we associate with arrays.

How do we derive a time complexity?

Above we listed facts like O(1) and O(n). Where do they come from? Every one of them comes from the same three steps, which we met in the complexity article:

1. Pick a unit step that takes constant time
↓
2. Count how many steps are needed, as a function of n: T(n)
↓
3. Keep the dominant growth: drop constants and smaller terms

The unit step is one small thing the computer does that doesn’t get slower as the array gets bigger. Different machines take different amounts of time per step, but each step is still a constant. We also have to say which case we are counting: best, average or worst. Here is the unit step for each operation we’ll derive:

OperationUnit step we count
Access arr[i]one address calculation and one memory read
Linear searchone comparison
Insert / deletemoving one element by one place
Resizecopying one element
Binary searchone comparison
Traversing a 2D arrayvisiting one element

For instance, if counting gave T(n) = 3n + 7 steps, step 3 reduces it to Θ(n). We’ll now do the counting for each operation, right where it appears.

Why is array access O(1)?

Consider arr[3], the fourth element. A beginner might imagine the computer starts at the beginning and walks 10 → 20 → 30 → 40. That isn’t necessary. Because the elements are contiguous and each has the same size, the address can be calculated:

address = starting_address + index × element_size

Choose an index and watch the calculation (starting address 1000, element size 4 bytes):

Python code (click to hide or show)
arr = [10, 20, 30, 40, 50]
print(arr[3])   # 40

We jump straight to the location of 40 without walking past the earlier elements. The flow is: index → calculate address → jump directly to element. That is why arr[i] is O(1). But “arrays are O(1)” is incomplete. Arrays are good at indexed access because of their memory organization:

Contiguous storage + fixed-size elements → predictable address → direct access. O(1) is the consequence.

Deriving it: count the steps

To evaluate arr[i] the computer does three things: multiply the index by the element size, add the starting address, and read that location. That is 3 unit steps. Notice that none of them depends on how many elements the array has:

So T(n) = 3, a constant that doesn’t grow with n. A function that doesn’t grow is O(1). (This assumes that reading one memory address counts as one step.)

Knowing the index vs knowing the value

Now ask a different question: where is 40? This differs from arr[3]. With arr[3] we already know the location. Here we only know the value, and the array doesn’t tell us where it is. In an unsorted array like [10, 50, 20, 90, 40, 30], we have no clue where 40 might be. It could be anywhere. So we inspect the elements one by one: linear search. Choose a target and step through:

Python code (click to hide or show)
def linear_search(arr, target):
    for i in range(len(arr)):
        if arr[i] == target:
            return i

    return -1

arr = [10, 50, 20, 90, 40, 30]
print(linear_search(arr, 40))    # 4
print(linear_search(arr, 100))   # -1  (not found)

Why is linear search O(n)?

The important question isn’t “why does the formula say O(n)?” Ask: how many elements might I have to inspect? Searching for the first element takes 1 check (best case, O(1)). Searching for the last takes all of them. And searching for a value that isn’t there (like 100) still inspects everything, because we must prove it isn’t anywhere. So the average and worst cases are both O(n).

An unsorted array gives us no information that lets us safely eliminate large parts of the search space. Each comparison mostly eliminates one possibility.

Deriving it: count the comparisons

The unit step is one comparison. If the target sits at position p (counting from 1), the loop makes exactly p comparisons before stopping. If the target isn’t there, it makes n. Drag the slider to see the cost for every possible target:

  • Best case: target is first, T(n) = 1, so O(1).
  • Worst case: target is last or missing, T(n) = n, so O(n).
  • Average case: if the target is equally likely to be at any of the n positions, the average is (1 + 2 + … + n) / n. To add those up, pair the first with the last: 1 + n, then 2 + (n−1), and so on. Every pair sums to n + 1, and there are n/2 pairs, so the sum is n(n+1)/2. Dividing by n gives (n+1)/2.

That average, (n+1)/2 = n/2 + ½, loses its constant ½ and its smaller term in step 3, leaving Θ(n). Real loops also do a little bookkeeping per iteration, which only multiplies the count by a constant. Same conclusion.

Access arr[3]
“I know the position. Give me what’s there.” The array calculates the location. O(1)
Search linear_search(arr, 40)
“I know the value, not the position.” We may inspect every element. O(n)

Knowing the index and finding the index are completely different problems.

Keeping the row compact: insertion and deletion

The same contiguity that gives fast access creates a cost elsewhere. To insert 25 between 20 and 30, we want 10 20 25 30 40 50. But the array must stay contiguous, and there is no room between 20 and 30. So elements must move. Deletion is the same problem in reverse: leaving a hole like 10 20 __ 40 50 would break the compact layout, so elements slide left. Try each operation:

  • Insert in the middle or at the beginning: potentially many elements shift → O(n). At the beginning, almost the whole array moves.
  • Delete from the middle or beginning: likewise O(n).
  • Delete from the end: nothing else moves → O(1) (assuming no shrinking work).
  • Append at the end: no shifting, if there is spare room. That condition is the next problem.

Deriving it: count the moves

The unit step is moving one element by one place. In an array of n = 10 elements, choose where to insert or delete and count the elements that must move:

Inserting at index k pushes every element from index k onward one place right. Those are the elements at indices k, k+1, …, n−1, which is n − k of them. Deleting at index k pulls the elements after it left: n − k − 1 of them.

  • Beginning (k = 0): n moves. O(n).
  • Middle (k ≈ n/2): about n/2 moves. Still O(n), because halving is just a constant factor.
  • End (k = n): 0 moves.

Averaged over all n + 1 insertion positions, the moves are n/2, again Θ(n). So the worst case, and the typical case, are O(n). Only the end escapes, and only because it needs no shifting.

What if we run out of space?

Suppose we allocated room for five elements and want to add 60. Ideally it goes right after 50. But what if the memory immediately after the array is already used by something else? We can’t put 60 somewhere far away, because then the elements are no longer contiguous, which would break the organization that gave us direct indexed access.

Arrays need contiguous memory, but a contiguous block has a fixed amount of space.

Static arrays

One solution is to decide the size beforehand: “I need space for 100 elements.” Simple. But if we need 101, there’s no room. If we only need 5, we’ve reserved a lot of unused space. A static array has a capacity that is fixed once allocated: predictable, but not flexible.

Dynamic arrays

What we really want is to just write arr.append(10) without promising a maximum size. The idea: allocate more space than we currently need. With size = 3 and capacity = 5:

Python code (click to hide or show)
arr = []

arr.append(30)

But eventually the extra space runs out. Then the dynamic array allocates a larger contiguous block somewhere else (for example, double the capacity), copies every old element across, and adds the new one. That particular append is expensive. So dynamic-array append is not literally O(1) every single time.

Then why “amortized O(1)”?

Resizing doesn’t happen every time. Capacities grow like 1, 2, 4, 8, 16, 32, 64… Most appends just use space already allocated; occasionally we resize and copy 1, 2, 4, 8, 16… elements. Press Append repeatedly and watch the cost of each one (the bar chart):

Over n appends, the total copying is proportional to n, so the total work is O(n), and the average per append is O(n) / n = O(1). This is what amortized O(1) means. It does not mean every append is constant time. It means that over a long sequence of operations, the occasional expensive resize is cheap enough once its cost is spread across all the ordinary appends.

Deriving it: add up the copies

Count two kinds of unit steps over n appends. First, placing each new element: n steps in total. Second, copying during resizes. With doubling, a resize happens when the size reaches 1, 2, 4, 8, … and copies that many elements. If the last resize happened at size 2j (which is less than n), the copies add up to:

1 + 2 + 4 + … + 2j = 2j+1 − 1

An easy way to see it: 1 + 2 + 4 + 8 = 15, which is one less than the next power, 16. Each batch of copies is about as large as all the earlier batches combined. Since 2j < n, we get 2j+1 < 2n, so the copies total less than 2n. Total work is below n + 2n = 3n, and per append it is below 3, a constant. Check the arithmetic:

So the average cost per append never grows with n: O(1) amortized. This also matches the bar chart above, where the average stayed under 3. The same argument works for any constant growth factor above 1, not only doubling.

If we can directly calculate the location and don’t need to move elements, the operation can be O(1). If many elements have to move or be inspected, the operation becomes O(n).

What if our data has two dimensions?

So far we’ve worked with a single row. But many problems have rows and columns: a matrix, a chessboard, pixels in an image, student marks across subjects, a grid in a game. This is a 2D array, accessed with two indices: matrix[row][column].

Python code (click to hide or show)
matrix = [
    [1, 2, 3],
    [4, 5, 6],
    [7, 8, 9]
]

print(matrix[1][2])   # 6

Memory is still one-dimensional

We visualize a grid, but physical memory is a linear sequence of addresses. There is no magical 2D memory. So the computer must map (row, column) to a position in a 1D block. There are two common ways. In row-major order, we store an entire row before the next one: 1 2 3 4 5 6 7 8 9. In column-major order, we finish a column first: 1 4 7 2 5 8 3 6 9.

Why does traversal order matter?

Choose how the matrix is stored and how we walk through it, then move the slider. The strip below shows memory:

Both traversals visit the same number of elements. Counting: each element is visited once, and each visit costs a constant number of steps, so T = c × rows × columns, which is O(rows × columns). (For a square n × n grid that is n².) But with a mismatched order we jump around memory instead of moving through neighboring locations. Modern computers fetch memory in chunks and benefit when nearby data is used together. This is cache locality, which matters for performance beyond Big-O. The intuition:

A 2D structure is an abstraction. Physical memory is still linear, so the way we map the abstraction onto memory matters.

Can we search faster?

Linear search gives each comparison very little information. But suppose the array is sorted: [10, 20, 30, 40, 50, 60, 70, 80, 90]. Now we have something new: order. And order gives us information.

The key insight

Search for 70. Instead of starting from the beginning, look at the middle: 50. We compare, and find 70 > 50. What does sortedness tell us? Everything left of 50 (10, 20, 30, 40) is smaller than 50, and our target is 70, so none of those can be 70. In fact everything up to and including 50 can be thrown away.

Linear vs binary

With linear search the search space behaves like n → n−1 → n−2 → … With binary search it behaves like n → n/2 → n/4 → n/8 → … Slide to see how many possibilities remain after each comparison (starting with 16):

The real insight is not the logarithm. It is: one comparison allows us to eliminate half the remaining possibilities.

Deriving the logarithm

The unit step is one comparison. Let’s count how many we can be forced to make. After each comparison, at most half of the remaining possibilities are left. So after k comparisons, at most n / 2k remain. In the worst case we keep going until a single possibility is left. Set that equal to 1 and solve for k:

n / 2k = 1  ⇒  2k = n  ⇒  k = log₂ n

That is all a logarithm is here: log₂ n is how many times you can halve n before reaching 1. One more comparison checks that last candidate, so the worst case is about log₂ n + 1 comparisons. Exactly, it is ⌊log₂ n⌋ + 1. Pick a size and count the halvings:

Dropping the constant +1 leaves O(log n). The base of the logarithm doesn’t matter either: log₂ n and log₁₀ n differ only by a constant factor, which step 3 discards. Compare this with linear search, where the count was n, not log n: halving is what turned a million checks into about twenty.

Deriving binary search

We need to track the region where the target could still exist. Initially left = 0 and right = len(arr) - 1. Everything between them is still possible. Calculate mid = (left + right) // 2. If arr[mid] == target, found. If arr[mid] < target, the target must be to the right: left = mid + 1. If arr[mid] > target, it must be to the left: right = mid - 1. The invariant:

Everything outside [left, right] has already been proven impossible.

Python code (click to hide or show)
def binary_search(arr, target):
    left = 0
    right = len(arr) - 1

    while left <= right:
        mid = (left + right) // 2

        if arr[mid] == target:
            return mid

        if arr[mid] < target:
            left = mid + 1
        else:
            right = mid - 1

    return -1

arr = [10, 20, 30, 40, 50, 60, 70, 80, 90]
print(binary_search(arr, 70))   # 6

Trace it, including when the target isn’t there

Pick a search. The first finds 70 in two rounds. The second looks for 35, which isn’t in the array. L, R and M mark left, right and mid.

When the target is missing, the possibilities run out: left > right, the search space is empty, and we return -1. That is why the loop is while left <= right.

Why does binary search require sorted data?

This is the most important limitation. In the unsorted [73, 12, 91, 5, 44, 28, 67], suppose we inspect 5 while searching for 44. We know 44 > 5, but can we throw away everything before 5? No: a 44 could be there. The comparison tells us nothing about the rest. Order is what lets one comparison say something about an entire region.

Binary search requires an ordered search space where a comparison lets us eliminate a portion of the possibilities.

Why do we need different data structures?

Perhaps the biggest lesson from arrays: an array is not “good” or “bad.” It makes certain operations cheap because of the choice it makes, contiguous storage and indexed access. Fast: indexed access, O(1). Potentially expensive: middle insertion, middle deletion, searching. Another data structure makes a different trade-off. A hash table organizes information so finding something by its key can be very fast. A tree organizes information around ordering or hierarchy. A heap organizes it around priority. Different structures exist because different problems require different kinds of efficiency.

The complete story of arrays

  1. Many related values → we want one collection.
  2. How do we identify one value? → indices.
  3. How can the computer reach an indexed element efficiently? → store elements contiguously, so address = base + index × element size, so access is O(1).
  4. Where is a value, if we only know the value? Unsorted arrays give no shortcut → linear search, O(n).
  5. Insert or delete in the middle? Contiguity forces elements to shift → O(n).
  6. Run out of contiguous space? → dynamic arrays resize and copy. Resizing is rare → append is amortized O(1).
  7. Rows and columns? → 2D arrays, mapped onto 1D memory by row-major or column-major, and traversal order can matter.
  8. Sorted data? One comparison eliminates half the possibilities → binary search, O(log n).

If there is only one thing to remember about arrays, it shouldn’t be a complexity table. It should be this:

The real lesson is bigger than arrays:

Don’t memorize the behavior of a data structure. Understand the physical and logical choices that created it.

Once you know why the data is organized in a particular way, the performance characteristics stop looking like arbitrary facts. They become consequences. And that is the real purpose of studying data structures from first principles.
