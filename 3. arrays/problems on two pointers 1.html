Two Pointers, From First Principles

Two pointers is often taught as a pattern: “Keep one pointer at the beginning, another at the end, and move them according to some condition.” That description is technically correct, but it misses the important part. It doesn’t explain why two pointers work. And it doesn’t explain how you would recognize a two-pointer problem if nobody told you the pattern beforehand.

The real idea is much simpler:

Two pointers are useful when we can use two positions to eliminate large parts of the search space without ever needing to reconsider them.

The pointers are not the clever part. The clever part is the reasoning that allows us to throw possibilities away. Let’s build that reasoning from scratch, on seven problems. 1. Why do we need two pointers?

Take the array [1, 2, 3, 4, 6]. We want two numbers whose sum is 6. The obvious approach is to try pairs: 1 + 2, 1 + 3, 1 + 4, 1 + 6, 2 + 3, and so on.

Python code (click to hide or show)
def pair_brute_force(arr, target):
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] + arr[j] == target:
                return [i, j]
    return [-1, -1]

This works. But notice something frustrating. Every check teaches us something, and brute force immediately forgets it. Compare the two ends of the array:

1 + 6 = 7, but our target is 6. Too large.

The array is sorted, and 1 is the smallest possible partner for 6. If even the smallest partner makes the sum too large, then every other partner makes it larger still:

So 6 cannot be part of any valid pair. One comparison ruled out four pairs, and we never tested three of them. That is the beginning of the two-pointer idea. The question that starts it is not “can we make this faster?” but:

Are we doing work that we could have avoided?

2. Pair With Target Sum

Instead of starting with arbitrary pairs, ask: which two candidates give us the most information? The smallest and the largest. They are the two ends of the sorted array, so we put one pointer on each. Their sum is too large or too small, and that tells us which pointer to move.

Try it: which pointer should move?

Before reading the explanation, make the decision yourself. The array is sorted. Pick a move; you’ll be told why it is, or isn’t, safe.

Why exactly are the movements valid?

This is the part that should never be skipped. If arr[left] + arr[right] < target, we need a larger sum. Keeping left and moving right left would only make the sum smaller, and right is already the biggest partner left has left. So arr[left] is too small for every remaining partner, and the only useful move is left++.

Symmetrically, if the sum is > target, even the smallest remaining partner for arr[right] overshoots, so right--. We aren’t following a memorized rule. The rule follows directly from the ordering of the data.

Watch the search space shrink

The grid shows every pair and its sum. Yellow is the pair being compared, blue is what this comparison just ruled out, grey was ruled out earlier, green is the answer. A single comparison wipes out a whole row or a whole column.

Python code (click to hide or show)
def pair_with_target_sum(arr, target):
    left = 0
    right = len(arr) - 1

    while left < right:
        total = arr[left] + arr[right]

        if total == target:
            return [left, right]

        if total < target:
            left += 1       # arr[left] is too small for any partner
        else:
            right -= 1      # arr[right] is too big for any partner

    return [-1, -1]

For [1, 2, 3, 4, 6] and target 6 this returns [1, 3], because 2 + 4 = 6.

Why not brute force?

Brute force is perfectly reasonable for a small input. But with n elements there are n(n−1)/2 pairs, so the work is O(n²). The pointers start n − 1 apart, and every comparison either finishes or shrinks that gap by exactly 1, so they make at most n − 1 comparisons: O(n), with O(1) extra space.

Two pointers gets its efficiency by exploiting structure.

If the array isn’t sorted, we cannot automatically use this reasoning. We could sort it first, but sorting costs O(n log n), which then dominates, and it destroys the original indices unless we keep track of them.

3. But two pointers don’t require a sorted array

This is an important misconception, and the next problem shows why. Take [0, 1, 0, 1, 1, 0, 0]. We want all 0s on the left and all 1s on the right: [0, 0, 0, 0, 1, 1, 1]. There is no target sum. There isn’t even a sorted array. So why might two pointers help?

Because we know something else: 0 belongs on the left and 1 belongs on the right. That gives us two boundaries, and the array splits into three regions:

unknown region
correct 1s
left ↑
↑ right

Inspect the two ends. If arr[left] == 0, it is already in the correct region, so move left. If arr[right] == 1, it is already correct, so move right. Eventually we get arr[left] == 1 and arr[right] == 0: both are on the wrong side, so swap them. Green is a finished 0, blue is a finished 1, yellow is being inspected:

Python code (click to hide or show)
def rearrange_zeros_and_ones(arr):
    left = 0
    right = len(arr) - 1

    while left < right:
        if arr[left] == 0:
            left += 1
        elif arr[right] == 1:
            right -= 1
        else:
            arr[left], arr[right] = arr[right], arr[left]
            left += 1
            right -= 1

    return arr

Why not just sort?

For this particular problem, arr.sort() is probably the simplest practical solution, and that is an important trade-off to admit. The two-pointer version is interesting because it shows a more general idea: we don’t need a general-purpose sort when the problem gives us much simpler structure. There are only two possible values, and we know exactly where each belongs, so we can partition directly, in place, in one pass. The price is slightly trickier logic than a library call.

The theoretically interesting solution isn’t always the best production solution.

We’re learning two pointers to understand the reasoning, not because every problem should avoid sorting.

4. Remove Duplicates

Now take [2, 3, 3, 3, 6, 9, 9]. We want [2, 3, 6, 9]. The array is sorted, so duplicates sit next to each other, and the problem isn’t really “find every duplicate.” It is: keep the first occurrence of each value and ignore the rest.

But suppose we must modify the array in place. Now there are two different jobs: one position needs to read the array, and another needs to say “this is where the next unique value should be written.” Two jobs, so two pointers. They both travel left to right, at different speeds.

The key invariant

At every point, arr[:write] holds the unique values discovered so far. read explores; write maintains the useful portion. When read meets a value different from the last unique value, we copy it to write.

Python code (click to hide or show)
def remove_duplicates(arr):
    if not arr:
        return 0

    write = 1

    for read in range(1, len(arr)):
        if arr[read] != arr[write - 1]:
            arr[write] = arr[read]
            write += 1

    return write

arr = [2, 3, 3, 3, 6, 9, 9]
length = remove_duplicates(arr)
print(arr[:length])   # [2, 3, 6, 9]

Why not use a set?

list(set(arr)) is a natural Python answer, but it changes the problem. It uses extra memory, and it may not preserve ordering. Building a second list keeps the order and is easier to understand, but it also costs O(n) extra space.

The technique is buying us something: reuse the existing array and compress the useful information into its front.

5. Squaring a Sorted Array

Take [-4, -1, 0, 3, 10]. We want the squares in sorted order: [0, 1, 9, 16, 100]. The obvious approach is sorted(x * x for x in arr). It is simple, so why look further? Because the input has structure that lets us skip the second sort.

What squaring breaks, and what survives

The input is sorted: -4 < -1 < 0 < 3 < 10. After squaring we get 16, 1, 0, 9, 100, and the order is destroyed, because negatives flip: -4 < -1 but (-4)² > (-1)². Something survives, though. Look at the shape of the squares:

The squares form a valley. The largest one is always at one of the two ends.

The largest absolute value must be at one of the two ends, so the largest remaining square can always be found there. That is exactly the kind of structure two pointers can exploit.

Build the answer from the back

If we’re finding the largest remaining square, it belongs at the end of the result. So we also get a write position that moves backward. Compare the two absolute values, put the bigger square at write, and move whichever pointer produced it:

Python code (click to hide or show)
def sorted_squares(arr):
    result = [0] * len(arr)

    left = 0
    right = len(arr) - 1

    for write in range(len(arr) - 1, -1, -1):
        if abs(arr[left]) > abs(arr[right]):
            result[write] = arr[left] ** 2
            left += 1
        else:
            result[write] = arr[right] ** 2
            right -= 1

    return result

Why not just square and sort?

Again, the trade-off matters. sorted(x * x for x in arr) is very readable. The two-pointer version uses the existing order to avoid sorting the squares again, so we exchange more reasoning and code for better asymptotic performance: O(n) instead of O(n log n). The lesson isn’t “never use sorting.” It is:

Before doing another expensive operation, ask whether the input’s existing structure already gives you the information you need.

6. Triplet Sum to Zero

Now things become more interesting. Take [-3, -1, 0, 1, 2] and find all triplets that sum to zero. The naive approach chooses i, j and k and checks every combination: three dimensions of search. Can we reduce the problem?

Yes. Fix one number. Suppose we choose -3. Then -3 + x + y = 0, so x + y = 3. We have turned a three-number problem into a two-number problem, and we already know how to solve that on sorted data.

So: sort first, fix i, put left = i + 1 and right = n − 1, and run the pair-sum logic. Blue is the fixed i, yellow is the pair under inspection, grey is eliminated for this i:

Handling duplicates

Take [-2, 0, 0, 2, 2]. There are several ways to pick the same values, but we don’t want [-2, 0, 2] reported three times. Sorting makes duplicates adjacent. If arr[i] == arr[i − 1], we skip this i. After finding a valid triplet, we similarly skip repeated values at left and right. Try the third preset above to watch it happen.

Python code (click to hide or show)
def three_sum(arr):
    arr.sort()
    result = []

    for i in range(len(arr) - 2):
        if i > 0 and arr[i] == arr[i - 1]:
            continue

        left = i + 1
        right = len(arr) - 1

        while left < right:
            total = arr[i] + arr[left] + arr[right]

            if total == 0:
                result.append([arr[i], arr[left], arr[right]])

                left += 1
                right -= 1

                while left < right and arr[left] == arr[left - 1]:
                    left += 1

                while left < right and arr[right] == arr[right + 1]:
                    right -= 1

            elif total < 0:
                left += 1
            else:
                right -= 1

    return result

How much did the reduction buy us?

Brute force examines n(n−1)(n−2)/6 triplets: O(n³). For each fixed i the pointers make at most n − i − 2 comparisons, and adding those up over every i gives (n−1)(n−2)/2: O(n²). (Sorting adds only O(n log n), which is dominated.)

Why not use a hash set?

That is another legitimate approach: for every fixed i, look up the needed complement in a hash set. It also reaches O(n²). So why use two pointers? Because sorting gives us more structure: constant extra space for the search itself, directional reasoning, and an easy way to avoid duplicate triplets. The cost is that sorting takes time and reorders the array unless we copy it. This isn’t about one universally superior technique. It’s about the constraints, and what structure we want to exploit.

7. Triplet Sum Close to Target

Slightly change the question. Instead of “find a triplet whose sum is exactly the target,” ask for the triplet whose sum is closest to it. For [-2, 0, 1, 2] and target 2, we could try every triplet. But the same reduction works: fix one element, then solve a two-pointer problem on the rest. The difference is that we aren’t looking for sum == target. We measure abs(target − sum) and remember the best we’ve seen.

Why can we still move the pointers intelligently?

If current_sum < target we are below, we want a larger sum, and left++ is the useful move. If it’s above, right--. The objective changed from equality to minimum distance, but the monotonic relationship between pointer movement and the sum did not change. That is why the same structure survives. And if current_sum == target, the distance is zero and nothing can be closer, so we stop immediately (try the third preset).

Python code (click to hide or show)
def triplet_sum_closest(arr, target):
    arr.sort()

    closest = arr[0] + arr[1] + arr[2]

    for i in range(len(arr) - 2):
        left = i + 1
        right = len(arr) - 1

        while left < right:
            total = arr[i] + arr[left] + arr[right]

            if abs(target - total) < abs(target - closest):
                closest = total

            if total < target:
                left += 1
            elif total > target:
                right -= 1
            else:
                return total

    return closest

Why not brute force?

Brute force is perfectly valid and easier to reason about at first, but it checks every triplet. Sort + two pointers is more complicated and needs sorting, yet it exploits the order to dramatically reduce the search. It works because sorting tells us which direction can improve the current candidate.

8. Triplets With Smaller Sum

This problem teaches perhaps the most powerful idea in the whole group. Given [-1, 0, 2, 3] and target 3, count the triplets whose sum is less than 3. The valid ones are [-1, 0, 2] (sum 1) and [-1, 0, 3] (sum 2), so the answer is 2. The naive approach examines every triplet. We can do much better.

Fix i = 0 (the -1), so left = 1 and right = 3. The sum is -1 + 0 + 3 = 2, which is below 3, so this triplet is valid. Now look at the sorted array. If we replace 3 with 2, the sum gets even smaller, so that triplet is valid too. We don’t have to test them one by one: there are right − left valid choices, here 3 − 1 = 2, so we add 2 to the count at once.

In the stepper, the green block is every partner that is proven valid by a single comparison:

Why does this counting trick work?

Suppose arr[i] + arr[left] + arr[right] < target. Because the array is sorted, arr[left] ≤ arr[left+1] ≤ … ≤ arr[right]. Replacing arr[right] with any smaller element cannot make the sum larger, so arr[i] + arr[left] + arr[k] < target for every left < k ≤ right. We have proven an entire group of solutions at once. We’re no longer merely using the array to decide which pointer moves. We’re using it to count many possibilities without inspecting them individually.

And if the sum is ≥ target? Even the largest candidate is too large, so we have no guaranteed group. We need a smaller value: right--.

Python code (click to hide or show)
def triplets_with_smaller_sum(arr, target):
    arr.sort()
    count = 0

    for i in range(len(arr) - 2):
        left = i + 1
        right = len(arr) - 1

        while left < right:
            total = arr[i] + arr[left] + arr[right]

            if total < target:
                count += right - left
                left += 1
            else:
                right -= 1

    return count

Why this problem is more interesting than it looks

Situation A: sum ≥ target
We know only that this combination doesn’t work. So we move right.
Situation B: sum < target
We know much more: this combination works, and every smaller choice on the right works too. We count the whole block, right − left, in one go.

This is a beautiful example of how algorithms become faster not by doing the same work faster, but by proving that a lot of work doesn’t need to be done at all.

9. The common thread across all seven

At first these problems don’t look very related:

Yet the same idea keeps appearing. Suppose we have [left ———— right]. At every step we want to learn something that lets us shrink this region. Sum too large tells us right can never be part of a solution with this left, so right--. Sum too small tells us left is too small, so left++. Current arrangement is correct lets us step past an element. This entire range produces valid triplets lets us count them all at once.

Maintain a small set of boundaries and use information to permanently remove possibilities from consideration.

The invariant is the real algorithm

A pointer movement should never be “it seems like we should move left here.” There should be a reason. A useful question is: what do I now know that I didn’t know before? Pick a problem to see the regions it maintains and the statement that is always true:

These statements are the real algorithm. The code merely expresses them.

10. Why sorting appears so often, and what it costs

A large number of these problems begin with arr.sort(). Why? Because sorting gives us direction.

After sorting, left++ means the value cannot decrease and right-- means it cannot increase. That predictability is what allows us to eliminate possibilities. Sorting isn’t just preparation. It is what makes the pointer movement logically safe.

But it has a cost. If the original array isn’t sorted we have two options. We can not sort and use brute force, hashing or another data structure, preserving the original arrangement. Or we can sort, pay for it, and gain ordering, which gives predictable movement, which eliminates possibilities, which gives a faster search. So an algorithm isn’t simply “faster.” It is faster because I’m willing to exploit this structure and accept its associated cost or constraint.

The trade-off isn’t always “time for space”

Two pointers may involve a sorting cost, mutation of the input, more complicated code than a library call, and stronger constraints: sorted data, only certain values present, an invariant we can maintain, the ability to discard possibilities permanently. Two pointers vs brute force

Brute force has an important place. It is usually the first thing we should be able to imagine, because it shows us the search space. Then we can ask, “Am I repeatedly considering possibilities that I could have ruled out earlier?” That question leads naturally to optimization:

11. Recognizing a two-pointer problem

After working through these problems, we can start spotting the opportunity. Instead of memorizing “sorted array → two pointers,” ask:

  1. Is there useful ordering? Maybe the array is already sorted, or sorting would expose useful structure.
  2. Can I describe two positions as boundaries? left ———— right, or write ← read.
  3. Does moving a pointer have a predictable effect? left++ makes the sum increase, right-- makes it decrease.
  4. Can I permanently eliminate what I leave behind? This is the most important question. If moving a pointer means “this part can never help anymore,” two pointers may be appropriate.

12. The most important lesson

If there is one thing to take away, it shouldn’t be “when you see an array, try two pointers.” It should be:

When solving a problem, look for a way to prove that some possibilities no longer matter.

That’s the beginning of algorithmic thinking. Brute force says “let me check everything.” Optimization asks “do I really need to check everything?” Two pointers gives one particularly elegant answer: “if I know enough about the structure of the data, I can move a boundary and prove that an entire part of the search space is finished.”

The magic isn’t in the two variables called left and right. The magic is in the proof that lets them move forward without looking back.
