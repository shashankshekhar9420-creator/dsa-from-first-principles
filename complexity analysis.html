Complexity Analysis from First Principles

In the previous article we looked at DSA from the ground up, starting with one idea:

Data structures are ways of organizing information so that the operations we care about become easier.

Now the next question. Suppose we have found an algorithm that solves our problem. How do we know whether it is a good algorithm? And more importantly: what happens when the problem becomes much bigger? That is where complexity analysis comes in.

Why do we need complexity analysis?

Back to our college. With 100 students, we find a particular student by checking them one by one. Suppose it takes 50 checks for today’s input. Fine. But the college grows: 10,000 students, then 1,000,000, then perhaps 10,000,000.

The important question is no longer “How many checks did my program make today?” It is:

How does the amount of work grow as the number of students grows?

That is the fundamental question behind complexity analysis.

What are we actually spending?

Every time an algorithm runs, it uses up two basic resources:

ResourceWhat it measuresWhen it runs short
Timehow many steps the algorithm performsthe program is too slow to be useful
Spacehow much memory the algorithm needs while it runsthe data no longer fits, or the program is forced to work far more slowly

Why do we bother analyzing them? Because:

  • Both are limited. A user won’t wait an hour for a student search, and a machine can only hold so much in memory.
  • We can’t just try it at full size. We don’t have 10,000,000 students on day one. We need to predict what will happen when the college grows.
  • Resources cost money. At large scale, more time and more memory mean more hardware, more waiting, and a bigger bill.
  • They give us a fair way to compare. Two algorithms can solve the same problem while using very different amounts of time and space.
  • They often pull against each other. Spending extra memory can save time, and the reverse. We can only choose wisely if we can measure both.

Most of this article studies time, because the ideas are easiest to see there. Space gets its own section later, and it turns out to use the same tools.

Complexity analysis is about scalability

Below n = 10, B is actually cheaper. At n = 10 they tie. After that, B pulls away and never comes back. So complexity analysis lets us ask: if the problem grows, how badly does the work grow? That is more useful than measuring how long the program takes on today’s input.

Why don’t we just measure the time?

The same algorithm takes 0.1 seconds on my laptop, 0.2 seconds on yours, and 0.03 seconds on a powerful server.

My laptop: 0.1 s
Your laptop: 0.2 s
Server: 0.03 s

Which is the true running time? There isn’t one universal answer. It depends on CPU, RAM, programming language, compiler or interpreter, operating system, implementation, system load, and input. So we ask something more fundamental: how does the amount of work grow as the input grows? That lets us reason about the algorithm independently of a particular machine.

What exactly are we measuring?

With n students, we can think of the work as a function of n, written T(n): the amount of work, or running time, as a function of input size.

  • Check every student once: T(n) = n.
  • Compare every student with every other student: T(n) = n².

The exact formula isn’t always literally the number of CPU instructions. It represents how the work grows with input size. Now we can study T(n).

The real thing we care about is growth

Take T(n) = n and T(n) = n² side by side, and make the input 10 times larger each row:

Input ×10 → left column work ×10, right column work ×100.

When input grows 10× and the work grows roughly 10×, that’s linear growth, written O(n). Don’t think of it as a mysterious label. Think: when my input becomes 10 times larger, my work becomes roughly 10 times larger.

Comparing every student with every other: 5 students → 5 × 5 = 25 comparisons; 100 → 10,000; 1,000 → 1,000,000. When the input becomes 10× larger, the work becomes roughly 100× larger. That’s O(n²). The important thing isn’t that there are “two loops.” It’s that the work grows roughly as the input multiplied by itself. This is why growth matters: the difference between the 10n and n² algorithms isn’t a slightly faster start, it’s a fundamentally different growth pattern.

But now we have a problem

Suppose we get T(n) = 3n + 7. For understanding how it scales on very large inputs, do we care about the 7, or the exact multiplier 3? Probably not much. See how the 7 fades:

We want a way to describe the shape of the growth without carrying every small detail. That is where asymptotic notation comes in.

What does “asymptotic” mean?

Asymptotic analysis is concerned with what happens as the input becomes very large.

We care about n → very large, not about n = 5 or n = 10. Algorithms that look similar on small inputs can behave completely differently at scale, so we focus on long-term growth behavior.

Why do we need bounds?

For T(n) = 3n + 7 we could say “the work is no more than n².” True for large n. Or “no more than n³.” Also true. Or “no more than 2ⁿ.” Also true. But these are too loose. They are correct, yet hide the actual growth. We want bounds that are meaningful.

Big-O: the upper bound

Big-O describes an asymptotic upper bound. T(n) = O(n) means, intuitively: once the input is large enough, the work does not grow faster than a constant multiple of n. It is a ceiling on growth. Is 3n + 7 under a ceiling of 4n? Check:

From n = 7 onward, 3n + 7 stays under 4n, so 3n + 7 = O(n). (O(n²) would also be true, but it’s far less informative.)

Why not pick an arbitrarily large bound?

“The algorithm never takes more than one trillion operations” may be technically true, but says nothing about scaling. “It is O(n¹⁰⁰)” is the same problem if the real growth is linear. Many upper bounds can be correct. We care about the tightest meaningful one, the one that tells us the most about the actual growth.

Lower bounds: Big-Ω

Instead of “How much can the work grow?” ask “How little can the work possibly grow?” That is a lower bound, written with Ω. T(n) = Ω(n) means: for large enough inputs, the work grows at least as fast as some constant multiple of n.

Big-Θ: the tight bound

For T(n) = 3n + 7, for large enough n: 2n ≤ T(n) ≤ 4n. That is exactly the band in the chart above, squeezed between two linear functions. The exact constants aren’t important. What matters is that both sides grow like n. So T(n) = Θ(n): the function grows at the same rate as n.

Why do we usually want the tightest bound?

For 3n + 7 we could write O(n), O(n²), O(n³) or O(2ⁿ). All are valid, but they carry different amounts of information. Say “O(2ⁿ)” and you’d reasonably worry the algorithm becomes unusable quickly, yet it is actually linear. The closer the bound is to the true behavior, the more useful it is. So when we can establish it, we want Θ(n). The goal isn’t any bound; it’s a meaningful characterization of growth.

Why do we ignore constants?

T₁(n) = 3n and T₂(n) = 100n aren’t identical; on a given input the second does far more work. But make the input 10× larger and both become 10× larger. Same growth pattern, so both are Θ(n).

Constants can matter in real systems. They just don’t change the asymptotic growth class.

Why do we ignore lower-order terms?

Take T(n) = n² + n + 100. For small inputs all three terms matter. As n grows, see which one dominates:

The smaller terms haven’t magically disappeared. We’ve just recognized they don’t determine the long-term growth. So T(n) = Θ(n²).

This is what asymptotic analysis is really doing

Start with something detailed like 7n² + 4n + 19. Ask: what determines the growth when n becomes huge? The answer is n², so we summarize it as Θ(n²). We deliberately throw away information, but information that is not relevant to the question we’re asking.

Slowly increase the problem size and watch the work:

Space complexity: how much memory?

So far we’ve asked how the work grows with n. We can ask the same question about memory: how much memory does the algorithm need as the input grows? Call it S(n). The same tools apply. We ignore constants and lower-order terms, and we describe growth with O, Ω and Θ.

A first example: the highest mark

Recall finding the highest of n marks. One method scans once and remembers a single value, best. Another first copies all the marks into a new list, then works on the copy. Both give the right answer. Drag the slider and compare the extra memory each needs:

Method 1 needs the same one extra cell no matter how big n gets: O(1) extra space. Method 2 needs one extra cell per mark: O(n) extra space. Notice that both read the same input. What differs is the memory the algorithm itself asks for on top of it.

When memory grows like n²

Suppose we compare every student with every other student and want to remember each result. That needs a table with one entry per pair. Here is n = 4:

4 × 4 = 16 cells. With 1,000 students the table would have 1,000,000 cells. The memory grows as the input multiplied by itself, just like the work did earlier.

Trading space for time

Back to the first article. Organizing students around IDs made lookups cheap, but the organization itself takes memory. In general, we often spend extra space to save time, for example by keeping an index of n entries so we don’t have to scan. Sometimes the trade goes the other way. This is why we measure both resources: improving one can cost us the other.

Note: books differ on whether “space” includes the input itself. Here we count the extra memory the algorithm needs. Always check which one is meant.

Complexity connects back to data structures

Data structures ask: how should I organize my information? Complexity analysis asks: how does the work required by that organization grow as the data grows? One organization gives “find student → O(n)”, another gives “find student → O(1)”. With 10 students the difference may be irrelevant. With 10 million it can change the whole system. A data structure determines which operations are easy; complexity analysis tells us how well those operations scale.

The complete picture

We ignore machine-specific times, constants and insignificant details, and study asymptotic growth. When several bounds are possible, we prefer the tightest meaningful one.

The deepest mental model

Complexity analysis is not really about counting operations. It is about understanding scalability.

Mentally grow the problem: 10, 100, 1,000, 10,000, 100,000, 1,000,000… and ask, “How does the work grow?” Asymptotic notation is the language for that.

  • Big-O: how fast can the work grow?
  • Big-Ω: how slowly can the work grow?
  • Big-Θ: what is the actual asymptotic growth, when upper and lower bounds match?

Once you think this way, O(n), O(log n), O(n²), Ω(n) and Θ(n) stop being mysterious symbols. They become a language for describing how algorithms grow.
