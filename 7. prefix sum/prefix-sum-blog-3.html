When Equality Becomes a Remainder

We don’t need a new pattern every time the question changes. Sometimes the old idea is already correct. We only need to change what it means for two states to “match.”

In the previous article we reached an important idea. For a subarray from i to j, sum(i … j) = prefix[j + 1] − prefix[i]. If we want the sum to be exactly K, then prefix[i] = prefix[j + 1] − K, so we walk through the array, remember the prefix states from the past, and ask what previous prefix would make this subarray valid. 1. What if we don’t care about the exact sum?

Suppose the problem says: find a subarray whose sum is divisible by K. For nums = [2, 4, 3, 5] and K = 3, the subarray [4, 3, 5] has sum 12, and 12 % 3 = 0. At first glance this looks like a completely different problem, so let’s start with the definition. Divisible means sum % K = 0, and for a subarray sum = prefix[j] − prefix[i], so we want (prefix[j] − prefix[i]) % K = 0.

The naive way

Try every subarray with a running sum and test sum % K. That is O(n²).

When is a difference divisible by K?

When the two numbers leave the same remainder. With K = 5, 17 % 5 = 2 and 12 % 5 = 2, and 17 − 12 = 5. Likewise 27 and 42 both leave remainder 2, and 42 − 27 = 15. So A % K == B % K implies (A − B) % K == 0, and the subarray problem becomes:

Find two prefix sums that have the same remainder modulo K.

Drag K. The highlighted numbers all leave the same remainder as 12, and neighbours differ by exactly a multiple of K.

2. The old idea is still alive

For an exact sum we asked previous_prefix = current_prefix − K. Now we want current_prefix % K = previous_prefix % K. So instead of remembering prefix → information we remember remainder → information. That is the entire conceptual transition. We haven’t invented a new algorithm. We’ve changed what information about the prefix matters.

Look at a real example

Take nums = [4, 5, 0, -2, -3, 1] and K = 5, with positives, zero and negatives. The prefix sums are 0, 4, 9, 9, 7, 4, 5 and their remainders are 0, 4, 4, 4, 2, 4, 0. The remainder 4 appears four times. Choose any two prefix positions and see whether they bound a subarray divisible by 5. Equal remainders share a colour.

The actual prefix values don’t matter anymore. Only their remainders matter. We’re not searching for subarrays anymore. We’re grouping prefix states.

3. Subarray Sums Divisible by K

Count the subarrays whose sum is divisible by K. In the previous article the map was prefix → frequency. Now it is remainder → frequency, because we want to count pairs of prefixes with the same remainder. Whenever we meet remainder r again, every earlier occurrence of r forms a valid subarray with the current position. Step through the example, then the second preset.

Yellow is the current element, green the most recent subarray counted at this step. The map shows how many earlier prefixes had each remainder.

Python code (click to hide or show)
def subarrays_div_by_k(nums, k):
    remainder_count = {0: 1}
    prefix = 0
    answer = 0

    for num in nums:
        prefix += num

        remainder = prefix % k

        answer += remainder_count.get(remainder, 0)

        remainder_count[remainder] = (
            remainder_count.get(remainder, 0) + 1
        )

    return answer

Why {0: 1}? Before processing anything the prefix is 0, and 0 % K = 0. There is one empty prefix with remainder 0, the same leading-zero idea as before. The key line reads: how many earlier prefixes had the same remainder as me? Each one gives a subarray whose sum is divisible by K.

Why does counting equal remainders count subarrays?

If P[i] % K == P[j] % K then P[j] − P[i] is divisible by K, and P[j] − P[i] is exactly the sum of the subarray between them. Same remainder, so the difference is divisible, so the subarray sum is divisible. That is the entire algorithm.

4. Compressing information, and negative numbers

Suppose the prefix sums are 102, 57, 302 and 1000002, and K = 5. If we only care whether differences are divisible by 5, storing the whole numbers is unnecessary. All four leave remainder 2, so they belong to one group, and we remember just remainder 2.

If a problem only cares about some property of a value, we may not need to remember the entire value. Keep only the information the constraint actually cares about.

Python’s modulo conveniently normalizes negatives: -2 % 5 is 3, so remainders always land in 0 … K−1. What matters conceptually is that two numbers share a remainder class exactly when their difference is divisible by K. For example -2 % 5 = 3 = 3 % 5, and 3 − (−2) = 5. In languages where % can return a negative value (Java, C++, JavaScript), normalize with ((x % k) + k) % k.

5. Continuous Subarray Sum

Now ask: does there exist a subarray whose sum is a multiple of K (K, 2K, 3K, …, or zero)? We already know the core idea: have we seen this remainder before? But there is an extra constraint, the subarray must contain at least two elements. If we only check that a remainder has appeared before, we might accept a one-element subarray. So we need to remember where we first saw each remainder: remainder → earliest index. The prefix mathematics hasn’t changed. The question has changed what we need to store.

Why the earliest index?

If the same remainder was seen at index 2 and later at 5, the subarray ending at j has length j − 2 or j − 5. For a length constraint the earliest occurrence is most useful because later ones can’t give a longer subarray. Try the third preset, [6] with K = 6, where the remainder matches but the subarray is too short.

Python code (click to hide or show)
def check_subarray_sum(nums, k):
    first = {0: -1}
    prefix = 0

    for i, num in enumerate(nums):
        prefix += num
        remainder = prefix % k

        if remainder in first:
            if i - first[remainder] >= 2:
                return True
        else:
            first[remainder] = i

    return False

The assignment first[remainder] = i only happens when the remainder hasn’t been seen. We deliberately keep the earliest index.

6. Odd and even: modulo 2

Modulo isn’t only for arbitrary K. Ask: how many subarrays have an odd sum? Every prefix has remainder 0 (even) or 1 (odd) modulo 2. If two prefixes have the same parity, their difference is even. If they differ, it is odd. So a subarray has an odd sum exactly when its starting and ending prefix parities differ.

For nums = [1, 3, 5] the prefix sums are 1, 4, 9, with parities odd, even, odd. We keep counts of even and odd prefixes, starting with even = 1, odd = 0 for the empty prefix. When the current prefix is odd we need a previous even one, and vice versa.

Python code (click to hide or show)
def num_of_subarrays(nums):
    MOD = 10**9 + 7
    even, odd = 1, 0
    prefix = 0
    answer = 0

    for num in nums:
        prefix += num

        if prefix % 2 == 1:
            answer += even
            odd += 1
        else:
            answer += odd
            even += 1

    return answer % MOD

A subarray property can often be expressed as a relationship between two prefix states.

7. Equivalence classes

This sounds more abstract than it needs to be. With K = 4 every number falls into one of four groups: remainder 0 (0, 4, 8, …), remainder 1 (1, 5, 9, …) and so on. Two numbers in the same group differ by a multiple of 4. Drag K and see the groups.

So instead of the exact prefix sum we ask which remainder group a prefix belongs to, and the subarray problem becomes a grouping problem.

8. Information design, and when to use this

Odd sum?Parity → frequency

The prefix sum is not the final algorithm. It is the state. The hashmap stores whatever property of that state is useful for the question. When you see contiguous subarrays with sums, divisibility, multiples, parity, or equal counts after a transformation, ask whether the condition can be written as a relationship between two prefix states. If it becomes difference % K == 0, think same prefix remainder. Then ask what you need from the past: existence, frequency or earliest index.

9. But there is a boundary

It’s tempting to think “prefix sum + hashmap solves every subarray problem.” It doesn’t. It works when the relationship is current state ↔ previous state and the previous state can be efficiently remembered. Now consider: find the shortest subarray whose sum is at least K. The condition isn’t difference = K or difference % K = 0. It is difference ≥ K, and we also want the smallest distance. Any earlier prefix that is small enough qualifies, so an exact lookup in a hashmap can’t find the closest one. That introduces ordering and comparison between prefix states.

When the constraint changes, don’t force the old tool to fit. Let the constraint tell you what information must be preserved.

10. The evolution so far

The progression isn’t Pattern 1, Pattern 2, Pattern 3. It is same state + new constraint + different information needed = new solution.

The deeper lesson

We began with “can I avoid recomputing sums?”, which gave prefix sums. Then “can I discover a subarray by comparing the current prefix with something from the past?”, which gave the hashmap. Now we learned that if a problem only cares about divisibility, the exact prefix value contains more information than we need, so we compress prefix sum into prefix sum % K and compare the compressed states. The important idea isn’t remainder = prefix % k. It is to keep only the information that the constraint actually cares about.

Coming next

So far our questions were: does a previous state exist, how many, how far back was the first one? Now we ask for the shortest subarray whose sum is at least K. That is an inequality while minimizing distance, and it breaks the simple hashmap. When the old representation is no longer enough, we ask the same question as always: what information do we actually need to keep? That leads us to prefix sums + a monotonic deque.
