Why Do We Need Prefix Sums?

A prefix sum is not a trick to memorize. It is what naturally appears when we get tired of doing the same work again and again.

1. We have seen this problem before

Take [3, 1, 4, 2, 5, 6]. What is the sum from index 1 to index 4? Easy: 1 + 4 + 2 + 5 = 12.

The naive way

Python code (click to hide or show)
def range_sum(arr, left, right):
    total = 0

    for i in range(left, right + 1):
        total += arr[i]

    return total

For one query there is nothing wrong with this. But suppose the problem asks sum(1, 4), sum(0, 3), sum(2, 5), sum(1, 5), sum(0, 4) and so on. Something feels suspicious. sum(1, 4) adds 1 + 4 + 2 + 5 and sum(2, 5) adds 4 + 2 + 5 + 6. We calculated 4 + 2 + 5 once, then calculated it again. The problem isn’t addition. The problem is repeated work.

Can we remember our work?

This is one of the most useful questions in algorithm design: if I have already calculated something, can I store it so I don’t calculate it again? Let’s keep the cumulative sum as we move from left to right. Step through it.

Yellow is the element being added, green the elements already absorbed. Each prefix value contains all the work done before it.

That is our first prefix sum array. Nothing magical happened. We simply remembered the cumulative work we had already done.

2. How does remembering help?

Say we want sum(1, 4) with prefix = [3, 4, 8, 10, 15, 21]. prefix[4] = 15 contains 3 + 1 + 4 + 2 + 5. We don’t want the 3, and prefix[0] = 3. So 15 − 3 = 12, which is exactly 1 + 4 + 2 + 5. A potentially repeated calculation became a subtraction.

The real idea isn’t the formula. It is: store large overlapping sums once, then remove the part you don’t need.

Choose any range. The big prefix is green and the unwanted prefix is blue. Every range is big prefix − unwanted prefix.

The formula emerges naturally

Define P[i] as the sum of elements 0..i. Then P[right] is arr[0] + … + arr[left−1] + arr[left] + … + arr[right], and P[left−1] is the first part. Subtract and what survives is arr[left] + … + arr[right]. So sum(left, right) = P[right] − P[left−1]. We didn’t memorize it. It is simply cancellation.

3. The annoying edge case, and the leading zero

If left = 0 we’d need P[-1], which doesn’t represent what we want (drag the start to 0 above to see it). We could special-case it, but there is a cleaner idea: start the prefix array with 0. Now P[i] means the sum of the first i elements, and the formula becomes uniform: sum(left, right) = P[right + 1] − P[left].

The extra zero isn’t mathematical magic. It represents the sum of zero elements. This indexing idea will return throughout DSA.

Let’s build it

Python code (click to hide or show)
def build_prefix_sum(arr):
    prefix = [0]

    for num in arr:
        prefix.append(prefix[-1] + num)

    return prefix

def range_sum(prefix, left, right):
    return prefix[right + 1] - prefix[left]

prefix = build_prefix_sum([3, 1, 4, 2, 5, 6])
print(range_sum(prefix, 1, 4))   # 12

The result is [0, 3, 4, 8, 10, 15, 21]. The implementation is almost boring, and that’s a good sign.

4. What did we actually trade?

We didn’t make computation disappear, we moved it. Without prefix sums every query walks its range again. With prefix sums we walk the array once to store cumulative information, then each query is two array accesses and a subtraction. We spend extra memory and preprocessing time to make repeated queries cheap.

When is it worth it?

With one million elements and a single query, building a million-element prefix array may not be useful. With a million queries, the same information is recomputed again and again and preprocessing wins. Play with the sliders and find where the trade flips.

Why not the simpler approach?

NaivePrefix sum
PreprocessingNoneO(n) time
Per queryO(range length)O(1)
Extra spaceO(1)O(n)
Best whenFew queriesMany queries on the same array

We paid once so we don’t have to pay repeatedly. If the same expensive computation appears repeatedly, perhaps we should preprocess and remember something.

5. Four problems, one idea

Problem 1: Running Sum of 1D Array

Given [1, 2, 3, 4], return [1, 3, 6, 10]. At every position the question is “what is the sum of everything I’ve seen so far?”, which is the definition of a prefix sum.

Python code (click to hide or show)
def running_sum(nums):
    result = []
    total = 0

    for num in nums:
        total += num
        result.append(total)

    return result

We don’t need a separate prefix array here because the problem asks us to return those values. The concept and the implementation structure are different things. How we store the accumulated information depends on what the problem asks us to do with it. (The stepper in section 1 is exactly this problem.)

Problem 2: Range Sum Query

With nums = [-2, 0, 3, -5, 2, -1] and many queries like [0, 2], [2, 5], [0, 5], calculating each independently re-walks the same elements. The reasoning is: many overlapping range sums, repeated addition, remember cumulative sums, subtract the unwanted prefix, O(1) query.

Python code (click to hide or show)
class NumArray:

    def __init__(self, nums):
        self.prefix = [0]

        for num in nums:
            self.prefix.append(self.prefix[-1] + num)

    def sumRange(self, left, right):
        return self.prefix[right + 1] - self.prefix[left]

For those queries the answers are 1, -1 and -3.

Problem 3: Find Pivot Index

Find the index where the sum to the left equals the sum to the right. In [1, 7, 3, 6, 5, 6] the answer is index 3, since 1 + 7 + 3 = 11 and 5 + 6 = 11.

The naive thought is to compute both sums for every index, which repeatedly re-walks the array. A nicer observation: with total known and a running left_sum, the right side is right_sum = total − left_sum − nums[i]. Slide the pivot across the array.

Green is the left side, yellow the current element, blue the right side.

Python code (click to hide or show)
def pivot_index(nums):
    total = sum(nums)
    left_sum = 0

    for i, num in enumerate(nums):
        right_sum = total - left_sum - num

        if left_sum == right_sum:
            return i

        left_sum += num

    return -1

Prefix information doesn’t always need a visible array. Sometimes a single running variable is enough.

Problem 4: Left and Right Sum Differences

For [10, 4, 8, 3], compute |left_sum − right_sum| at every index. At index 2 the left is 10 + 4 = 14, the right is 3, and the difference is 11. We already have what we need: total = 25 and a running left_sum.

Python code (click to hide or show)
def left_right_difference(nums):
    total = sum(nums)
    left_sum = 0
    result = []

    for num in nums:
        right_sum = total - left_sum - num
        result.append(abs(left_sum - right_sum))
        left_sum += num

    return result

Same idea, different question.

6. Prefix sum is not always an array

When people hear “use prefix sum” they think of prefix = [0] * (n + 1). That isn’t the important part. The important part is that we have cumulative information about everything before the current position. That information can live in different places depending on what the problem needs us to remember.

Where it livesWhenExample here
An arrayWe need to query arbitrary ranges laterRange Sum Query
One variableWe only need the running total as we scanPivot Index, Left/Right Differences
A hashmapWe need to look up earlier prefix valuesComing next
A dequeWe need prefix values in a sliding windowLater

7. The deeper pattern

We started with “I need the sum of this range” and the naive answer of walking the range and adding. Then we noticed that different ranges overlap, and asked why we calculate the same partial sums again. We stored cumulative sums, then noticed that a large prefix contains smaller prefixes, so large prefix − smaller prefix gives exactly the range we want. That is preprocess, remember cumulative information, query, subtract what we don’t need. This is the first form of prefix sum.

8. A useful way to recognize these problems

  1. Am I adding the same numbers again and again? Overlapping ranges are the sign.
  2. Are there many queries on a fixed array? That is when preprocessing pays off.
  3. Do I need “everything before” and “everything after” a position? A running total plus the grand total often suffices.
  4. Can the answer be written as one accumulation minus another? That is cancellation.
  5. What is the smallest form of memory I need? An array, a variable, or something later.

9. What we learned, and where this goes next

Where this becomes much more interesting

So far we ask “what is the sum of this range?” and the prefix sums answer “here.” The more interesting problems ask something different, because now we aren’t given a range. We have to discover it.

QuestionWhat changes
How many subarrays have sum exactly K?We must find the ranges ourselves
What is the longest subarray whose sum is K?We must remember where a prefix sum first appeared
How many subarrays have a sum divisible by K?We compare prefix sums by remainder

At that point prefix sums stop being merely a fast way to answer range-sum queries. They become a way of remembering the past so we can recognize a useful subarray when we reach its end. Instead of asking “what did I accumulate?”, we’ll ask “have I seen the prefix sum I need before?” That small change in the question leads naturally to prefix sum + hashmap.

When the same computation keeps appearing, ask whether some information from the past can be stored and reused.
