When Equality Is Not Enough

So far, our prefix-sum journey has been remarkably consistent. We started with repeated range calculations and fixed them with prefix sums. Then we saw that a subarray sum is the difference of two prefix sums. A target sum became "look for the required previous prefix", and divisibility became "compare prefix remainders". The hashmap appeared naturally, because we needed to remember useful information about the past.

Now we meet a problem where that simple memory is not enough. We do not want to learn a new pattern because someone says "this is a monotonic deque problem". We want to understand why the old approach stops working and what new constraint forces us to evolve it.

Sometimes the old idea is correct, but the information we kept is no longer enough.

1. A different question

Take the array [2, -1, 2, 3, -2, 4] and ask: what is the shortest contiguous subarray whose sum is at least 5?

Notice the difference from what we have seen. Before, the condition was sum == K or sum % K == 0. Now it is sum >= K, and we want the shortest such subarray.

Let's find one by hand. The subarray [2, 3] has sum 5, so its length is 2. Could a length-1 answer exist? The largest single element is 4, so no. The answer is 2.

2. Why the hashmap is not enough

As always, sum(i ... j) = prefix[j + 1] - prefix[i]. We need prefix[j + 1] - prefix[i] >= K, which rearranges to:

prefix[i] <= prefix[j + 1] - K

This looks promising. For the exact-sum problem the condition was previous = current - K: exactly one value to look for, which a hashmap handles beautifully. Now we need previous <= current - K, and there may be many values that qualify.

We don't want one exact value. We want the best one, and "best" means the shortest subarray. If two valid previous prefixes sit at indices 2 and 7, then j - 7 beats j - 2.

Among all valid previous prefixes, we want the latest one.

The naive way

Compute all prefix sums, and for every current prefix scan every earlier one asking "is P[i] <= P[j] - K?". It is correct, but it can take O(n²).

Python code (click to hide or show)
def shortest_naive(nums, k):
    prefix = [0]
    for num in nums:
        prefix.append(prefix[-1] + num)

    best = len(nums) + 1
    for j in range(1, len(prefix)):
        for i in range(j):
            if prefix[j] - prefix[i] >= k:
                best = min(best, j - i)

    return best if best <= len(nums) else -1

We are back to the problem we were trying to escape: too much repeated searching through history.

What our history must support

For a current prefix we need to (1) find previous prefixes that are small enough, and (2) among them prefer the most recent. A hashmap answers "give me the information for exactly this key". We now need "give me the best previous state among all keys below a threshold". That is a different kind of question.

3. Some old states are useless

For [2, -1, 2, 3, -2, 4] the prefix sums are:

Write each state as (i, P[i]): its index and its prefix value. Now compare (1, 2) and (2, 1). The state at index 2 is later, and its prefix value 1 is smaller. Whenever the current prefix is large enough for both to be valid, we would rather use index 2, because current_index - 2 is shorter than current_index - 1.

So (1, 2) has become useless. It is dominated by (2, 1), and we can forget it.

A previous state is permanently useless when another state is both newer and better for every future query.

What does "better" mean here?

  • A small prefix value is better, because it makes P[i] <= P[j] - K easier to satisfy.
  • A large index is better, because it produces a shorter subarray.

A state with a larger prefix and a smaller index than another state is worse in both dimensions. It can never win. Step through the prefixes below and watch states get dominated.

We are not throwing information away randomly. We remove only states that can never become optimal.

4. Two ends, so a deque

Suppose our useful history has prefix values 0, 1, 3, 6, the current prefix is 8, and K = 5. We need previous <= 3, so 0, 1 and 3 are all valid. We should use the latest valid one, 3. We examine valid candidates from the front of our history and remove them as they get used. That looks like a queue.

But we also need to remove dominated states from the back, as the new prefix arrives. So we need access to both ends.

The deque is not the idea. It is what the constraints force on us.

Why not a normal queue?

A FIFO queue only removes from the front. With prefix values 0, 5 in the queue and 2 arriving, the state with 5 is dominated and sits at the back. A queue cannot remove it.

Why does the deque end up increasing?

We drop an old state (i, P[i]) whenever a later state satisfies P[j] <= P[i]. So among the states we keep, prefix values must be strictly increasing from front to back, for example 0 < 1 < 3 < 4. That is the monotonic deque, and the monotonic property is what lets us discard states cheaply.

After both cleanups, we append the current state.

5. The complete algorithm

The problem: given an integer array nums and an integer K, return the length of the shortest non-empty subarray whose sum is at least K, or -1 if none exists. For example, nums = [2, -1, 2] with K = 3 has prefix sums 0, 2, 1, 3, and 3 - 0 = 3 gives the whole array, length 3.

Watch the deque evolve

Each step is one action. A POP FRONT means a valid candidate was found. A POP BACK means a dominated state was removed. The first example is our running one.

Now you drive it

At each prefix, choose the next move. The front is always checked before the back.

The code

Python code (click to hide or show)
from collections import deque


def shortest_subarray(nums, k):
    prefix = [0]

    for num in nums:
        prefix.append(prefix[-1] + num)

    dq = deque()
    answer = len(nums) + 1

    for i, current in enumerate(prefix):

        # Find valid subarrays ending here.
        while dq and current - prefix[dq[0]] >= k:
            answer = min(answer, i - dq.popleft())

        # Remove states dominated by the current prefix.
        while dq and prefix[dq[-1]] >= current:
            dq.pop()

        dq.append(i)

    return answer if answer <= len(nums) else -1

The code should now feel like the result of several constraints rather than a memorized recipe:

  • while dq and current - prefix[dq[0]] >= k: the oldest useful prefix is small enough that the current prefix forms a large enough sum.
  • answer = min(answer, i - dq.popleft()): record the length, and discard this starting point because waiting only makes it longer.
  • while dq and prefix[dq[-1]] >= current: the back state is older and no smaller, so it is dominated.
  • dq.append(i): keep the current prefix as useful future history.

The deque is not "better" in every way. If all numbers are positive, a sliding window is simpler and uses less memory. The deque earns its place exactly when negatives break the window's assumption, and it pays with O(n) memory and an invariant you have to get right.

6. Why negative numbers matter

If all numbers were positive, expanding a window would always increase the sum and shrinking it would always decrease it. That monotonic behavior lets a sliding window control the sum. With negatives, the sum can move in either direction, so the link between window size and window sum is gone.

7. Why this is O(n)

The code has a while loop inside a for loop, which looks like O(n²). It is not. Every prefix index is:

  • appended once,
  • removed from the front at most once,
  • removed from the back at most once (and never both, since it is gone after the first removal).

So across the whole run, appends, front pops and back pops are each O(n). Total time is O(n) and space is O(n). Drag the slider to count the real operations on a pseudo-random array.

The important question is not how many loops are nested. It is how many times each piece of information can move through the data structure.

We pay O(n) extra memory for this. That is the same philosophy as before: spend memory to remember useful history, and avoid repeatedly searching old states. The difference is that our memory is no longer a plain array or hashmap. It is a maintained set of only the states that can still matter.

8. What these problems taught us

The prefix-sum foundation never changed across the three variants. The constraint changed the data structure.

9. The bigger pattern

Normally we think more information is safer. But more information can also make searching expensive. So a powerful strategy is to keep only the information that could still produce a better answer.

For this problem, a state is useless if a later state has a smaller-or-equal prefix and a larger index. That is called dominance, and the monotonic deque is a structure for maintaining the non-dominated history. The idea reaches far beyond this one problem.

A mental model

Imagine every prefix sum is a person standing in a line, with two properties: when they arrived, and their prefix value. For a future prefix, we want someone who arrived as recently as possible and whose value is small enough. If a newer person has an even smaller value, the older one has no advantage left, so they leave. If someone has already helped form a valid shortest subarray, they cannot help form a shorter one later, so they leave too. The deque holds the candidates from the past that can still win.

10. A useful way to recognize these problems

Don't ask "which pattern is this?". Ask these questions in order, with the answers for this problem:

  1. What is my state? The prefix sum.
  2. What does a valid subarray mean in terms of two states? P[j] - P[i] >= K.
  3. What am I optimizing? The minimum j - i.
  4. What information from the past do I need? A small enough prefix, preferably with the largest possible i.
  5. Which old states can never be useful again? Those dominated by a later, smaller prefix, and those that already produced a candidate.
  6. What data structure supports exactly those operations? A deque.

This is problem solving from constraints rather than pattern recognition.

11. The evolution of the idea

ProblemWhat it teaches
Repeated range sumsPrecompute prefix sums instead of re-adding.
Subarray sumA subarray is the difference of two prefix states.
Exact targetThe needed past state is one exact value, so use a hashmap.
Divisible by KCompare prefix remainders with a remainder hashmap.
At least K, shortestAn inequality plus optimization makes some states dominated, so keep only useful history with a monotonic deque.

We did not jump from "prefix sum" to "monotonic deque". We followed the constraints until the data structure became necessary.

Good algorithms often become fast not because they process more information, but because they learn which information can safely be forgotten.

Coming next

We have now seen three uses of prefix information: prefix sums for range queries, prefix sums with a hashmap to find or count matching past states, and prefix sums with a monotonic deque to optimize over a range of possible past states.

So far we have used prefix sums to reason about one-dimensional subarrays. What if we want to perform many range updates efficiently? Instead of asking "what is the sum of this range?", the question becomes "how can I change an entire range without touching every element?". That leads to difference arrays, another idea that comes from asking what work we can avoid.
