When Prefix Sums Run Backwards: Difference Arrays

What if, instead of asking “what is the sum of this range?”, we ask “how can I change this entire range without touching every element?”

So far, prefix sums have moved in one direction. We had an array and built cumulative information, prefix[i] = everything accumulated up to i, so that many range queries could be answered cheaply after precomputing once. Now let’s turn the problem around. Suppose an array represents seats, bookings, workloads or capacities, and we receive operations like “add 10 to every element from index 2 to 7,” then “add 5 to every element from 4 to 9,” then “subtract 3 from 1 to 6.” If we modify every element of every range directly, we do enormous amounts of repeated work. So: can we remember the changes instead of immediately applying them? That question gives birth to the difference array. 1. The problem: range updates

Start with [0, 0, 0, 0, 0, 0] and add 5 to indices 1 through 4. The result should be [0, 5, 5, 5, 5, 0].

The naive way

Python code (click to hide or show)
for i in range(1, 5):
    nums[i] += 5

That’s fine for one update. But with n = 1,000,000 elements and 100,000 range updates that each touch thousands of elements, the repeated work becomes enormous. Updating one element isn’t expensive. The problem is that we’re repeatedly touching the same elements just to communicate that a change should continue across a range. Maybe we can describe the change more intelligently.

2. What an update actually means

For “add 5 to [1, 4]” we don’t really need to say index 1 → +5, index 2 → +5, index 3 → +5, index 4 → +5. The update has a simpler structure: start adding 5 at index 1, keep going, and stop after index 4. The entire range is described by only two events: index 1 → +5 begins and index 5 → −5 ends. Notice the ending event sits at right + 1, not at right.

Record the changes, not the final values

The difference array for that update is [0, 5, 0, 0, 0, -5]. Take its prefix sum and you get [0, 5, 5, 5, 5, 0], exactly the array we wanted. Choose any update below. Green is the start event, blue the stop event.

A range update is just a start event and a stop event. Prefix accumulation spreads those events across the range.

Why does subtracting at right + 1 work?

For “add 5 to [2, 5]” we record diff[2] += 5 and diff[6] -= 5. Accumulating gives 0, 0, 5, 5, 5, 5, 0. The +5 survives through index 5 and the subtraction at index 6 says “the effect stops from here onward.” In general, for “add x to [left, right]” we do diff[left] += x and diff[right + 1] -= x. Two modifications, whether the range has length 3, 100 or 1,000,000.

3. The hidden relationship, and why n + 1

Earlier we started with an array and built its prefix sums to answer questions. Now we store where values change, and prefix accumulation reconstructs the values. They are nearly inverse operations. If we start from nums = [4, 7, 7, 2, 2], then diff[0] = nums[0] and diff[i] = nums[i] − nums[i − 1] give [4, 3, 0, -5, 0], and a prefix sum recovers the original. Step through both directions.

Yellow is the element being processed, green the elements already done.

Why do we allocate n + 1?

If right = n − 1 then right + 1 = n, which is outside the array. We still want to record “stop after the final element,” so diff = [0] * (n + 1) gives that ending event a safe place to live. We never reconstruct index n, only 0 … n − 1.

4. Multiple updates, and the tradeoff

Now the real benefit appears. With nums = [0, 0, 0, 0, 0, 0] take three updates: +5 to [1, 4], +3 to [2, 5] and +2 to [0, 2]. Instead of applying each one immediately we record its two events, then accumulate once. The combined diff is [2, 5, 3, -2, 0, -5, -3] and one pass gives [2, 7, 10, 8, 8, 3]. Step through it, and then the second preset (flight bookings, which we’ll meet shortly).

Green marks a start event, blue a stop event, yellow the position being accumulated.

Python code (click to hide or show)
def apply_range_updates(n, updates):
    diff = [0] * (n + 1)

    for left, right, value in updates:
        diff[left] += value
        diff[right + 1] -= value

    result = [0] * n
    current = 0

    for i in range(n):
        current += diff[i]
        result[i] = current

    return result

updates = [(1, 4, 5), (2, 5, 3), (0, 2, 2)]
print(apply_range_updates(6, updates))   # [2, 7, 10, 8, 8, 3]

The update phase never touches result. It only records changes in diff, and the final pass turns those changes into values.

The complexity transformation

With n elements and m range updates, the direct approach is O(m·n) in the worst case. Each difference-array update is O(1), and one reconstruction pass is O(n), so the total is O(m + n). Slide the numbers and watch.

Why not the simpler approach?

ApproachPer updateFinal reconstructionTotal
DirectO(range length)nonepotentially O(m·n)
Difference arrayO(1)O(n)O(m + n)

We didn’t magically eliminate work. We delayed it. This is especially useful when there are many updates but we don’t need the fully updated array after every individual update. If we needed to query after every update, this technique alone wouldn’t be enough.

This is the same philosophy as prefix sums: represent repeated work in a form that can be accumulated efficiently. Prefix sums store cumulative information. Difference arrays store change information.

5. Corporate Flight Bookings

An airline has n flights, and each booking [first, last, seats] adds seats passengers to every flight from first through last. For [[1, 2, 10], [2, 3, 20], [2, 5, 25]] with n = 5, the naive reaction is a loop over every affected flight for every booking. That repeats work, and the constraint is exactly what difference arrays were designed for.

Translate each booking into two events

[1, 2, 10] becomes flight 1 → +10, flight 3 → −10. [2, 3, 20] becomes flight 2 → +20, flight 4 → −20. [2, 5, 25] becomes flight 2 → +25, flight 6 → −25. One cumulative pass tells us how many passengers are on each flight. Run the second preset in the stepper above to watch it, with flights labelled 1 to 5. The answer is [10, 55, 45, 25, 25].

Python code (click to hide or show)
def corp_flight_bookings(bookings, n):
    diff = [0] * (n + 2)          # flights are 1-indexed

    for first, last, seats in bookings:
        diff[first] += seats
        diff[last + 1] -= seats

    result = []
    current = 0
    for flight in range(1, n + 1):
        current += diff[flight]
        result.append(current)

    return result

The problem has become: range updates → start/stop events → prefix accumulation → final values.

6. Car Pooling

A car has limited capacity. Trips are [passengers, from, to], for example [2, 1, 5], [3, 3, 7], [2, 6, 8]. The first means: pick up 2 at location 1 and drop them off at location 5. So the events are location 1 → +2 and location 5 → −2, and so on. Sweep left to right and the running total is how many passengers are in the car right now. If it ever exceeds capacity, the plan is invalid. Drag the capacity.

Yellow marks a location where the car is over capacity.

Python code (click to hide or show)
def car_pooling(trips, capacity):
    diff = [0] * 1002

    for passengers, start, end in trips:
        diff[start] += passengers
        diff[end] -= passengers      # dropped off at `end`

    current = 0
    for change in diff:
        current += change
        if current > capacity:
            return False

    return True

Notice how different the statements sound. Flight bookings say “add passengers to every flight in a range.” Car pooling says “pick up here, drop off there.” Structurally both say something starts affecting us and then stops affecting us, which is exactly what a difference array represents.

7. Difference arrays as event accumulators

This is an even more general way to see them. Imagine time moving forward. At time 10, +5 machines become active. At time 20, 2 stop. At time 30, 4 more start. We don’t write the number of active machines at every moment. We record time 10 → +5, time 20 → −2, time 30 → +4, sweep left to right, and the running total is the current state. A difference array is really an event accumulator.

An interval has two boundaries, start ---- end, so its effect is +effect at start and −effect immediately after end. The cumulative sum fills in everything between. That is the fundamental reason difference arrays work: they compress many repeated updates into boundary events.

8. Prefix sums vs difference arrays, and the wrong-tool cases

Prefix sumDifference array
Starts fromArray valuesRange updates
AsksWhat is the cumulative value, or the sum of this range?What is the final value at each position after all updates?
Directionvalues → cumulative informationrange changes → events → values

When difference arrays are the wrong tool

They shine when there are many range updates, the updates can be delayed, we need the final array afterwards, and the updates are additive. But suppose we must update a range, query the current range sum, update another range, query again…. Now we need answers between updates, and a plain difference array would require reconstructing the array after every update, which defeats the purpose. That is where structures like Fenwick trees or segment trees may become necessary. We shouldn’t jump there yet.

The important caveat

The technique assumes updates can be combined before their effects are materialized. For additive updates, +5, +3, −2 can be safely combined into +6 because addition is associative and order doesn’t matter. If the update operation doesn’t combine this way, we need to think more carefully. The algebra of the operation determines whether delayed accumulation is possible.

9. The evolution, and the bigger connection

The data structure wasn’t memorized. It was forced by the structure of the operation. And several techniques that looked unrelated now connect.

TechniqueInstead of…We…
Sliding windowRecomputing an entire rangeRemove what leaves, add what enters
Prefix sumRecomputing a range sumRemember cumulative work
Hashmap + prefix sumSearching every previous prefixRemember the useful states
Monotonic deque + prefix sumConsidering every previous stateDiscard states that can never win
Difference arrayApplying every range update immediatelyRemember only the boundaries

They are different answers to the same question: what work are we repeating, and what information would let us avoid repeating it?

10. Final takeaway, and where we go next

When you see many operations like add X to [L, R], don’t immediately think “loop from L to R.” Ask whether you can describe the effect using only where it starts and where it stops: L → +X, R + 1 → −X, then accumulate.

When a process has long stretches of identical behavior, store the boundaries where the behavior changes instead of storing every point inside the stretch.

Where we go next

We’ve explored prefix-based thinking in one dimension from several directions: prefix sums answer range sums, with a hashmap they discover unknown subarrays, with remainders they reason about divisibility, with a monotonic deque they optimize under inequalities, and difference arrays process many range updates. But what if the data isn’t a line? What if values live in a grid? Then a range isn’t left → right but a rectangle, and the same cumulative reasoning extends into two dimensions. That leads to 2D Prefix Sums, and shows that the idea was never really about arrays. It was about remembering cumulative information so that repeated work disappears.
