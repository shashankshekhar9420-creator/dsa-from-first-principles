Fast and Slow Pointers

So far, we have used two pointers in a few different ways. Sometimes they started at opposite ends:

L →                  ← R

Sometimes they both moved forward, but for different purposes:

slow →
fast →

The important lesson from two pointers was not: “Use two variables called left and right.” It was:

Keep track of two positions when the relationship between those positions gives you information.

Fast and slow pointers are simply another application of that idea. Here, the relationship is not usually where the pointers are. It is: how far each pointer has travelled.

One pointer moves slowly. The other moves quickly. And surprisingly, that difference in speed can reveal structural properties that would otherwise require extra memory or repeated traversal.

1. The Core Intuition: Relative Speed as an Information Probe

The Basic Idea & Linear Traversal

Imagine an ordinary linear linked list:

1 → 2 → 3 → 4 → 5 → 6 → None

Suppose we advance two pointers from the head, but with different step sizes:

Python code (click to hide or show)
slow = head
fast = head

while fast and fast.next:
    slow = slow.next
    fast = fast.next.next

Their trajectories unfold side-by-side:

slow: 1 → 2 → 3 → 4 → 5 → 6

fast: 1 → 3 → 5 → None

The two pointers travel through the exact same structure, but at different rates. If the structure is finite and linear, fast simply reaches None twice as fast as slow. But what happens if the structure contains a cycle?

What Happens in a Cycle: The Circular Track

Consider a list where node 6 connects back to node 3:

Once both pointers enter the cycle, neither pointer can escape. slow moves 1 step per turn (→ → → →), while fast moves 2 steps per turn (→→ →→). This is identical to two runners on a circular running track:

If one runner runs twice as fast as another on a closed loop, the faster runner must eventually lap and catch the slower runner.

Mathematical Derivation: Why Fast Must Catch Slow

Why can't fast jump cleanly over slow and skip it forever? The answer lies in relative distance:

Let the cycle contain L nodes.
In each iteration, slow advances +1 step.
In each iteration, fast advances +2 steps.
Relative speed: 2 - 1 = +1 node / iteration.
If the distance behind slow is d, then after 1 turn the distance is d - 1.
After 2 turns: d - 2 ... until d = 0 (Collision!).

Because the gap decreases by strictly 1 unit at each iteration, it is mathematically impossible for the gap to transition from 1 to negative without landing squarely on 0. They cannot skip past each other!

2. Problem 1: Linked List Cycle Detection

The Problem Statement

Given the head of a linked list, determine whether the linked list contains a cycle. For example:

1 → 2 → 3 → 4 → 5 → 3 ... (Cycle detected: return True)

Whereas 1 → 2 → 3 → 4 → 5 → None terminates (return False).

Set of Visited Nodes vs Movement

The naive approach uses a hash set to record every visited node:

Python code (click to hide or show)
def has_cycle_set(head):
    seen = set()
    current = head
    while current:
        if current in seen:
            return True
        seen.add(current)
        current = current.next
    return False

The reasoning is intuitive: “If I ever see the same node reference twice, I must have traversed a cycle.” However, if the list contains n nodes, the set consumes O(n) auxiliary memory. Can we detect the cycle with zero extra memory?

Floyd's Cycle Finding Algorithm

Instead of remembering every visited node in memory, we maintain two moving pointers: slow and fast. If fast encounters None, the list is acyclic. If slow is fast at any point, a cycle exists.

Python code (click to hide or show)
def has_cycle(head):
    slow = head
    fast = head

    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next

        if slow is fast:
            return True

    return False

Notice we use slow is fast (reference identity), not slow == fast. We verify whether they point to the exact same memory address, not whether two separate nodes happen to hold equal values.

3. Problem 2: Finding the Start of the Cycle

Why the Meeting Point Is Not the Entrance

Knowing that a cycle exists is useful, but many real-world problems require finding the exact entrance node where the cycle begins:

1 → 2 → 3 → 4 → 5 → 6 → 3  (Cycle entrance is node 3)

Notice that in Problem 1, slow and fast collided at node 5. The meeting point is almost never the entrance! Why should this collision help us locate the entrance? It doesn't directly — until we analyze the distance geometry.

Thinking in Distances: Defining a, b, and c

Let's partition the linked list into three precise distances:

  • a: Distance from head to the cycle entrance.
  • b: Distance from the cycle entrance to the meeting point.
  • c: Remaining distance from the meeting point back to the cycle entrance.

The total length of the cycle is L = b + c.

Interactive Derivation: Visualizing a ≡ c (mod L)

Let's derive the algebraic relationship step-by-step:

1. When slow and fast meet:
Distance travelled by slow: D_slow = a + b
Distance travelled by fast: D_fast = 2 × D_slow = 2(a + b)

2. Fast has also looped around the cycle k times (where k ≥ 1):
D_fast = a + b + k × L

3. Equating both expressions for D_fast:
2(a + b) = a + b + k × L
a + b = k × L

4. Express L as (b + c):
a + b = (k - 1)L + b + c

5. Subtract b from both sides:
a = (k - 1)L + c

This is the fundamental formula of Floyd's Cycle Detection. For k = 1 (the most common case where fast laps slow once), this simplifies directly to: a = c!

The distance from the head to the cycle start (a) is identical to the distance from the meeting point back to the cycle start (c)!

Adjust the parameters below. Watch how moving one pointer a steps from head and another pointer c steps from the meeting point brings both pointers to the entrance at the exact same moment:

The Second Phase: Aligning the Dual Race

The algebraic equivalence a = c gives us an elegant two-phase algorithm:

  1. Phase 1: Run slow (1 step) and fast (2 steps) until they collide inside the cycle.
  2. Phase 2: Leave fast at the meeting point. Reset slow back to head. Now advance both one step at a time.
  3. Because both pointers must travel identical distances (a = c), they will collide at the cycle entrance!

Full Implementation & Verification

Python code (click to hide or show)
def detect_cycle(head):
    slow = head
    fast = head

    # Phase 1: detect meeting point
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            break
    else:
        return None  # No cycle exists

    # Phase 2: find cycle entrance
    slow = head
    while slow is not fast:
        slow = slow.next
        fast = fast.next

    return slow

4. Generalizing to State Machines: Problem 3 — Happy Number

The Happy Number Problem

Take any positive integer. Replace the number by the sum of the squares of its digits, and repeat:

19 → 1² + 9² = 82 → 8² + 2² = 68 → 6² + 8² = 100 → 1² + 0² + 0² = 1 (Happy!)

If the sequence reaches 1, the number is happy. But what happens if we start with 2?

2 → 4 → 16 → 37 → 58 → 89 → 145 → 42 → 20 → 4 ...

The computation loops endlessly in an 8-number cycle: 4 → 16 → 37 → 58 → 89 → 145 → 42 → 20 → 4.

The Hidden Linked List: Computed Next Pointers

Notice that every number has exactly one deterministic next number: next_state = sum_of_squared_digits(n). We don't need actual Node objects in memory. The computational function f(n) acts as the node.next reference!

Python code (click to hide or show)
def next_number(n):
    total = 0
    while n:
        digit = n % 10
        total += digit * digit
        n //= 10
    return total

def is_happy(n):
    slow = n
    fast = n

    while True:
        slow = next_number(slow)
        fast = next_number(next_number(fast))
        if slow == fast:
            break

    return slow == 1

5. Array as an Implicit Graph: Problem 4 — Find the Duplicate Number

The Problem and Special Constraints

Given an array of integers nums containing n + 1 integers where each integer is in the range [1, n] inclusive. There is only one repeated number. Find the duplicate without modifying the array and using only O(1) extra space.

nums = [1, 3, 4, 2, 2]   (n = 4, length = 5, duplicate = 2)

Mapping Indices to Values (i → nums[i])

Because every value in nums is between 1 and n, each value can be interpreted as a valid index in the array! If we define: current_node = i and next_node = nums[i], the array transforms into a directed graph:

Index 0 → nums[0]=1 → nums[1]=3 → nums[3]=2 → nums[2]=4 → nums[4]=2 → nums[2]=4 ...

Pigeonhole Principle: Why Duplicates Guarantee a Cycle

The array has n + 1 indices pointing to only n distinct target values. By the Pigeonhole Principle, at least two separate indices must contain the same value. That means two directed arrows merge into the same node! Once two paths merge, they enter a cycle. The entrance to that cycle is the duplicate value.

6. Beyond Cycles: Problem 5 — Middle of the Linked List

Single-Pass Midpoint Discovery

Suppose: 1 → 2 → 3 → 4 → 5. We want node 3 without counting the total length first. The standard two-pass approach traverses once to count n, then traverses n/2 steps in a second pass. Fast and slow pointers find the middle in exactly one pass.

The 2:1 Invariant: Halfway Across the Structure

Speed of fast = 2 × Speed of slow.
Distance of fast = 2 × Distance of slow.
When fast reaches the end (Distance = n), slow must have travelled n / 2 steps!
Python code (click to hide or show)
def middle_node(head):
    slow = head
    fast = head

    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next

    return slow

Interactive Midpoint Explorer: Odd vs Even Lengths

For odd lists, fast lands on the last node (fast.next is None). For even lists, fast reaches None, returning the second middle node (node 4).

A Foundational Primitive: Splitting the List

Finding the midpoint in O(n) time and O(1) space is a cornerstone primitive in DSA. It allows splitting a singly linked list into two equal halves without auxiliary arrays, serving as the basis for merge sort, palindrome checking, and list reordering.

7. Algorithmic Decomposition: Problem 6 — Palindrome Linked List

Why Singly Linked Lists Cannot Traverse Backward

In an array [1, 2, 3, 2, 1], we can place two pointers at the ends (L →   ← R) and compare inward. But in a singly linked list, there are no backward pointers!

The 3-Step Pipeline: Find Middle → Reverse → Compare

We decompose the problem into three reusable building blocks:

  1. Find the middle: Use fast/slow pointers to find the midpoint in one pass.
  2. Reverse the second half: Invert the next pointers of the second half in place.
  3. Compare halves: Move first from head and second from the reversed tail. If all values match, it is a palindrome!
Python code (click to hide or show)
def is_palindrome(head):
    slow = head
    fast = head

    # 1. Find middle
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next

    # 2. Reverse second half
    prev = None
    curr = slow
    while curr:
        nxt = curr.next
        curr.next = prev
        prev = curr
        curr = nxt

    # 3. Compare halves
    first = head
    second = prev
    while second:
        if first.val != second.val:
            return False
        first = first.next
        second = second.next

    return True

In-Place Mutation and Production Restoration

Operating in O(1) space temporarily mutates the list's second half. In production environments, it is good practice to run the reverse function on the second half once more before returning to restore the list to its original state.

8. Problem 7: Rearrange / Reorder a Linked List

The Problem: Alternating First and Last Nodes

Given 1 → 2 → 3 → 4 → 5 → 6, reorder the list into 1 → 6 → 2 → 5 → 3 → 4. In words: take the first node, then the last, then the second, then the second-to-last, and keep alternating until the nodes run out.

The easiest way to see the pattern is to pair the nodes from the outside in:

PairFront nodeBack nodeOutput order
1st pair161, 6
2nd pair252, 5
3rd pair343, 4

Reading the output column top to bottom gives 1, 6, 2, 5, 3, 4. The front nodes are the first half read forward, and the back nodes are the second half read backward.

Two rules of the problem matter for everything below:

  • In place: we must change the next pointers of the existing nodes. We do not create new nodes, and we do not just overwrite values.
  • No return value: the function reorders the list starting from the same head node. Node 1 stays first, so head never changes.

Why Naive Traversal Becomes O(n²)

Because singly linked lists cannot jump to the tail, finding the last node repeatedly costs O(n) work per node, totaling O(n2).

Here is what that looks like on our 6-node list. To move the last node next to the first, we walk from the head to find the tail (5 hops) and its predecessor. Then the list is shorter, so the next round is a little cheaper, but still a long walk:

RoundWhat we doHops to reach the tail
1Walk from 1 to 6, detach it, insert it after 1 (list becomes 1, 6, 2, 3, 4, 5)5
2Walk from 2 to 5, detach it, insert it after 2 (list becomes 1, 6, 2, 5, 3, 4)3
3Walk from 3 to 4. It is already in place, so we are done1

Each round the walk is shorter by two hops, so the totals add up to 5 + 3 + 1 here, or roughly n + (n−2) + (n−4) + … in general, which is about n²/4. That is O(n2), and for a list of 100,000 nodes it means billions of pointer hops.

Two other tempting ideas have their own cost:

  • Copy every node into an array, then use two index pointers (front and back) to relink. This is O(n) time but needs O(n) extra memory.
  • Push the second half onto a stack. Popping a stack returns nodes in reverse order, which is what we want, but again it costs O(n) extra memory.

The three-phase approach below gets O(n) time and O(1) extra space. In effect, "reverse the second half" is a stack that lives inside the list itself.

The Key Insight: Three Problems We Already Know

The trick is to notice that the answer is built from tools we have already used in this guide:

  1. Find the middle (Problem 5): split the list into a front half 1 → 2 → 3 and a back half 4 → 5 → 6.
  2. Reverse the second half (Problem 6): 4 → 5 → 6 becomes 6 → 5 → 4.
  3. Weave the two halves together, taking one node from each in turn: 1 → 6 → 2 → 5 → 3 → 4.

Why reverse the second half? We want to visit the back nodes in the order 6, 5, 4. A singly linked list can only be walked forward, so the back half 4 → 5 → 6 gives us 4, 5, 6, which is the wrong order. After reversing, walking forward through 6 → 5 → 4 is exactly the same as walking the original list backward from the tail. Reversal is how we manufacture the missing "previous" pointers.

Use the stepper below to watch the three phases happen on the whole list. The sections after it zoom in on each phase with exact pointer values.

Phase 1 in Detail: Finding the Middle and Splitting

We use slow and fast exactly like Problem 5. The only decision is where fast starts, because it controls which node slow ends on when the length is even. In this solution we start with slow = head and fast = head.next. That makes slow stop on the last node of the first half, which is exactly the node we need to cut after.

Trace on 1 → 2 → 3 → 4 → 5 → 6:

StepslowfastLoop check: fast and fast.next

After round 1244 exists, 4.next = 5 exists: continue
After round 2366 exists, but 6.next is None: stop

slow ends on node 3. The first half is 1 → 2 → 3 and the second half starts at slow.next, which is node 4.

Now the odd case, 1 → 2 → 3 → 4 → 5:

StepslowfastLoop check
Start12continue

Here slow ends on the true middle node 3. The first half is 1 → 2 → 3 (the middle goes with the front) and the second half is 4 → 5. So the front half is either the same length as the back half (even case) or exactly one node longer (odd case). The weave step relies on that.

Quick rule: slow stops on the last node of the first half, so slow.next is always the head of the second half.

Phase 2 in Detail: Reversing the Second Half

Before reversing, we cut the list in two with slow.next = None. This line is easy to forget and it matters (see the pitfalls below). After the cut we have two independent lists: 1 → 2 → 3 → None and 4 → 5 → 6 → None.

Reversal uses three variables. curr is the node being processed, prev is the already-reversed part (it starts empty), and nxt remembers where to go next before we overwrite curr.next. Trace on 4 → 5 → 6:

Iterationcurr at startnxt = curr.nextThen curr.next = prevprev aftercurr after
1454 → None45

When curr becomes None, the loop ends and prev points at node 6. That is the head of the reversed half: 6 → 5 → 4 → None.

Why do we need nxt? The moment we write curr.next = prev, we lose the link to the rest of the original list. Saving it first is what keeps the walk going.

Phase 3 in Detail: Weaving the Two Halves

Now we hold two lists: first walks the front half 1 → 2 → 3 and second walks the reversed half 6 → 5 → 4. Each round does a "zipper" move: node from the front, then node from the back, then continue the front.

The four lines inside the loop must stay in this order:

  1. tmp1 = first.next and tmp2 = second.next: save both "rest of the list" links before we overwrite anything.
  2. first.next = second: the front node now points to the back node.
  3. second.next = tmp1: the back node now points to the next front node.
  4. first = tmp1 and second = tmp2: move both pointers forward using the saved links.

Trace on our example:

Roundfirst / secondSaved tmp1 / tmp2Links writtenList so far
11 / 62 / 51 → 6, 6 → 21 → 6 → 2 → 3
22 / 53 / 42 → 5, 5 → 31 → 6 → 2 → 5 → 3
33 / 4None / None3 → 4, 4 → None1 → 6 → 2 → 5 → 3 → 4

After round 3, second becomes None and the loop ends. The finished list is 1 → 6 → 2 → 5 → 3 → 4, as required.

Why while second and not while first? The second half is never longer than the first half, so it runs out first. If the original length is odd, the first half has one extra node. Trace 1 → 2 → 3 → 4 → 5, whose halves are 1 → 2 → 3 and the reversed 5 → 4:

Roundfirst / secondSaved tmp1 / tmp2Links writtenList so far
11 / 52 / 41 → 5, 5 → 21 → 5 → 2 → 3
22 / 43 / None2 → 4, 4 → 31 → 5 → 2 → 4 → 3

Now second is None, so we stop. Node 3 is the left-over middle node. It is already the tail because we cut its link earlier (3.next is None) and nothing points past it. The result is 1 → 5 → 2 → 4 → 3.

Common Mistakes

  • Forgetting slow.next = None. Without the cut, node 3 still points to node 4. In round 3 above, tmp1 = first.next would be node 4 instead of None, so the line second.next = tmp1 would make 4.next = 4, which is a self-loop. Any later traversal of the list would never end.
  • Overwriting before saving. If you write first.next = second before saving tmp1, the original link from the front half is gone and you can no longer continue along it.
  • Picking the wrong middle. If slow lands one node too far to the right on an even list, the second half is shorter than expected. The weave can still work, but your explanation of the halves will not match the code. Starting with fast = head.next removes that ambiguity.
  • Reversing before cutting. The reversal must happen on a detached second half. Reversing it while it is still attached to the first half creates tangled links.
  • Edge cases. A list with 0 or 1 nodes is already in order, which is why the function returns immediately at the top. A 2-node list also works: slow ends on node 1, the second half is node 2, and the weave produces 1 → 2 unchanged.

Complete Implementation

Python code (click to hide or show)
def reorder_list(head):
    if not head or not head.next:
        return

    # 1. Find the end of the first half.
    #    fast starts one step ahead so that slow stops on the
    #    LAST node of the first half (for both odd and even lengths).
    slow = head
    fast = head.next
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next

    # 2. Cut the list, then reverse the second half.
    prev = None
    curr = slow.next
    slow.next = None          # detach: first half now ends at slow
    while curr:
        nxt = curr.next       # remember the rest
        curr.next = prev      # flip the link
        prev = curr           # grow the reversed part
        curr = nxt            # move on
    # prev is now the head of the reversed second half

    # 3. Weave alternate links.
    first = head
    second = prev
    while second:
        tmp1 = first.next     # save both "rest of list" links first
        tmp2 = second.next
        first.next = second   # front -> back
        second.next = tmp1    # back -> next front
        first = tmp1
        second = tmp2

Complexity: finding the middle visits about n/2 nodes, reversing visits n/2 nodes, and weaving visits n/2 pairs. The total is O(n) time. We only use a few pointer variables, so extra space is O(1).

9. Problem 8: Cycle in a Circular Array

Array Traversal with Modulo Arithmetic

Suppose nums = [2, -1, 1, 2, 2]. Each value indicates jump distance (positive = forward, negative = backward). The array wraps around circularly: next_index = (i + nums[i]) % n.

This is the same "array as a graph" idea from Problem 4, with one difference. There, every value was already a valid index, so we jumped to nums[i]. Here the value is a distance, so we jump by nums[i] positions from where we are, and wrap around if we fall off either end.

Compute where every index sends us (here n = 5):

Index inums[i]Direction(i + nums[i]) % 5Next index
0+2forward2 % 52
1−1backward0 % 50
2+1forward3 % 53
3+2forward5 % 50 (wrapped around)
4+2forward6 % 51 (wrapped around)

Every index has exactly one outgoing arrow, so this is just a linked list in disguise: following the arrows from any start never gets stuck. It either ends in a loop or returns to where it started. That is why fast/slow pointers apply. Following the table from index 0 gives 0 → 2 → 3 → 0 → 2 → 3 → …, a loop of length 3.

A note on negative jumps. The wrap-around has to produce an index between 0 and n − 1. In Python, % already returns a non-negative result, so (0 + (−1)) % 5 = 4. In Java, C++ and JavaScript, -1 % 5 is -1, so you must write ((i + nums[i]) % n + n) % n.

Constraints: Direction Consistency & Self-Loop Rejection

Unlike normal cycle finding, a valid loop must fulfill two critical criteria:

  • Single Direction: The cycle must move exclusively forward or exclusively backward (no direction flips).
  • Cycle Length > 1: Single-element self-loops (nums[i] % n == 0) do not count.

Both rules add a reason for a walk to be rejected even when the graph does contain a cycle. Here is each one in a tiny example.

Rule 1: direction flips disqualify a cycle. Take nums = [1, -1] with n = 2. Index 0 jumps forward to index 1, and index 1 jumps backward to index 0. As a graph this is a cycle (0 → 1 → 0), but the cycle uses one forward jump and one backward jump, so it is not valid. If we start at index 0 (direction forward), the next step lands on index 1, whose value is negative. That does not match "forward", so the walk is rejected on the spot.

The check in code is nums[i] * direction > 0. A positive times positive is positive, and a negative times negative is positive, so a positive result means "this node moves the same way as the walk". A zero or negative result means the direction changed.

Rule 2: self-loops are not cycles. Take nums = [3, 1, 2] with n = 3. From index 0 we jump 3 positions and wrap around to (0 + 3) % 3 = 0: we land on ourselves. That is a loop of length 1, which the problem does not count. The code sees nxt == i and returns -1 (reject).

The same array shows a real cycle: from index 1, 1 → 2 (since 1 + 1 = 2), and 2 → 1 (since (2 + 2) % 3 = 1). That is a loop of length 2, all forward, so it is valid.

  • slow makes one jump per step, and fast makes two. Because the graph is a loop of length 3 here, fast gains one position on slow every round.

  • The collision at index 0 is the signal that a loop exists. The direction check has been happening silently at every jump (every node visited was positive).

The loop above only follows the starting index 0, which succeeds. The full algorithm tries every index as a start, because a bad start (one that walks into a dead end) does not rule out other starts. Here is what would happen for each start on this same array if the algorithm began there:

StartDirectionWhat happensResult
0forward0 → 2 → 3 → 0, all forward, slow and fast meetValid cycle found, return True
1backward1 → 0 is backward, but 0 holds +2 (forward), so fast is rejected on its second jumpDead end for this start
2forward2 → 3 → 0 → 2 …, all forwardValid cycle (same loop as start 0)
3forward3 → 0 → 2 → 3 …, all forwardValid cycle (same loop)
4forward4 → 1, but 1 holds −1 (backward), so the walk is rejectedDead end for this start

Starts 1 and 4 are dead ends, yet the answer is still True because other starts reach the loop. This is why the algorithm must keep trying new starting indices before it can answer False.

Reading the Code Line by Line

The implementation below has three layers. Here is what each layer is responsible for.

  1. The helper next_index(i, direction) performs one jump and decides whether it is allowed.
    • nums[i] * direction <= 0: the node at i moves opposite to the walk, so return -1 (direction mismatch).
    • nxt = (i + nums[i]) % n: compute the wrapped destination.
    • nxt == i: the jump lands on the same index, a self-loop, so return -1.
    • Otherwise return nxt. The value -1 is a sentinel meaning "this walk cannot be part of a valid cycle".
  2. The outer loop for i in range(n) tries every index as a start. The direction is fixed by the sign of nums[i] and stays the same for the whole walk. That is how "no direction flips" is enforced.
  3. The inner loop is Floyd's algorithm with a safety check after every single jump:
    • slow jumps once.
    • fast jumps twice, and we check -1 after each of the two jumps. A check only after the second jump would be wrong: the first jump might already be illegal, and the next call would then index nums[-1] (the last element, in Python) without any error.
    • slow == fast means the pointers collided inside a loop that used only legal jumps. Return True.
    • Any -1 breaks out of the inner loop. We abandon this start and try the next index.

If every start fails, the function returns False.

Full Implementation

Python code (click to hide or show)
def circular_array_loop(nums):
    n = len(nums)

    def next_index(i, direction):
        if nums[i] * direction <= 0:
            return -1  # Direction mismatch
        nxt = (i + nums[i]) % n
        return -1 if nxt == i else nxt  # Reject self-loops

    for i in range(n):
        direction = 1 if nums[i] > 0 else -1
        slow = i
        fast = i

        while True:
            slow = next_index(slow, direction)
            if slow == -1: break
            fast = next_index(fast, direction)
            if fast == -1: break
            fast = next_index(fast, direction)
            if fast == -1: break
            if slow == fast:
                return True

    return False

Complexity, Optimization and Common Mistakes

Complexity of the code above. Each walk from one start takes O(n) jumps, and there are n starts, so the worst case is O(n2) time with O(1) space. It is the simplest correct version and is usually fine for interview-sized inputs.

Getting to O(n). The waste is that a failed walk may re-walk nodes that earlier starts already proved to be dead ends. The fix is to erase the failed path: after a walk fails, set nums[j] = 0 for every node on it, and skip any start whose value is 0. A zero fails the nums[i] * direction > 0 test automatically, so later walks stop immediately when they touch an erased node. Each node is erased at most once, so the total work is O(n). The trade-off is that this version modifies the input array.

Optimized Python code (click to show)
def circular_array_loop_linear(nums):
    n = len(nums)

    def step(i, d):
        if nums[i] * d <= 0:
            return -1
        nxt = (i + nums[i]) % n
        return -1 if nxt == i else nxt

    for i in range(n):
        if nums[i] == 0:          # erased earlier: known dead end
            continue
        d = 1 if nums[i] > 0 else -1
        slow = fast = i

        while True:
            slow = step(slow, d)
            if slow == -1: break
            fast = step(fast, d)
            if fast == -1: break
            fast = step(fast, d)
            if fast == -1: break
            if slow == fast:
                return True

        # This start failed: erase its same-direction path.
        j = i
        while nums[j] * d > 0:
            nxt = (j + nums[j]) % n
            nums[j] = 0
            j = nxt

    return False

Common mistakes:

  • Using the wrong modulo for negatives in languages where % can return a negative number. Always normalize with ((x % n) + n) % n there.
  • Forgetting the self-loop check. An element like nums[i] = n or nums[i] = -n jumps a full lap back to itself. Without the check, slow and fast would collide immediately and you would return True for a non-cycle.
  • Checking only the direction of the start and not every node along the walk. The direction test must run on every jump, because a cycle can contain a backward node even if the start looks forward.
  • Treating a collision as enough. A collision proves that a loop exists in the graph. It only counts here because every jump that led to it passed the direction and self-loop checks.
