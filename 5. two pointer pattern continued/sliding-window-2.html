Sliding Window II: When the Window Is Controlled by a Constraint

In the previous article we met the simplest form of sliding window: a fixed-size window. We knew exactly how large it had to be, so each move was one element leaving on the left and one entering on the right, while we updated whatever we were tracking.

That was useful, but a little too convenient. Real problems rarely say "look at exactly 5 elements". They say things like find the longest substring with at most K distinct characters, or find the longest substring without repeating characters. Now there is a new question: how big should the window be? We do not know.

The window can be any size, as long as it satisfies the rule.

1. The window no longer has a fixed size

Consider "araaci" and the question: find the longest substring containing at most 2 distinct characters. What should the window size be? Could it be 2 ("ar")? 4 ("araa")? 5 ("araac")? It depends on what is inside the window.

First understand what "valid" means

The problem gives us a constraint: at most 2 distinct characters. So "ara" holds a and r, which is valid. "araa" still holds just a and r, so it is valid too. But "araac" holds a, r and c, which is three, so it is invalid.

The window now has a state: valid or invalid. A fixed-size window never needed that idea.

2. Grow, break, repair

The naive way

Generate every substring (a, ar, ara, araa, araac, ...) and count the distinct characters in each. But those substrings overlap heavily. "araa" and "araac" share almost their whole range, so we keep recounting things we already knew.

Let the window grow, then repair it

We want the longest valid window, so while the window is valid there is no reason to stop: expand. When a new character makes it invalid, we ask a better question than "start over":

Can I remove elements from the left until the window becomes valid again?

Step through it. The blue cells are the window, the yellow cell is the character just added, the grey cells are outside, and the green cells at the end are the best window found. L and R mark the two pointers.

Why shrink from the left?

Why not remove something from the middle, or the rightmost character? Because the window must stay contiguous. Removing the middle r leaves a hole, and we can no longer describe the range with just two boundaries.

If we only ever move left and right, the window stays contiguous automatically.

What do we need to know about the window?

For a sum problem we kept window_sum. Here we need to know how many times each character occurs inside the window. A frequency map gives that, and the number of distinct characters is just len(counts). Sliding window itself has not changed. Only the information we maintain about the window has.

How does K change the answer?

Drag the slider. The same string, with a looser rule, allows a longer window.

The complete algorithm

Python code (click to hide or show)
def longest_substring_k_distinct(s, k):
    left = 0
    counts = {}
    best = 0

    for right in range(len(s)):
        counts[s[right]] = counts.get(s[right], 0) + 1

        while len(counts) > k:
            char = s[left]
            counts[char] -= 1
            if counts[char] == 0:
                del counts[char]
            left += 1

        best = max(best, right - left + 1)

    return best

Do not memorize it. Read what each piece means. counts is "what is inside my window?". len(counts) > k is "have I violated the constraint?". left += 1 is "remove things from the left until the constraint is restored". right - left + 1 is "how large is my current valid window?".

The invariant

After the shrinking step finishes, the window [left, right] contains at most k distinct characters.

Adding a character may temporarily break the window. That is fine, because we repair it immediately. So at the moment we compute best, the window is guaranteed valid.

Now you drive

You decide at each moment whether to expand or shrink. Wrong moves get an explanation.

3. Why this is linear

The nested while inside the for looks quadratic, but it is not. right only moves forward, and left only moves forward. Each character enters the window once and leaves at most once; it never comes back. Together, the two pointers make at most 2n moves.

The frequency map holds at most K entries (or at most the number of distinct characters in the input), so the extra space is O(K), and O(n) in the worst case when K can grow with the input.

A nested while loop does not automatically make an algorithm quadratic. Count pointer movement, not loop depth.

A useful mental model is a rubber band stretched over the array. The right side keeps pulling it forward. If the rule is broken, the left side is pulled forward to repair it.

5. Remove K entirely: No-Repeat Substring

Find the longest substring without repeating characters. What makes a window valid? No character may appear more than once. So "abc" is valid, but "abca" is not, because a appears twice. The behaviour is identical: expand, detect a duplicate, shrink until valid.

The naive way to shrink: frequency counts

When we hit a duplicate we remove from the left one character at a time until the duplicate disappears. Simple, and easy to reason about. But we already know exactly which character caused the problem.

Key insight: remember where each character was last seen

If we maintain more information, can we make the update cheaper?

For a b c a, the previous a was at index 0. So the next valid window must start after it: left = 1. We can jump, not crawl. Compare both approaches side by side, then try the string abba, which has a trap in the jump version.

Left: frequency counts, shrink one at a time. Right: last-seen positions, jump left directly. On abba, notice that the second a was seen at index 0, but that is already outside the window, so left must not move backward. That is why the code uses max.

The complete algorithms

Python code (click to hide or show)
# Frequency counts
def longest_no_repeat_counts(s):
    left, best = 0, 0
    counts = {}
    for right, ch in enumerate(s):
        counts[ch] = counts.get(ch, 0) + 1
        while counts[ch] > 1:
            counts[s[left]] -= 1
            left += 1
        best = max(best, right - left + 1)
    return best

# Last-seen positions
def longest_no_repeat_last_seen(s):
    last = {}
    left, best = 0, 0
    for right, ch in enumerate(s):
        if ch in last:
            left = max(left, last[ch] + 1)   # never move left backward
        last[ch] = right
        best = max(best, right - left + 1)
    return best

Why not just pick the faster one?

Frequency countsLast-seen positions
TimeO(n)O(n)
Extra spaceO(distinct characters)O(distinct characters)
Movement of leftone step at a timedirect jump
Reasoningsame loop shape as every other window problemneeds the max guard; easy to get wrong

Both are linear. The jump version stores more state to move the boundary more directly, but it asks you to reason about a subtle edge case. Neither is universally better, and the lesson is the tradeoff, not a canonical template.

6. Longest versus smallest

This distinction changes the behaviour of the whole algorithm. Pick a tab.

Here is the smallest case in action: the smallest subarray with sum at least a target, from the previous article. Notice how it shrinks while the window is still valid, the opposite of what we did above.

Python code (click to hide or show)
def smallest_subarray_sum(nums, target):
    left, total = 0, 0
    best = float("inf")
    for right in range(len(nums)):
        total += nums[right]
        while total >= target:            # shrink while VALID
            best = min(best, right - left + 1)
            total -= nums[left]
            left += 1
    return 0 if best == float("inf") else best

Longest: expand aggressively, shrink only when forced. Smallest: expand until valid, shrink aggressively while valid.

7. When does this actually work?

Not every substring problem can be solved by blindly doing right += 1 and while invalid: left += 1. The crucial question is whether moving left monotonically repairs the violation.

The pattern works because of the properties of the problem, not because we memorized a loop.

9. The bigger pattern

In the first article the reasoning was: the next window overlaps with the previous one, so do not recalculate everything. Now we have added a layer: the window has no predetermined size, so let its boundaries move according to a validity condition.

The tradeoff is the same one that appears all over algorithm design:

more maintained state
↓
less recomputation
↓
faster algorithm

We spend a little memory on a frequency map to avoid asking "what is inside this substring?" from scratch every time.

Can this window satisfy the constraint, and what is the cheapest state that lets me check?

10. A useful way to recognize these problems

When you see a new subarray or substring problem, do not ask "which template is this?". Ask these instead.

  1. Is the thing we look at contiguous? If yes, a window may make sense.
  2. What makes a window valid? Write it in plain English, such as "at most 2 distinct characters".
  3. What information do I need to maintain? A sum, a frequency map, last-seen positions, a count of zeroes.
  4. If I expand, what changes? A new element enters, so update the state.
  5. If the window becomes invalid, how can I repair it? Usually move left forward while updating the state.
  6. Longest or shortest? That decides when shrinking happens.

What comes next

The next problems make the constraint itself more interesting. In longest substring with at most K replacements to make all characters the same, "distinct characters" is no longer enough: we need the most frequent character in the window and how many replacements the rest would cost. In longest run of 1s after flipping at most K zeroes, the state becomes the number of zeroes in the window.

The window itself is no longer the difficult part. Designing the right state and the right validity condition is.
