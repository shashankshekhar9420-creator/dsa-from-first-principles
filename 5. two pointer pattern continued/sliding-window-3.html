Sliding Window III: The State Inside the Window

By now, sliding window itself should no longer feel mysterious. We have a range [left ... right]. We move right to expand it, and when the window violates a condition we move left to shrink it. The hard part is no longer how to move two pointers. The harder question is what exactly we need to remember about everything inside the window.

The window is just the container. The state tells us what is happening inside it.

This post is about designing that state, from a derived value like "most frequent letter" to a whole contract of required counts. Every problem has a stepper, there are sliders and a "you drive it" widget, and the code can be hidden with the button at the top.

1. The window is only half the algorithm

Given a string of uppercase letters, find the length of the longest substring that can be made to contain only one distinct letter after replacing at most k characters. Take A A B A C A with k = 2. Could we turn the whole string into one letter? The counts are A: 4, B: 1, C: 1. Keep A, replace B and C: 2 replacements. Valid.

But how did we know? Window length was not enough, and neither was the number of distinct characters. We needed the frequency of each character, and specifically the frequency of the most common one.

The naive way

Try making everything A and count the replacements. Try B and count again. Try C. Take the best. Pick a letter below to see the cost of keeping it.

Key insight: keep the most frequent letter

We never need to try every letter. The letter that already appears most is the one that minimizes replacements, so:

replacements needed = window length − frequency of the most common character

The window is valid when that number is at most k. With k = 2, the window A A B A C A costs 6 − 4 = 2, valid. Add a D and it costs 7 − 4 = 3, invalid.

The sliding-window machinery stayed the same. Only the definition of valid became more sophisticated.

2. Character Replacement: validity from derived state

Our window now needs the frequency of every character and a max_frequency. Each time we expand we update the count and the max, then derive validity from window_length - max_frequency. Step through it. Blue is the window, yellow is what was just added, green is the best window at the end.

The complete algorithm

Python code (click to hide or show)
def character_replacement(s, k):
    left = 0
    counts = {}
    max_frequency = 0
    best = 0

    for right in range(len(s)):
        char = s[right]
        counts[char] = counts.get(char, 0) + 1
        max_frequency = max(max_frequency, counts[char])

        while (right - left + 1) - max_frequency > k:
            counts[s[left]] -= 1
            left += 1

        best = max(best, right - left + 1)

    return best

Do not memorize it. Understand this line: (right - left + 1) - max_frequency says "if I keep the most frequent character and change everything else, how many replacements do I need?". If that exceeds k, the window is too large, so we shrink it.

3. Why don't we decrease max_frequency?

Look back at the stepper: when we remove a letter from the left, the stored max_frequency can become larger than the true maximum in the window. Suppose the window is A A A B (max 3) and we remove an A. The real maximum is now 2, but we leave the stored value at 3. It looks wrong.

Why it is safe

Think about what the stored value means: it is the best frequency we have seen in any window so far, a high-water mark. The window can never need to be longer than record + k, and the answer only grows when a new record is set by a real window. A stale value cannot invent a longer answer; it only stops us from shrinking more than needed. Compare the stale version against the exact one that recomputes the true maximum every time:

We may keep a value that is no longer the exact maximum of the current window, but this does not make us miss a longer valid answer.

The tradeoff: exact versus useful state

For an alphabet of 26 letters we could simply rescan the frequency table whenever we need the true maximum. That is simple and exact. Or we can maintain max_frequency incrementally, which keeps the validity check trivial.

Exact max (rescan)Stored max (stale)
TimeO(n · alphabet)O(n)
Extra spaceO(alphabet)O(alphabet)
Reasoningobviously correctneeds the high-water-mark argument

Sometimes an algorithm maintains an exact state, and sometimes a carefully chosen useful approximation. Both are fine if we understand what the state is used for. This is the same principle as old_sum - leaving + entering from the first article, applied to frequencies.

4. Ones after Replacement: a much simpler state

Given a binary array, find the longest contiguous subarray of 1s after replacing at most k zeroes. For 1 1 0 0 1 1 1 0 with k = 2, the window 1 1 0 0 1 1 1 has two zeroes, so it can become all ones. Add the final 0 and there are three zeroes, which is one too many.

What state do we need? Just number_of_zeroes, and validity is zeroes <= k. Step through it, then try driving it yourself.

Python code (click to hide or show)
def longest_ones_after_replacement(nums, k):
    left = 0
    zeroes = 0
    best = 0

    for right in range(len(nums)):
        if nums[right] == 0:
            zeroes += 1

        while zeroes > k:
            if nums[left] == 0:
                zeroes -= 1
            left += 1

        best = max(best, right - left + 1)

    return best

The window mechanics are almost identical to character replacement. The state is different: a frequency map plus max frequency for one, a single zero count for the other.

Sliding window is not about a particular data structure. It is about maintaining enough state to describe the current window.

6. Matching: Permutation and Anagrams

So far we asked how long a valid window can become. Sliding window can also match. Given s1 = "ab" and s2 = "eidbaooo", does s2 contain a permutation of s1? "ba" does, so the answer is True.

The naive way

Sort every window and compare it with the sorted target. It works, but overlapping windows repeat the sorting work.

Key insight: fixed length, so a fixed window

Every permutation of "ab" has length 2, so we only look at windows of size 2. This is the fixed-size window from the first article, but the question is no longer a sum. It is whether the window has exactly the same character counts as the target.

When order does not matter, frequency information may be the right state.

The same idea solves String Anagrams (find all start positions), just collecting every match instead of stopping at the first. Pick a case:

Python code (click to hide or show)
from collections import Counter

def check_inclusion(s1, s2):
    need = Counter(s1)
    window = Counter()
    m = len(s1)

    for right, ch in enumerate(s2):
        window[ch] += 1
        if right >= m:
            out = s2[right - m]
            window[out] -= 1
            if window[out] == 0:
                del window[out]
        if window == need:
            return True
    return False

8. Minimum Window Substring: the state becomes a contract

Given a string s and a pattern t, find the smallest substring of s containing every character of t with the required frequency. For s = "ADOBECODEBANC" and t = "ABC" the answer is "BANC". We want the smallest valid window, so once valid we shrink aggressively.

Distinct characters are not required frequencies

If the target is AABC, it is not enough that A, B, C exist. We need A → 2, B → 1, C → 1. So A B C is not enough, but A A B C is.

Distinct characters are not the same thing as required frequencies.

Think of the target as a contract

The target is a contract: need says how many of each letter. As the window grows we gradually satisfy clauses. Instead of re-comparing everything, we keep a single number: how many clauses are satisfied. When it equals the number of clauses, the window is valid, and we shrink until a removal breaks a clause.

Python code (click to hide or show)
from collections import Counter

def min_window(s, t):
    need = Counter(t)
    have = {}
    required, formed = len(need), 0
    left = 0
    best = (float("inf"), 0, 0)

    for right, ch in enumerate(s):
        have[ch] = have.get(ch, 0) + 1
        if ch in need and have[ch] == need[ch]:
            formed += 1

        while formed == required:
            if right - left + 1 < best[0]:
                best = (right - left + 1, left, right)
            out = s[left]
            have[out] -= 1
            if out in need and have[out] < need[out]:
                formed -= 1
            left += 1

    return "" if best[0] == float("inf") else s[best[1]:best[2] + 1]

The key state is formed, a derived number: "how many requirements are satisfied". We do not keep what describes the window perfectly. We keep the cheapest information that lets us decide validity.

10. Product Less Than a Target: counting from a valid window

Count all contiguous subarrays whose product is less than target (positive numbers). The state is window_product: multiply on expand, divide on shrink. Here is the subtle insight. If [left ... right] is valid, then every subarray ending at right and starting anywhere from left to right is also valid. So we add right - left + 1 at once, instead of counting them one by one.

Change the target and check that the shortcut agrees with brute force on [10, 5, 2, 6]:

Python code (click to hide or show)
def num_subarray_product_less_than_k(nums, k):
    if k <= 1:
        return 0
    left, prod, count = 0, 1, 0
    for right, x in enumerate(nums):
        prod *= x
        while prod >= k:
            prod //= nums[left]
            left += 1
        count += right - left + 1
    return count

This is another example of extracting more information from the current valid window than just its length.

12. The bigger pattern

Sliding window is fast because it refuses to solve overlapping ranges from scratch. It removes what left, adds what entered, updates state, and checks validity. The window moves monotonically, so even complicated problems stay linear, provided the state updates and validity checks are cheap. The sophistication is not in the number of operations. It is in choosing the right state.

Don't memorize the sliding-window template. Learn to design the window's state.

One final caution

Sliding window works because the boundaries move in one direction and we can reason about what happens to validity when they move. Positive sums grow when we expand and shrink when we contract; frequencies rise and fall predictably. Ask one more question before reaching for the technique:

If I move the left or right boundary, can I predict how the validity of the window changes?

If yes, sliding window may be a natural fit. If not, do not force it.

13. A useful way to recognize these problems

When you see a new problem, follow the reasoning path. The code comes afterward.

  1. What ranges would I examine by brute force? These are the overlapping ranges.
  2. What information would I repeatedly recalculate? That is your candidate state.
  3. Can I maintain it as the window moves? Incrementally, on every expand and shrink.
  4. What makes the current window valid? Write it in plain English, then derive it from the state.
  5. When should I expand, and when should I shrink? Longest and smallest differ here.
  6. What am I optimizing or counting? Longest, smallest, number of valid subarrays, existence, or all start positions.
  7. Is the validity predictable when a boundary moves? If not, do not force a window.

Notice how many different-looking problems collapse into the same small set of ideas. We started with a contiguous range and the wish not to recalculate overlapping ranges. Then the range became a window that expands and shrinks. Then the window gained state and a constraint. The window is the container, the state tells us what is happening inside it, the constraint says whether it is acceptable, and the objective says whether we want it larger, smaller, or counted.

Sliding window stops being a pattern you memorize and becomes a way of thinking about overlapping contiguous ranges.
