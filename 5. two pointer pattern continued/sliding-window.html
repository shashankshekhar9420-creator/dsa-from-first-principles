Sliding Window: From Recomputing Everything to Maintaining a Window

We have already seen the two-pointer idea. Two pointers are useful when we are trying to reason about a range inside an array or string without blindly checking every possible pair of positions.

But there is another very common situation:

What if the thing we care about is not two individual elements, but an entire contiguous range?

For example: [2, 1, 5, 1, 3, 2]

Suppose we ask:

What is the maximum sum of any 3 consecutive elements?

The ranges we care about are:

[2, 1, 5] → 8
[1, 5, 1] → 7
[5, 1, 3] → 9
[1, 3, 2] → 6

The answer is 9. At first, this looks simple enough. But the interesting question is not:

How do we calculate these sums?

It is:

Do we really need to calculate each sum from scratch?

That question leads us to the sliding window. Each problem below has a stepper, and the code can be hidden with the button at the top.

1. Start with the obvious solution

We need every group of k consecutive elements. For [2, 1, 5, 1, 3, 2] with k = 3, we could simply take every group and add its elements.

Python code (click to hide or show)
def max_sum_subarray(arr, k):
    best = float("-inf")

    for i in range(len(arr) - k + 1):
        current = sum(arr[i:i + k])
        best = max(best, current)

    return best

Conceptually:

There is nothing wrong with this approach. But look carefully at what happens when the window moves. From [2, 1, 5] to [1, 5, 1] we didn't get a completely new collection of elements. We already know 1 + 5 was part of the previous calculation.

The only things that changed were:

  • 2 left the window
  • 1 entered the window

So instead of throwing away the previous sum and calculating everything again, why not update the existing sum? That is the first important idea.

2. Don't recalculate what you already know

Suppose our current window is [2, 1, 5]. Its sum is 8. Now move the window one position to the right:

The new window is [1, 5, 1]. Instead of doing 1 + 5 + 1 we can say:

old sum
- element that left
+ element that entered

So: 8 - 2 + 1 = 7

The next movement, [1, 5, 1] ↓ [5, 1, 3], becomes 7 - 1 + 3 = 9

And again, [5, 1, 3] ↓ [1, 3, 2], becomes 9 - 5 + 2 = 6

We are no longer repeatedly calculating the contents of the window. We are maintaining the state of the window. That is the fundamental idea behind sliding window.

3. What exactly is the "window"?

A window is simply a range of contiguous elements that we are currently looking at. For example:

The window has:

  • a left boundary
  • a right boundary

We can represent them with two indices, left and right, as the labels above the cells show. The elements between them are our current window.

The important part is that the window moves. We don't create a completely new window every time. We move the boundaries and update whatever information we care about.

For a sum problem, that information is window_sum. For other problems, it might eventually become:

  • frequency of characters
  • number of distinct elements
  • number of zeroes
  • number of elements satisfying some condition
  • ...

This is why the name is useful:

We keep a window over the data and slide it while maintaining information about what is inside.

4. The fixed-size window

The first kind of sliding window we should learn is the easiest:

The window always has the same size.

If k = 3, then the window must always contain exactly three elements. So:

[2, 1, 5, 1, 3, 2]

[2, 1, 5]
   ↓
[1, 5, 1]
   ↓
[5, 1, 3]
   ↓
[1, 3, 2]

The window doesn't grow or shrink. It simply moves. This gives us a very clean algorithm.

Step 1

Build the first window, [2, 1, 5]. Calculate its sum: 8

Step 2

Move the window one position. Remove the element leaving: -2. Add the new element entering: +1. New sum: 7

Step 3

Repeat. 7 - 1 + 3 = 9

Step 4

Repeat again. 9 - 5 + 2 = 6

Keep the largest sum seen.

5. The Python solution

Python code (click to hide or show)
def max_sum_subarray(arr, k):
    window_sum = sum(arr[:k])
    best = window_sum

    for right in range(k, len(arr)):
        window_sum += arr[right]
        window_sum -= arr[right - k]

        best = max(best, window_sum)

    return best

There is a useful invariant hiding inside this code:

window_sum always represents the sum of the current window of size k.

That is the key idea. Not the loop. Not the syntax. The invariant. At every iteration, window_sum is the sum of exactly k elements.

6. Why is this better?

The naive approach repeatedly adds all k elements. If there are many windows, we repeatedly do work that we have already done.

The sliding-window approach does something different. For every movement, it performs only two updates: remove one, add one.

So instead of thinking:

"Calculate the next subarray."

we think:

"I already know almost everything about the next subarray. What changed?"

That shift in thinking is much more important than this particular problem. Drag the window size to see how the work compares on an array of 1,000 numbers:

Why not the simpler approach?

Recompute each windowPrefix sumsSliding window
TimeO(n · k)O(n)O(n)
Extra spaceO(1)O(n)O(1)
ReasoningObvious and always correct, but repeats workWindow sum is P[i+k] − P[i]; stores every prefixKeeps one number and updates it

Prefix sums are also a good answer here. The sliding window wins on memory, and it grows into problems prefix sums handle less naturally. It also leans on the fact that a sum can be undone by subtracting.

7. A visual way to think about it

Imagine physically moving a window across the array.

Notice something important. The window is not jumping from one unrelated group to another. It overlaps heavily with the previous window. That overlap is the entire reason sliding window works so well here.

8. The deeper pattern: overlapping subproblems

This is the question worth carrying forward:

When consecutive ranges overlap heavily, am I recalculating information that I already have?

For [2, 1, 5] and [1, 5, 1], two out of three elements are the same. Why would we calculate those two elements again? We don't. We preserve what we already know and update only what changed.

This is the intuition behind the entire sliding-window family.

9. But fixed-size windows are almost too easy

So far, the window size was given to us, k = 3. That makes life convenient. We always know exactly when the window is valid.

But what happens when the problem says something like:

Find the smallest contiguous subarray whose sum is at least 7.

Now there is no k. We don't know how large the window should be. That changes everything.

Consider [2, 1, 5, 2, 3, 2]. We want the smallest contiguous range whose sum is at least 7. Possible ranges include:

The answer is [5, 2] with length 2.

But now the window cannot simply move one element at a time while staying the same size. We need to figure out:

When should the window grow?
and:
When should the window shrink?

This is where sliding window becomes much more interesting.

10. Let the window grow

Start with an empty window.

We move the right boundary forward and add elements.

Add 2: [2], sum = 2. Not enough. Keep expanding.

Add 1: [2, 1], sum = 3. Still not enough.

Add 5: [2, 1, 5], sum = 8. Now sum >= 7. The window is valid.

But are we done? No. We want the smallest valid window. And our current window has length 3. Maybe we can remove something from the left and still remain valid.

11. Now shrink the window

Current:

Remove the leftmost 2: [1, 5], sum = 6. Now the sum is too small. So [1, 5] is invalid. We must stop shrinking.

Our best valid window so far is [2, 1, 5], length 3.

Now expand again. Add 2: [1, 5, 2], sum = 8. Valid again. Can we shrink?

Remove 1: [5, 2], sum = 7. Still valid. This is important. We found [5, 2], length 2. Can we shrink again?

Remove 5: [2], sum = 2. Invalid. So we stop. Our best answer is now length 2.

12. The window now has two jobs

This is the key transition from fixed-size to variable-size sliding windows. The window can now:

Expand when the current window doesn't satisfy the requirement: invalid ↓ expand right

Shrink when the current window satisfies the requirement and we want to improve it: valid ↓ shrink left

So the window behaves almost like a controlled search:

This expand/shrink behavior is the heart of the next level of sliding window problems.

13. Why are we allowed to shrink greedily?

This deserves attention because otherwise the algorithm can feel like a trick. We are solving:

Find the smallest subarray whose sum is at least 7.

Suppose [2, 1, 5], sum = 8. The window is valid. If we want the smallest valid window, keeping the 2 on the left cannot make the window better. So we try removing it.

If the resulting window is still valid... [1, 5], sum = 6. Oops. It isn't. Therefore we know:

Removing 2 made the window invalid.

So there cannot be a smaller valid window obtained by removing even more from this particular left side. We stop. Then we move the right side forward and continue searching.

The important property here is that the array contains positive numbers. If all numbers are positive:

  • expanding the window can only increase the sum
  • shrinking the window can only decrease the sum

That monotonic behavior gives us permission to make these local decisions. This is a very important tradeoff to understand.

Here is what that permission looks like in a snapshot: everything grey on the left is finished, because for each start we have dropped, its shortest valid window has already been recorded.

Now you drive it

At every moment there is one decision: expand, shrink, or stop. Look at the sum and decide.

14. The variable-size solution

Python code (click to hide or show)
def min_subarray_len(target, arr):
    left = 0
    window_sum = 0
    best = float("inf")

    for right in range(len(arr)):
        window_sum += arr[right]

        while window_sum >= target:
            best = min(best, right - left + 1)

            window_sum -= arr[left]
            left += 1

    return 0 if best == float("inf") else best

window_sum represents the sum of all elements between left and right.

15. Notice something subtle

Look at the nested while loop. At first glance, someone might think:

"There's a for loop and a while loop inside it. Isn't that quadratic?"

This is where understanding the movement of the pointers matters more than staring at the nesting. right only moves forward. left also only moves forward. Neither pointer ever goes backward.

Across the entire algorithm:

right:  0 → 1 → 2 → 3 → ... → n

left:   0 → 1 → 2 → 3 → ... → n

Each element can enter the window once and leave the window once. So although the while loop is nested syntactically, the total pointer movement is still linear.

The important mental model is:

Don't count loops blindly. Count how many times the pointers can actually move.

16. Fixed window vs variable window

We now have two versions of the same broader idea.

Fixed-size window

The size is known, window size = k. We add the incoming element and remove the outgoing element. Example:

Maximum sum of a subarray of size K.

Variable-size window

The size is determined by a condition. We expand until valid, then shrink while valid. Example:

Smallest subarray whose sum is at least target.

The difference is small syntactically. Conceptually, it is important.

17. The real abstraction

It is tempting to memorize:

for right in range(...):
    ...

and:

while condition:
    ...

But that isn't the useful part. Instead, think:

Fixed window

"I know exactly how big my range should be. I just need to move it efficiently."

Variable window

"I don't know how big the range should be. I need to adjust its size according to a condition."

And both rely on the same underlying observation:

The next window overlaps heavily with the current window, so preserve what you already know instead of starting from scratch.

18. When does this approach actually make sense?

Sliding window is not magic. We shouldn't see a contiguous array and automatically write two pointers. The better question is:

Does the problem repeatedly ask about contiguous ranges, and can I maintain the relevant information when the range moves?

For example, these are strong signals:

  • subarray
  • substring
  • contiguous range
  • consecutive elements

Then ask:

  1. What information does the window need? For the first problem: sum. For the second: sum. Later it might be: frequency map, number of distinct characters, number of zeroes, required character counts, ...
  2. What makes the window valid? For example: window has exactly K elements, or window_sum >= target. Later: at most K distinct characters, or no character appears twice.
  3. What happens when we expand? Does the window become more or less valid?
  4. What happens when we shrink? Does the constraint move in the direction we need?

These questions will become much more important as the problems get harder.

19. A limitation we should not ignore

The variable-size minimum-subarray solution above relies on positive numbers. Consider [2, -10, 10, 5].

Now removing an element from the left does not necessarily behave in the simple way we relied upon. With positive numbers: expand → sum increases, shrink → sum decreases. With negative numbers, that relationship disappears.

For example, [2, -10] has sum = -8. Remove 2 and [-10] has sum = -10. But other arrangements can make shrinking or expanding behave unexpectedly. Here are two of them, run through the same algorithm with target 10 and target 8, next to the true answer:

This matters because sliding window is not merely:

"Use two pointers on a subarray."

There needs to be some structure that makes moving the boundaries useful and safe. Understanding why the movement works is more valuable than memorizing the pattern.

Why not the simpler approach?

Try every startSliding window
TimeO(n2)O(n)
Extra spaceO(1)O(1)
ReasoningMakes no assumption about the valuesRelies on positive numbers: expanding raises the sum, shrinking lowers it

Trying every start (nested loops, stopping at the first valid end) stays correct with negative numbers. The sliding window is faster only because the problem gives its movement a direction. We choose by the constraints we have.

20. Two problems, one idea

Let's put the two problems side by side.

The second problem didn't require learning an entirely new pattern. It emerged naturally from the first.

The fixed window taught us:

Maintain a contiguous range instead of recomputing it.

The variable window adds:

Let the boundaries move independently according to the condition.

That is the real progression.

21. What we should carry forward

At this point, don't memorize a "sliding window template." Instead, remember these ideas:

1. A window is just a contiguous range

[left ........ right] Nothing more mysterious than that.

2. Consecutive windows overlap

That overlap is useful. Instead of recomputing everything:

3. Fixed windows have a predetermined size

size = K So the window simply slides.

4. Variable windows are controlled by a condition

We may expand → make the window larger or shrink → make the window smaller.

5. The window should maintain some state

For these problems: window_sum. Later: counts, distinct elements, frequency maps, number of replacements, ...

6. The most important question is "what changed?"

When the window moves:

What entered?

What left?

What information became different?

That question is often enough to turn an apparently expensive solution into a linear one.

22. Where this gets interesting

So far, our window has been tracking something very simple: sum. But imagine the following problem:

Find the longest substring containing at most 2 distinct characters.

Now the window isn't controlled by a fixed size. And we aren't tracking just a sum. We need to know:

  • Which characters are inside?
  • How many times does each occur?
  • Is the window still valid?
  • If not, how far should the left side move?

Or:

Find the longest substring without repeating characters.

Now the window needs to know whether a character has appeared before.

Or:

Find the longest substring where we can replace at most k characters to make all characters the same.

Now the window needs even more information. The window itself hasn't fundamentally changed. What changes is:

the state we maintain and the condition that determines whether the window is valid.

That is where sliding window stops feeling like a simple optimization and starts becoming a general way of reasoning about contiguous ranges. And that is what we'll build toward next.
