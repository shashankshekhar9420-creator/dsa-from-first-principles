Substring with Concatenation of All Words: Why We Slide by a Whole Word

In the last post (Find All Anagrams) we kept a window of letters and moved it one step at a time, updating counts instead of recounting. Now the letters become words. Same window, same counts, one new trap: where does a word start?

Treat every word as one big letter, then slide a window of whole words.

1. The problem and the slow way

You get a string s and a list of words, all the same length. Find every index where s contains all the words glued together, each used exactly once, in any order. Example: s = "barfoothefoobarman", words = ["foo","bar"]. The answer is [0, 9] because barfoo starts at 0 and foobar starts at 9.

The naive way

Try every start index. At each one, cut the next m*w characters into m chunks of length w, count them, compare with the word counts. Why is this wasteful? Start 0 and start 3 cut out almost the same chunks, yet we cut and count everything again. Work is thrown away every step.

Cost: about n starts, times m chunks, times w letters per chunk = n·m·w.

2. Words are just big letters

Suppose every word had length 1. Then words = ["a","b"] asks: is there a window of 2 letters with the same counts? That is exactly the anagram problem. So a longer word is only a letter that takes w characters of space. Drag the slider: the string is cut into chunks of length w, and each chunk is one "big letter".

Good news: if we know where the chunks begin, we already know how to do this. The only open question is where chunks begin.

3. Why slide by a whole word, not one character?

It feels natural: a new character arrives, so a new word appears, so slide by 1. Test that idea. Our window holds 2 words (6 characters). Slide it right by d characters and see how many chunks you can reuse. Blue = chunk was in the old window at the same place. Yellow = brand new, must be read again.

Try d = 1: every chunk is different (arf, oot). The old counts say nothing about them, so we must rebuild the whole window. That is the slow way again. Now try d = 3: one chunk is kept, only one is new. Why? Chunk borders only line up with the old ones when we move by exactly w.

Sliding by 1 character changes every chunk. Sliding by w changes one chunk. Only the second lets us update counts in O(1).

But we skip start positions!

Sliding by w from index 0 only visits 0, 3, 6, ... What about start 1 or 2? The answer might begin there ("xbarfoo" answers at 1). Fix: run the whole thing w times, once per offset 0, 1, ..., w-1. Each offset is its own chain of aligned chunks. Together the chains cover every start index exactly once, so nothing is missed.

4. One window per offset: step it, then drive it

For one offset, chunk the string and move a window over the chunks. For each new chunk there are only 3 cases:

  1. Not one of our words. No window containing it can ever work, so empty the window and restart right after it.
  2. A word we already have enough of. Adding it gives too many. Drop words from the left until there is room. Why left? The window must stay a contiguous run.
  3. Fine. Add it. If the window now holds all m words, record its left index, then drop one word from the left so we keep sliding.

Pick a preset and press Next. Green = in window, yellow = current chunk, grey = left behind. Numbers under chunks are real string indices. Notice offsets 1 and 2 of the first example find nothing: their chunks are never words.

Now you drive

Same algorithm, you choose the move. Wrong moves explain themselves. The duplicates preset has good twice in the list, which forces the "too many" case.

The complete algorithm

Python code (click to hide or show)
def findSubstring(self, s, words):
    w, k = len(words[0]), len(words)
    if len(s) < w * k:
        return []
    target = {}
    for x in words:
        target[x] = target.get(x, 0) + 1

    res = []
    for off in range(w):              # one chain per offset
        left, count, window = off, 0, {}
        for right in range(off, len(s) - w + 1, w):
            sub = s[right:right + w]
            if sub not in target:     # case 1: reset
                window.clear(); count = 0; left = right + w
                continue
            while window.get(sub, 0) == target[sub]:   # case 2: shrink
                old = s[left:left + w]
                window[old] -= 1; count -= 1; left += w
            window[sub] = window.get(sub, 0) + 1       # case 3: add
            count += 1
            if count == k:
                res.append(left)
                old = s[left:left + w]
                window[old] -= 1; count -= 1; left += w
    return res

How much faster, really?

Drag the number of words m. Naive work grows with it. Sliding work does not, because each step touches one chunk. (Here n = 100,000 and w = 5.)

NaiveSliding per offset
TimeO(n·m·w)O(n·w)
Extra spaceO(m·w)O(m·w)
ReasoningRecount every startChange one chunk per step

Honest trade-off: for tiny inputs the naive version is simpler and fast enough. Sliding wins when m or n is big. Note the w factor stays: comparing and hashing a chunk costs w characters.

6. The bigger pattern

A sliding window works when the thing you track can be updated by adding one item and removing one item. The hard part is choosing the right item and the right step size.

What is one unit here, and how far must I move so exactly one unit leaves and one enters?

7. A useful way to recognize these problems

  1. Is the window length fixed? Here it is m·w.
  2. Does order inside the window not matter? Then counts are enough.
  3. Are items bigger than a character? Then check alignment, and loop over offsets.
