Linked Lists: Understanding Why They Exist

If you learned arrays first, you probably came away with a very convenient mental model:

“I have a collection of things, and I can get any element whenever I want.”

Want C in [A, B, C, D, E]? Go to index 2. Want E? Index 4. Want to insert something? Well… that’s where things become interesting. Arrays are extremely good at one thing: putting things in known positions. But that strength comes with a constraint: the elements live next to each other, and once we change the collection frequently, that constraint starts fighting us.

This is where the idea of a linked list begins. Not with pointers, not with nodes, not with a class definition. With a problem. Every figure below is a stepper or a control you can drive, and code can be hidden with the button at the top.

1. The problem with our beautiful array

The elements of an array occupy consecutive positions in memory. If each element takes the same amount of space, finding element i is arithmetic:

address = starting_address + i × element_size

That is why arr[3] is so fast. We don’t look at A, B or C; we jump straight to index 3. Arrays are position-oriented: the position itself tells us where the element is.

But now let’s insert something

Suppose we want X between B and C. The logical operation sounds trivial: “put X between B and C.” Physically there is a problem: there was no empty space between them, so we need to make room. E moves, D moves, C moves, and then X can occupy the newly created space. The important thing is not that insertion takes O(n). The important thing is why:

The array’s elements are tied to their physical positions. Insert in the middle, and everything after it has to move.

Try it: insert X into an array

Pick an insertion index and step through. Blue cells are elements that physically moved. The small labels above the cells are memory addresses (4 bytes per element). Turn the toggle off to hide them and see only the logical picture.

Compare index 5 (nothing after it, nothing moves) with index 0 (everything moves). The cost is not an arbitrary rule about arrays. It is the number of elements that sit after the insertion point.

2. What if elements didn’t have to be neighbours?

This question gives birth to the linked list. Imagine memory like this: A at address 1000, B at 2500, C at 1370, D at 4200, E at 1800. These objects are nowhere near each other. If we don’t know where B is, how does A find it? Here is the idea:

Let A remember where B is.

Instead of storing only A, we store A + location of B. And B stores B + location of C, and so on. Now the nodes don’t need to live beside each other. They only need to know where the next node is.

A new way of organizing data

An array says: “My elements are next to each other. Their positions tell you where they are.” A linked list says: “My elements can be anywhere. Each element tells you where the next one is.” The arrow is not just a visual convention. It is an actual relationship: A.next = B, B.next = C, C.next = D, D.next = None.

What is a node?

Each piece of a linked list is a node. It holds two things: the value (left part of the box below) and a reference to the next node (the dot on the right).

So a linked list is not fundamentally “a bunch of nodes.” It is more accurately a chain of nodes connected through references. That distinction becomes important later.

The head

If the nodes are scattered around memory, how do we find the first one? We keep one reference, head, which says “this is where the list begins.” We don’t need to know where B, C or D are. We only need to know where A is. Then A tells us where B is, and B tells us where C is.

3. The first big tradeoff

We’ve solved one problem, but we’ve created another. With an array we can say “give me element 3” and the computer calculates where it is. With a linked list we have no address formula. We have to follow the chain, and if we want the 1000th element we may have to visit all 1000 nodes. This gives us our first fundamental tradeoff:

Arrays make positions cheap. Linked lists make relationships cheap.

Array: “Where is the 500th thing?” Easy. Linked list: “What comes after this thing?” Easy, if we already have that node. This distinction explains almost everything that follows.

Traversal and search

To traverse, set current = head and repeat: process current, then current = current.next. It takes O(n) not because “linked lists are O(n)” (too vague) but because:

To move from one node to the next we follow one link, and to visit n nodes we follow roughly n links.

Searching is the same story. To find D in A → B → C → D → E we ask “A? No. B? No. C? No. D? Yes.” In the worst case we inspect everything, because there is no direct way to jump to an arbitrary node. The reason matters more than the number.

4. Changing the structure: insertion and deletion

Remember why we invented this thing: we wanted to avoid physically moving elements when the structure changes. Take A → B → C → D and suppose we want A → B → X → C → D. Where does X live? Anywhere. We don’t move C or D. We simply change the relationships: B → C becomes B → X → C. The nodes haven’t moved. Only the links changed.

Try it: insert a node

Deletion has the same story

With an array, removing C from A B C D E means D and E have to shift left. With a linked list, B → C → D becomes B → D by setting B.next = D. C no longer belongs to the chain. Choose a node to delete and compare the two structures side by side:

Array: move data. Linked list: change relationships.

5. The famous “O(1) insertion”

This is where linked lists are often taught badly. You’ll hear “insertion in a linked list is O(1).” That’s not always true. If we already hold a reference to C and want to insert X after it, we change C → D into C → X → D: constant work. But if we only know “insert X after the 10,000th node,” we first have to find node 10,000:

find the locationO(n)
perform the insertionO(1)
totalO(n)

An operation can be cheap once we reach the right location, while reaching that location can still be expensive.

This idea appears throughout DSA. Slide k in a list or array of n = 1000 elements and watch where the cost actually lives:

Bars are linear, out of 1000 steps. Green rows are cheap, red rows are not.

6. Arrays vs linked lists: memory and why both exist

The central tradeoff

If linked lists make insertion and deletion so easy, why not use them for everything? Because we’ve been paying for those cheap modifications. We traded fast random access for cheap structural changes.

ArrayLinked list
The structure answers“Where is position i?”“Where do I go next?”
Random accessO(1): calculate the addressO(n): walk there
Insert at a known locationelements after it may movereconnect a few links
Extra memory per elementnoneone reference (next)

The computer doesn’t only care about Big-O

Array elements are close together in memory. When the CPU reads one, nearby data is often brought into the cache as well. Linked-list nodes can be scattered everywhere, so following the chain may mean jumping around memory. Even if both traversals are O(n), their real performance can differ significantly. That is one reason arrays are often faster in practice than Big-O alone suggests.

Big-O tells us how work scales. It does not tell us everything about the cost of performing that work on real hardware.

Try it: memory layout

Switch between the two. Arrows show the logical order. Compare it with the physical order, meaning the order of the addresses.

Why would anyone want this?

Linked lists aren’t “better arrays.” They solve a different problem. If your workload is read by index, read by index, read by index, an array is usually a much better fit. If it repeatedly changes the structure and you already know where those changes happen, a linked list can be useful. The question is not “which data structure is better?” but:

What operations does my problem need to be good at?

7. Head, tail and the ends of the list

Sometimes we also keep a tail reference. Without it, finding the last node means walking the entire list. This is another recurring idea in data structures: sometimes we store extra information so that an operation becomes cheaper later. We spend a tiny amount of memory to remember something we’d otherwise have to rediscover.

Operations at the ends are where linked lists shine. Inserting at the head is X.next = A; head = X. Deleting from the head is head = B. Inserting at the tail, with a tail pointer, is D.next = X; tail = X. Each is O(1): no shifting, no copying, no touching the rest of the list.

Python code (click to hide or show)
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

def traverse(head):
    current = head
    while current:
        print(current.value)
        current = current.next

def insert_at_head(head, value):
    node = Node(value)
    node.next = head
    return node              # the new head

def insert_after(node, value):   # O(1): we already hold `node`
    new = Node(value)
    new.next = node.next         # 1. the new node points onward first
    node.next = new              # 2. then the chain points to it

def delete_after(node):          # O(1): we hold the predecessor
    if node.next:
        node.next = node.next.next

Notice the order inside insert_after. If we set node.next = new first, nothing would remember where the rest of the list is.

8. Knowing the previous node: doubly and circular lists

Deleting the last node is more interesting. To delete D from A → B → C → D, we need C.next to become None. But how do we find C? In a singly linked list, D doesn’t know who points to it, so we walk from the beginning: O(n). What if nodes also knew their previous node? Each node would store prev | value | next. This is a doubly linked list. Compare the two:

Extra information can buy cheaper operations.

Three variations

A singly list is smaller, simpler and has fewer links to maintain, but it can’t move backward and some deletions need the predecessor. A doubly list moves in both directions and deletes a known node easily, at the cost of extra memory, more pointer updates and more opportunities for implementation mistakes. A circular list connects the last node back to the first (C.next = A), so there is no None. It fits situations with no natural end, such as repeatedly rotating through A → B → C → A → B → …. Each variation exists because of a requirement, not because textbooks needed another type. The right question is always: do we need the extra relationship badly enough to pay for it?

9. The complete mental model, and complexity

At this point a linked list should no longer look like class Node: .... It should look like this:

Node stores data and a reference. Head tells us where the chain begins. Next tells each node where to go. None marks the end of a normal singly linked list. Traversal follows the references. Insertion and deletion change references.

Complexity, derived instead of memorized

OperationWhy?Time
Access by indexMust follow linksO(n)

The asterisk matters, which is why complexity tables without context can be misleading. The better statement is:

Insertion is O(1) once we already have the relevant position or node. Finding that position may cost O(n).

10. The deeper lesson

Linked lists teach us something much bigger than linked lists. We started with “arrays are convenient.” Then we noticed a limitation: changing their structure can require moving many elements. So we asked, what if elements didn’t have to be next to each other? Then each element needs some way to find the next one, which produced nodes + references. That decision created new consequences: we can’t jump to arbitrary positions. So we gained cheap structural changes at the cost of expensive random access, extra memory and poorer locality.

This is what designing a data structure really is. You are not looking for a magical structure that makes everything fast. You are deciding:

Which operations should be cheap, and what am I willing to sacrifice to make them cheap?

11. And now something interesting happens

Remember where our DSA journey started: two pointers. We learned that it isn’t really a pattern. It is the idea of maintaining two positions with different jobs. With arrays those positions were left and right, or read and write. A linked list has no index-based jumping, but we can still have two positions moving through the structure. What happens if one moves one step at a time while another moves two?

At first this may seem like a strange thing to do. Why deliberately move two pointers at different speeds? That question is exactly where the next chapter begins.
