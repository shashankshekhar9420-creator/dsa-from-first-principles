Getting Comfortable with Linked Lists

In the previous article, we asked a fundamental question:

Why would we need a linked list when arrays already exist?

We discovered that a linked list makes a different tradeoff. An array gives us:

“Tell me the position, and I can jump there.”

A linked list gives us:

“Give me a node, and I can follow its relationship to the next node.”

That difference changes how we think about almost every operation. With an array, we are often thinking in terms of:

index → element

With a linked list, we should start thinking in terms of:

node → next node → next node → ...

So before we jump into clever algorithms like slow and fast pointers, we need to become comfortable with the basic mechanics. Not by memorizing a collection of linked-list functions. But by repeatedly asking three questions:

Where am I?

Where do I need to go?

Which link needs to change?

We’ll start with the simplest possible operations and gradually build toward more interesting ones. Every figure below is an interactive stepper or diagram you can drive.

1. First, Let's Build a Linked List

Suppose someone gives us an ordinary Python list:

values = [10, 20, 30, 40, 50]

and asks us to turn it into:

10 → 20 → 30 → 40 → 50 → None

What actually needs to happen? We need to create five nodes. Each node needs:

  • a value
  • a reference to the next node

Let's represent that in Python.

Python code (click to hide or show)
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

Now we need to connect the nodes.

Python code (click to hide or show)
def build_linked_list(values):
    head = None
    tail = None

    for value in values:
        node = Node(value)

        if head is None:
            head = node
            tail = node
        else:
            tail.next = node
            tail = node

    return head

We can use it like this:

head = build_linked_list([10, 20, 30, 40, 50])

The resulting structure is a chain of references:

The list starts at head, follows next links through 10, 20, 30, 40, 50, and terminates at None.

2. Why Do We Need Both head and tail While Building?

This is worth understanding. When we create the first node, 10, it is both the beginning of the list and the end of the list. So both head and tail point to it.

When we create 20, we want 10 → 20. We need to attach 20 after the current last node. If we only have head, finding the last node would require walking through the entire list every time. Instead, we maintain:

head → first node

tail → last node

So when a new node arrives:

tail.next = node
tail = node

We immediately know where to attach it. This is a tiny example of a broader data-structure principle:

Sometimes storing extra information makes future operations cheaper.

We’re spending one extra reference (tail) to avoid repeatedly searching for the end.

The important visual lesson: head and tail are references to nodes. They are not nodes themselves.

3. Traversing the List

Now that we have a linked list, the most basic thing we can do is walk through it. Suppose:

head → 10 → 20 → 30 → 40 → None

How do we print everything? We cannot say for i in range(len(values)): print(values[i]) because there is no direct indexing. Instead, we start at the head and repeatedly move to the next node:

Python code (click to hide or show)
def print_list(head):
    current = head

    while current is not None:
        print(current.value)
        current = current.next

The important line is:

current = current.next

This is essentially the fundamental operation of a linked list. We are saying:

“I am currently here. Where does this node tell me to go next?”

Then we follow that link until current is None.

Traversal is literally: current → next → next → next → None.

4. Finding the Length

Now that we know how to traverse, finding the length is almost automatic. We walk through the list and maintain a counter:

Python code (click to hide or show)
def length(head):
    count = 0
    current = head

    while current is not None:
        count += 1
        current = current.next

    return count

Why does this work? Because every time we successfully reach a node, we’ve found one more element. For 10 → 20 → 30 → 40 → None, we count 1, 2, 3, 4.

Notice how this differs from many array implementations. With an array, the length is typically maintained as part of the structure (O(1)). With a basic linked list, if all we have is head, we don’t inherently know how many nodes exist. We have to walk the chain and count them:

MetricArraySingly Linked List
Length timeO(1) (stored attribute)O(n) (must traverse chain)
Extra spaceO(1)O(1)

A useful observation

We’re beginning to see a recurring pattern:

This isn't a rule to memorize. It follows directly from the structure.

5. Searching for a Value

Suppose we want to find 30 in 10 → 20 → 30 → 40 → 50. We can't jump to it. So we start from the head: 10? No. 20? No. 30? Yes.

Python code (click to hide or show)
def contains(head, target):
    current = head

    while current is not None:
        if current.value == target:
            return True

        current = current.next

    return False

There is another important property here: we can stop as soon as we find the value. If we search for 10, it is found immediately in 1 step (O(1) best case). If we search for 50, it is found last in 5 steps (O(n) worst case). If the value is not present, we walk all the way to None.

6. Inserting at the Beginning

Now we're ready to modify the list. Suppose we have 20 → 30 → 40, and we want 10 → 20 → 30 → 40. Where should the new node go? Before the current head.

  1. Create: node = Node(10)
  2. Point to old head: node.next = head
  3. Update head: head = node
Python code (click to hide or show)
def insert_at_beginning(head, value):
    node = Node(value)

    node.next = head
    head = node

    return head

Notice how little work was required. We didn't touch 20, 30, or 40. We only changed the beginning of the chain. Therefore:

Insert at beginning: O(1)

Why is this so different from an array?

With an array [A, B, C, D], inserting X at the beginning requires shifting every existing element rightward to make room (O(n)). In a linked list, no existing node moved in memory: we simply changed one relationship and one reference.

7. Inserting at the End

Suppose we have 10 → 20 → 30 and want 10 → 20 → 30 → 40. If we already maintain a tail reference, this is constant work:

Python code (click to hide or show)
def insert_at_end(head, tail, value):
    node = Node(value)

    if head is None:
        return node, node

    tail.next = node
    tail = node

    return head, tail

The key operation is tail.next = node; tail = node. Constant work: O(1).

But what if we don't have a tail?

Suppose all we have is head → 10 → 20 → 30 → None. To insert at the end, we'd have to find 30 first. That means traversing from 10 all the way to 30: O(n).

Same linked list. Same operation. Different information available. Different complexity.

8. Deleting the Head

Suppose we have head → 10 → 20 → 30 → 40 and want 20 → 30 → 40. What needs to change? Only head.

Python code (click to hide or show)
def delete_head(head):
    if head is None:
        return None

    return head.next

We simply make the second node the new first node. The old 10 is no longer part of the list reachable from head. Therefore: Delete head: O(1). No traversal. No shifting. No searching.

Try it: change the head

Deleting the head doesn't require deleting or moving the other nodes. We only change what head points to.

9. Deleting the Last Node

Now things become slightly more interesting. Suppose 10 → 20 → 30 → 40, and we want 10 → 20 → 30. The obvious question is: Which link must change?

The answer: 30.next must become None. But in a singly linked list, 40 doesn't know who comes before it. So we must traverse until current.next.next is None to stop at 30:

Python code (click to hide or show)
def delete_last(head):
    if head is None:
        return None

    if head.next is None:
        return None

    current = head

    while current.next.next is not None:
        current = current.next

    current.next = None

    return head

The important lesson isn't the condition itself. It's:

To delete the last node in a singly linked list, we need to find its predecessor.

And finding that predecessor requires traversal: Delete last node: O(n).

Try it: delete the last node

10. Deleting a Node by Value

Now suppose we have 10 → 20 → 30 → 40 and want to delete 30. We don't actually modify 30. We modify the node before it: 20.next = 40.

To remove a node from a singly linked list, we usually need access to its predecessor.

Python code (click to hide or show)
def delete_value(head, target):
    if head is None:
        return None

    if head.value == target:
        return head.next

    current = head

    while current.next is not None:
        if current.next.value == target:
            current.next = current.next.next
            return head

        current = current.next

    return head

Look at the crucial line: current.next = current.next.next. When current is 20, current.next is 30 and current.next.next is 40. Setting current.next = 40 bypasses 30 completely.

Try it: bypass a node

Deletion in a linked list often means bypassing a node, not physically moving the remaining nodes.

11. What If the Value Appears More Than Once?

Suppose: 10 → 20 → 30 → 20 → 40, and we ask: Delete 20. Which one? This is a specification question. Our function in section 10 deleted only the first occurrence. If instead we want to delete every occurrence, we continue traversing:

Python code (click to hide or show)
def delete_all(head, target):
    while head is not None and head.value == target:
        head = head.next

    current = head

    while current is not None and current.next is not None:
        if current.next.value == target:
            current.next = current.next.next
        else:
            current = current.next

    return head

Try it: first occurrence vs all occurrences

The algorithm depends on the exact operation we are defining: first occurrence, last occurrence, or every occurrence.

12. Reversing a Linked List

Now we reach our first operation where we are not simply adding or removing something. We want to turn 10 → 20 → 30 → 40 → None into 40 → 30 → 20 → 10 → None.

The links currently point rightward. We need them to point leftward. But if we change 10.next = None before remembering where 20 is, we lose our path to the rest of the list. So we need to remember two things:

Where am I? (current)

Where does the rest of the list begin? (next_node)

This requires three references during the loop:

  • Step 1: Save the future: next_node = current.next
  • Step 2: Reverse the link: current.next = previous
  • Step 3: Move references forward: previous = current; current = next_node
Python code (click to hide or show)
def reverse(head):
    previous = None
    current = head

    while current is not None:
        next_node = current.next
        current.next = previous
        previous = current
        current = next_node

    return previous

13. Let's Actually Watch the Reversal

Let's trace it carefully:

  • Initially: previous = None, current = 10. Save 20. Reverse: 10 → None. Move: previous = 10, current = 20.
  • Next: Save 30. Reverse: 20 → 10. Move: previous = 20, current = 30.
  • Next: Save 40. Reverse: 30 → 20. Move: previous = 30, current = 40.
  • Next: Save None. Reverse: 40 → 30. Move: previous = 40, current = None.
  • Stop: current is None. Return previous (now pointing to 40, the new head!).

Try it: reverse the chain

Use Next and Previous to step through every iteration and link reversal. Watch the invariant hold true at every single step.

The invariant: The portion before current is already reversed. The portion beginning at current is still untouched.

14. Why Doesn't Reversing Take O(n²)?

A common first impression is: “We’re changing every node, so maybe we repeatedly scan things.” But we’re not. Each node is visited exactly once, performing constant work: save next, reverse link, move previous, move current.

Time: O(n)  |  Space: O(1)

The important point is: we changed the entire direction of the chain without creating a second linked list. We reused the existing nodes.

15. Finding the Middle of a Linked List

Suppose 10 → 20 → 30 → 40 → 50, and we want 30 (the middle node). In an array, we calculate middle = n // 2 and jump there. But in a linked list, we don't have random access.

We could traverse the list to find its length, divide by 2, and traverse again. But there is a more interesting way: two pointers moving at different speeds.

Python code (click to hide or show)
def find_middle(head):
    slow = head
    fast = head

    while fast is not None and fast.next is not None:
        slow = slow.next
        fast = fast.next.next

    return slow

Try it: slow and fast meet the middle

Toggle between an odd-length list (5 nodes) and an even-length list (6 nodes). Watch how fast travels twice as fast as slow.

16. Why Does the Trick Work?

The trick works because of relative speed. If slow moves 1 step while fast moves 2 steps, whenever fast has travelled the entire list (say, 10 steps), slow has travelled half of that (5 steps):

Sometimes we don't need to calculate a quantity directly. We can make two things move in a relationship that causes the desired information to reveal itself.

17. Finding the Nth Node From the End

Suppose we want the 2nd node from the end in 10 → 20 → 30 → 40 → 50 (answer: 40). Instead of two passes, we maintain a fixed gap between two pointers:

  1. First advance fast by n nodes. (For n = 2, fast is at 30 while slow is at 10.)
  2. Now move both pointers one step at a time, keeping the distance constant.
  3. When fast reaches None, slow is exactly at the nth node from the end!
Python code (click to hide or show)
def nth_from_end(head, n):
    fast = head
    slow = head

    for _ in range(n):
        if fast is None:
            return None
        fast = fast.next

    while fast is not None:
        slow = slow.next
        fast = fast.next

    return slow

Try it: maintain a gap

The invariant: Keep fast exactly n nodes ahead of slow. As both move together, that distance remains constant.

18. Removing the Nth Node From the End

To delete the nth node from the end, we need the node before it. So we maintain a pointer one position behind our target. A dummy node makes edge cases (like removing the head) effortless:

Python code (click to hide or show)
def remove_nth_from_end(head, n):
    dummy = Node(0)
    dummy.next = head

    slow = dummy
    fast = dummy

    for _ in range(n + 1):
        fast = fast.next

    while fast is not None:
        slow = slow.next
        fast = fast.next

    slow.next = slow.next.next

    return dummy.next

Why n + 1? Because slow needs to end up at the predecessor of the node being deleted. Then slow.next = slow.next.next cleanly bypasses it.

19. Removing Duplicates From a Sorted List

Consider 10 → 20 → 20 → 30 → 30 → 30 → 40. Because the list is sorted, duplicate values are always adjacent! We don't need a hash set or extra memory. If current.value == current.next.value, we bypass current.next:

Python code (click to hide or show)
def remove_duplicates(head):
    current = head

    while current is not None and current.next is not None:
        if current.value == current.next.value:
            current.next = current.next.next
        else:
            current = current.next

    return head

Let's watch how adjacent duplicates are detected and bypassed on 10 → 20 → 20 → 30 → 30 → 40:

  • At 10: 10 != 20 → no duplicate, advance current to 20.
  • At first 20: 20 == 20 → duplicate found! Bypass second 20: 20 ───→ 30.
  • At first 30: 30 == 30 → duplicate found! Bypass second 30: 30 ───→ 40.
  • At 40: current.next is None → finished!

Try it: bypass adjacent duplicates

20. Why Don't We Move current After Removing a Duplicate?

This tiny detail is worth understanding. Suppose: 10 → 20 → 20 → 20 → 30. When we remove the first duplicate 20, the next node is still 20! Therefore, we must stay where we are and check again:

duplicate found → change link, stay

no duplicate → move forward

Try it: remove duplicates

Sometimes the correct pointer movement depends on what happened at the current position.

21. The Patterns We've Quietly Learned

We started with simple tasks (build, traverse, count, search), changed structure (insert, delete), rearranged links (reverse), and extracted information from pointer motion (middle, nth from end). Five underlying patterns emerged:

  • Pattern 1: Walk the chain. When needing information, follow current = current.next.
  • Pattern 2: Change a relationship. Modifying lists means changing links, not shifting nodes.
  • Pattern 3: Keep the previous node. Deletion in singly linked lists requires access to the predecessor.
  • Pattern 4: Use multiple references when one isn't enough. Reversal requires prev, curr, and next so we never drop the rest of the list.
  • Pattern 5: Relative movement reveals information. Different pointer speeds or constant offsets eliminate extra passes.

22. A Small Complexity Summary

Now all major operations can be derived naturally from the structure:

The complexity isn't something we memorized. It is a consequence of how the structure works.

23. The Most Important Mental Shift

When looking at an array, your eyes naturally see indices: 0, 1, 2, 3, 4. When looking at a linked list, don't think indices. Think:

A linked list is fundamentally a chain of relationships. Once you see that, the algorithms become much less mysterious.

24. And This Is Why We're Not Jumping Into “Linked List Patterns” Yet

There is a temptation when learning DSA to immediately collect tricks: reverse, slow/fast, cycle detection, merge lists, palindrome, intersection. But that's backwards. First we need to be comfortable with the primitive operations: current = current.next, node.next as an actual link, and multiple pointers having distinct jobs. Only then do sophisticated algorithms become intuitive.

25. The Bridge to What Comes Next

We’ve now seen two pointers moving at different speeds to find the middle, and two pointers maintaining a gap to find the nth node from the end. That gives us a beautiful next question:

If two pointers move through a structure at different speeds, what else can their relative movement tell us?

Consider a list where the last node links back to an earlier node: A → B → C → D → E → C. There is a cycle. Traversal would run forever. But what if slow moves 1 step and fast moves 2 steps, and both are trapped inside the cycle?

Try it: relative motion in a cycle

The faster pointer gains on the slower pointer by 1 step in every iteration. Eventually, they must collide. We can detect a cycle without storing any visited nodes in memory. That is the deeper idea behind slow and fast pointers. And that is where our next chapter begins.
