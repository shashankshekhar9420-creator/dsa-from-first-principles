A Few Linked-List Ideas That Make Everything Easier

We have now learned how to walk through a linked list, insert nodes, delete nodes, reverse a list and use multiple pointers. The basic mechanics are becoming familiar. But a few ideas make linked-list problems dramatically easier once you see them. One of them is particularly simple: what if we had a node before the first node?

That sounds almost pointless. Why create a node that is not part of our data? It turns out that this tiny idea removes a surprising amount of complexity, and we will build up to it from scratch.

Sometimes adding something artificial makes the real logic simpler.

This post follows the dummy node into building, deleting and merging lists. Each idea has a figure to step through, there are sliders and a "you drive it" merge, and the code can be hidden with the button at the top.

1. The problem with building a list from scratch

Say we are given data and need to construct 10 → 20 → 30 by adding nodes one at a time. There is an annoying question: what happens when the list is empty? Initially head = None. Adding 10 has no existing node, so it needs a special case. Adding 20 needs different logic.

The naive way

if head is None:        # first node: special
    head = new_node
else:                   # every later node: normal
    tail.next = new_node
    tail = new_node

Our algorithm has two worlds: an empty list with special handling, and a non-empty list with normal handling. This is not wrong, but special cases are where pointer code becomes hard to reason about.

Key insight: give ourselves something to build onto

The dummy node gives us something to build onto from the very beginning.

2. Introducing the dummy node

Let us invent a node that is not really part of our data. For the real list 10 → 20 → 30 we create dummy → 10 → 20 → 30. The dummy holds no real value. Its only purpose is to be a stable starting point, like scaffolding: we do not care about the dummy itself, we care about everything after it.

When we add the first real node, it behaves exactly like every other insertion: tail.next = node; tail = node. The exceptional first case becomes an ordinary case.

The dummy is not part of the answer

At the end our real list begins at dummy.next. The pattern appears constantly:

dummy = Node(0)        # the value (0, -1, anything) does not matter
dummy.next = head
current = dummy
# ... work ...
return dummy.next

The dummy helps construct or manipulate the list. It does not belong to the final answer.

3. The dummy node eliminates special cases

Here is the deeper reason we like it. Suppose we want to delete a node. Without a dummy, deleting the head is special (head = head.next), while deleting anything else needs its predecessor (predecessor.next = ...). Two cases, so more reasoning. With a dummy, the predecessor of 10 is simply dummy.

The dummy node manufactures a predecessor for the head.

Removing every node with a given value

We start current at the dummy and inspect current.next rather than current, so that current always represents the predecessor. If current.next matches, we bypass it with current.next = current.next.next. Pick a target. Try 10 (the head) and watch that the same rule is used.

Python code (click to hide or show)
def remove_value(head, target):
    dummy = Node(0)
    dummy.next = head

    current = dummy

    while current.next is not None:
        if current.next.value == target:
            current.next = current.next.next   # bypass, do not move
        else:
            current = current.next             # move only when not deleting

    return dummy.next

The same code handles deleting the head, the middle and the tail, with no separate cases. Notice that we do not advance current after a deletion, because the new current.next has not been checked yet.

Why not just use a tail pointer?

These two ideas are sometimes confused because both are extra references. They solve different problems.

ToolQuestion it answersHelps with
headWhere is the beginning?finding the list
tailWhere is the end?appending efficiently
dummyWhat is a stable node before the beginning?removing boundary cases at the head

They are not alternatives; we can use all three. Usually we do not even keep a separate head if the dummy already gives us head = dummy.next.

4. Merging two sorted arrays

Now let us combine two lists. Before touching linked lists, understand the idea with arrays: A = [1, 4, 7] and B = [2, 3, 8] should become [1, 2, 3, 4, 7, 8].

The naive way

Concatenate and sort. But both inputs are already sorted, so sorting throws away information we already have.

Key insight: only the smallest remaining element of each matters

Compare the first elements. The smaller one must be the next element of the merged result. Take it, advance that pointer, and repeat. Drag the slider to place elements one at a time.

Everything already placed in the result is in sorted order. The next answer must be the smaller of the two current candidates.

Python code (click to hide or show)
def merge_arrays(a, b):
    i = 0
    j = 0
    result = []

    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            result.append(a[i])
            i += 1
        else:
            result.append(b[j])
            j += 1

    while i < len(a):
        result.append(a[i])
        i += 1

    while j < len(b):
        result.append(b[j])
        j += 1

    return result

5. Merging two sorted linked lists

With linked lists, list1 = 1 → 4 → 7 and list2 = 2 → 3 → 8, the reasoning has not changed. At every point compare the current value of each list and take the smaller. Only how we move forward changes: i += 1 for arrays becomes current = current.next for linked lists. The algorithm survives while the implementation changes with the data structure.

We need somewhere to build the result, and this is exactly where the dummy node shines. Every insertion is the same two lines, and we never ask "is this the first node?":

tail.next = chosen
tail = tail.next

Step through the full merge

Three pointers move: list1 and list2 mark the next unprocessed node of each input, and tail marks where the result ends. Yellow nodes are being compared, grey nodes have been taken, green nodes are in the result. Presets include an empty input and two empty inputs.

The complete algorithm

Python code (click to hide or show)
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None


def merge_two_lists(list1, list2):
    dummy = Node(0)
    tail = dummy

    while list1 is not None and list2 is not None:
        if list1.value <= list2.value:
            tail.next = list1
            list1 = list1.next
        else:
            tail.next = list2
            list2 = list2.next

        tail = tail.next

    if list1 is not None:
        tail.next = list1
    else:
        tail.next = list2

    return dummy.next

Do not memorize it. Give every pointer a job.

PointerJob
dummystable anchor: the beginning of the result
tailmoving end: where the next node is attached
list1current unprocessed candidate from list 1
list2current unprocessed candidate from list 2

Reuse existing nodes instead of creating new ones

We could create Node(2) and attach that copy. But the node containing 2 already exists, so we can move that very node into the merged chain with tail.next = list2. We are not copying data; we are changing relationships.

The merged list can be built by rearranging references rather than creating replacement nodes.

6. A dangerous detail: save before you break

When we execute tail.next = list2 we then need list2 = list2.next. More generally, we are changing links, and changing a link before saving where it used to point can cost us access to part of the structure. This is the same reason we needed next_node when reversing a list.

Consider current at 10 in 10 → 20 → 30 → 40. If we run current.next = None, then unless we saved 20 earlier, there is no path left to the rest. Compare the unsafe and the safe order.

Before breaking a link, preserve whatever lies beyond it if you will need it later.

The rhythm is save, change, move. You do not always need a temporary variable, but you should always think about whether you do: "If I change this link right now, can I still reach everything I need?"

7. What happens when one list runs out?

Suppose list1 = 1 → 3 → 5 and list2 = 2. We take 1, then 2. Now list2 is None and the comparison loop cannot continue, but we are not done: 3 → 5 remains. Because list1 was already sorted, we do not compare those nodes against anything. We attach the whole remaining chain in one move:

if list1 is not None:
    tail.next = list1
else:
    tail.next = list2

Why is attaching the remainder safe?

Every element already placed is at most 3, because otherwise we would have chosen 3 earlier, and the rest of list1 is sorted. So 3 → 5 is exactly the correct remainder.

Once one sorted input is exhausted, the remainder of the other input is already in the correct order.

9. How much work is a merge?

Every node is considered at most once, so with m nodes in list1 and n in list2, the time is O(m + n). We cannot do better in general, since we must at least process every node that appears in the result. Drag the slider for the total number of nodes.

The extra space is O(1): only the dummy node is created, and list1, list2, tail are references. A solution that creates m + n new nodes would use O(m + n) extra space.

Create new nodesReuse nodes (ours)
TimeO(m + n)O(m + n)
Extra spaceO(m + n)O(1)
Original listsleft intactconsumed: their nodes are rearranged

The honest trade-off: reusing nodes is cheaper, but it destroys the original lists. If the caller still needs them, copying is the right choice. The lesson is not that one is better, but asking "do I need new data, or only a new arrangement of existing data?"

11. The bigger pattern

Look at what we actually did. We had two ordered streams and, at every step, looked only at the frontier of each. We never inspected 7 while deciding between 1 and 2. The sorted property let us ignore everything behind the current positions, the linked structure let us rearrange relationships cheaply, the dummy made construction uniform, and the pointers kept track of exactly where we are.

At the beginning, linked lists looked like a row of nodes. Now they should look like relationships. With arrays, many problems are about positions. With linked lists, many problems are about relationships.

The question is often not "what value should I calculate?" but "what should each link point to after this operation?"

12. A useful way to recognize these problems

When manipulating a linked list, develop the habit of asking four questions.

  1. Where am I? That is current.
  2. Where do I need to go next? That is current.next.
  3. What am I about to disconnect? If it is the only path to something I need, save it: next_node = current.next.
  4. What relationship needs to change? For example previous.next = current.next, or tail.next = chosen_node, or current.next = previous.

And before you start, ask whether the head is awkward. If an operation treats the first node differently, a dummy node can probably make it ordinary.

13. The evolution of the idea

We now know how to construct a list, traverse it, count it, search it, insert into it, delete from it, reverse it, use multiple pointers, maintain a fixed distance between pointers, build a new chain, use a dummy node to eliminate boundary cases, reuse existing nodes, preserve references before changing links, and merge sorted structures.

IdeaWhat it teaches
Traverse, insert, deleteFollow links, change links.
Reverse a listPreserve links before overwriting them.
Slow and fast pointers, fixed gapRelative position finds the middle and the nth from the end.
Dummy nodeTurn an awkward boundary into an ordinary case.
Merge two sorted listsExploit sortedness, reuse nodes, attach the known-good remainder.

These are not isolated tricks. They all come from a few simple ideas: follow links, change links, preserve links, maintain invariants. And now there is one unresolved question. We have seen that slow moving one step while fast moves two finds the middle, and a fixed gap finds the nth node from the end. But what else can relative speed tell us? What happens when the list does not end, when following next eventually brings us back to a node we have already visited?

The pointers will no longer just help us traverse the list. They will help us reason about the shape of the list itself.
